**HTTP response streaming — design round (the AI SDLC prerequisite).** Eric opened the
arc: before the AI SDLC feature, design and implement HTTP response streaming (token
segments). Design converged in-conversation through three of his rulings:

1. **"The flux/mono is not good enough."** Code study confirmed why: the edge
   (`AsyncHttpResponse.handleStreamContent`) does chunk-relay an `x-stream-id` response,
   but structured Map segments BUFFER into one JSON array at completion, there is no SSE
   framing or in-band terminal/error event (the error path rewrites status after the
   head may be committed), and the producer API is Reactor-typed + JVM-only — invisible
   to Event Script, graphs, and the polyglot wrappers (where LLM tokens will come from).
2. **The model is platform-native streaming**: caller → callee; callee → caller's
   reply_to continuously until an end-of-transmission signal. The HTTP edge IS the
   caller today (HttpRouter sets reply_to=async.http.response@origin + cid;
   AsyncContextHolder has touch()). Today the return route is single-shot; the feature
   makes it multi-shot with progressive rendering. No new substrate, backward
   compatible, language-neutral.
3. **Envelope-vs-wire separation + the marker name**: internal reserved ENVELOPE header
   `x-event-stream: data|eof|exception` (ObjectStream vocabulary; consumed by the edge
   like x-stream-id/x-ttl, never on the wire); the public HTTP surface stays
   standards-only (chunked/HTTP-2 framing; `Content-Type: text/event-stream` for SSE).
   Landscape question answered: SSE IS the de facto wire for chat token streams and
   agent progress events (OpenAI/Anthropic/Gemini; MCP Streamable HTTP, A2A), and the
   live-watch window of long-running workflows (suspension stays on suspend/resume).

**D9 refined on Eric's review question ("would instances=1 serialize all HTTP
responses? or a pool of async.http.response.stream.{n}?"): the single lane became a
SHARDED POOL** — `async.http.response.stream.{n}` (pool size `event.stream.lanes`,
default 8, clamp 1..64), lane = floorMod(hash(requestId), lanes): one request's segments
stay strict-FIFO on one single-instance lane while different requests stream
concurrently (partition-by-key; per-request dynamic routes considered and rejected —
register/release lifecycle + leak surface for µs-scale rendering). The housekeeper's
in-band timeout targets the SAME lane so it cannot overtake segments. New concurrency
net: four parallel 50-segment bursts, each strictly ordered. **The concurrency net
then caught a REAL race under full-suite load (segment skipped: expected 25 got 26):
`flushPending` ran on BOTH the request's reply lane and the vert.x drainHandler
(event-loop thread) once the write queue had ever filled — two threads polling the
non-thread-safe pending queue and writing the response concurrently. The isolated run
never filled the write queue, so the drain path never raced. Fix: a per-request
ReentrantLock in EventStreamState guarding offer/flush/end/cleanup (pings use tryLock —
best-effort, never block a flush). The burst mock now pads segments to 8KB so the drain
path is exercised DETERMINISTICALLY every run, not only under load. Durable lesson: a
vert.x drainHandler is a second concurrent flusher — any hand-rolled pending queue it
shares with a producer thread needs a lock, and the regression test must force
writeQueueFull rather than hope for it.** 20 streaming tests green ×3 consecutive runs;
full suite 446/446.

**D9 REVISED to Eric's checkout-pool design (his ruling on reviewing the sharded pool:
two request ids hashing to one lane share a serialization point — a routing hazard).**
The pool became a **LIFO stack of 500 dedicated lanes** (pinned to the
async.http.response instance count — `event.stream.lanes` knob DELETED): a `stream: true`
request checks out one lane for its lifetime (`EventStreamRenderer.checkoutLane()`,
stored on the AsyncContextHolder per Eric's direction — direct access to the original
HTTP request/response), and the lane returns to the stack when the context closes —
the "ready" signal pattern of the reactive manager/worker design. Release lives in
`HttpRouter.closeContext` (the funnel for EVERY termination path: normal end, hardClose,
client disconnect, housekeeper, sendError — and the atomic contexts.remove makes it
exactly-once). Empty stack → immediate **HTTP-503 "Streaming response pool exhausted"**
(deterministic back-pressure; message is engine-parity surface for the Rust twin).
Checkout collapsed the interim `HttpRequestEvent.streamResponse` tag "12" — both reply
sites resolve the lane from the holder by requestId, returning HttpRequestEvent to its
pre-feature shape. An idle lane costs a little memory, no CPU (Eric). New tests:
exhaustion → 503 → recovery (drain via the public pool API), lane-returns-on-completion,
LIFO reuse. Gates after revision: streaming 23/23 (17 e2e + 6 units), full suite
449/449, mkdocs strict clean, ai-contract-provider 19/19. Durable lesson: a
hash-sharded pool trades collision behavior for zero bookkeeping — when each unit of
work needs true isolation, check out a dedicated resource and return it at a single
lifecycle funnel instead.
