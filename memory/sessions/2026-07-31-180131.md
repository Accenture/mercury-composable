**Root cause (confirmed with evidence):** `GETDEL` needs Redis 6.2+. The
`embedded-redis 1.4.3` library inside redis-standalone bundles REAL redis-server
binaries per platform — **6.2.6/6.2.7 for macOS/Linux but only 5.0.14 for Windows**
(the community Windows port stopped there; no OSS Windows build ≥ 6.2 exists). Exactly
the Docker-less VDI audience the helper serves ([[conv-helpers-docker-less]]); macOS

deployed environments are Linux, but enterprise managed Redis versions (AWS for one
field installation; also Azure/GCP) are outside our control.

**The fix (extensions/minigraph-state-redis):**
- `RedisStateConnection` detects the server version from `INFO server` once per
  connection and logs it: "(Redis {version}, consume via GETDEL | transactional
  GET+DEL)". New `consume(key)` strategy method: **≥ 6.2 → native GETDEL** (unchanged
  modern path); **older → MULTI/EXEC transaction pairing GET with DEL** (supported
  since Redis 1.2) — Eric's "two commands" made race-free, so the ADR-0010
  at-most-once consume-on-retrieve guarantee holds on BOTH paths (plain sequential
  GET→DEL would open a double-resume window). Unparseable version or INFO failure
  (some managed servers restrict INFO) → the transactional fallback, which works
  everywhere. The fallback transaction serializes on the shared connection (Lettuce
  MULTI state must not interleave across threads; suspend/resume is human-checkpoint
  scale).
- `RetrieveModel` routes through `consume()`; javadoc no longer claims "Requires
  Redis 6.2 or later".
- **Tests 10/10:** version-parse + threshold units (6.2.0/6.2.7/7.4.1/8.0 true;
  6.0.9/5.0.14.1/3.0.504/unknown/x.y.z/7 false — unparseable chooses the safe
  fallback) AND the transactional strategy exercised FOR REAL against the embedded
  6.2 server via a forced-strategy override (MULTI/EXEC works on every version) with
  the identical consume contract (record once, duplicate resume empty, key gone).
  The startup log proved detection live: "(Redis 6.2.11, consume via GETDEL)".
- Docs: workflow-suspension guide (both GETDEL statements now version-aware),

**Also (field question, same session): outbound content-based partitioning — answered
and documented.** The field wants a partitioner inspecting a confidential Kafka header
or payload key-value. Analysis (verified against the kafka-clients 4.2.0 interface):
the Kafka `Partitioner` API receives key+value but **NOT record headers** — so
header-based partitioning is impossible at that layer; a custom `partitioner.class` in
the externalized producer template works TODAY for payload inspection (KafkaClientConfig

explicit `partition` header, which bypasses all partitioners — the outbound mirror of
second-level routing's content inspection. Precedence: explicit partition header >
template partitioner.class > SimpleRandomPartitioner (unkeyed) / murmur2 (keyed).
