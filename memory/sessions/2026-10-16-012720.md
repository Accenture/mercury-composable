## Answers (checked against the API docs, the platform availability table for Bedrock, and the helper's code)

- Native inputs are images and PDFs as content blocks (each PDF page is rendered to an image and its text extracted) and plain
  text files as text documents. Word and Excel are not document types: convert to text or PDF first. On Bedrock there is no code
  execution, no Agent Skills and no Files API; sources are base64 only and the request ceiling is below the Claude API's 32 MB.
  PDF pages per request: 600 with a 1M-context model, 100 under 1M (Haiku 4.5); a page costs 1,500-3,000 text tokens plus its
  image. The helper today accepts only string content in a turn.
- The call is stateless: every request carries the whole conversation. Prompt caching is a prefix match on re-sent bytes
  (5-minute or 1-hour TTL), not state; the Files API stores uploads but is not on Bedrock. The graph holds the conversation.
- No server-side session accumulates pages. The patterns: the whole document in one cached request; chunk-and-reduce with the
  graph's state machine as the session (iterate page ranges, structured extraction per range, reduce, suspend for a human);
  retrieval for a small part of a large corpus.

## Decisions (Eric)

- Large payloads travel OUT OF BAND: the event carries a reference to a blob in a shared store (the temp file system when the
  helper and the graph application share a container, else S3, Redis or a database); the helper dereferences before the API call.
- A conversion's verdict is a LIST of per-block outcomes, each with its own confidence; the rendered machine-readable output and
  the chunks needing further analysis go to the shared folder for the next node (all green / partial / the list).
- Not every block belongs in the constructed graph: legal text is mostly elaboration. Every later AI round reads the previous
  round's machine-readable output, so each output is the next round's input contract.
- Other file formats need tools made available to the graph (an Excel parser); common tools and MCP are components of the epic.
- The sample documents are client proprietary: nothing about them enters any repository. A higher model may be tested through

## Design proposed (to become an RFC)

- A turn's content is a string or a list of typed parts: text, image, document. A binary part by reference with a declared
  resolver per scheme (a file under a configured root, S3 next; other stores plug in), optional sha256 verified and recorded in
  the trace, lifecycle with the producer, platform ceilings checked before encoding; the zero-copy URL source is Claude API only.
- The manifest: blocks with id, parent, kind (from a document profile's vocabulary), role (operative / supporting / elaborative),
  gist, depends_on and modifies, confidence, issues, continues, payload; the graph's thresholds decide status and next (none /
  analyze / human). A profile (legal-agreement, processing-spec) is a system prompt, a payload schema and a renderer living with
  the application; the helper only sees a schema. Selection is by reachability from operative blocks; the bias is over-include,
  since a rule filed as elaboration is the hazard. Big tables are descriptors with the data in the store.

## Lab experiment (2026-10-16, outside the repositories, neutral names)

- Lab folder with the inputs under neutral names (doc-a a processing specification, doc-b and doc-c agreements, a code-mapping
  spreadsheet), a venv with the SDK's Bedrock extra, pypdf and openpyxl, and a harness: split (15 pages, one-page overlap),
  spreadsheet to CSV, pass 1 with the manifest schema as structured output, pass 2 reconcile on the blocks alone, a two-run
  classifier that writes the manifest and the pending items, a report with agreement. Haiku 4.5 on Bedrock's classic runtime
  surface. The granularity rule (one block per step, rule, definition,
  formula or table, with a parent) was added after the first smoke summarized whole sections.
- Runs: doc-a 28 pages x2 chunked + whole; doc-c 31 pages x2 + whole; doc-b 124 pages x2 (9 chunks); the spreadsheet; two
  reconciles. About 3.4 USD and 33 minutes; ~2.3K input tokens per page. One chunk hit the 32K output cap and its structured
  reply was unparseable.
- Findings: (1) the model's SEGMENTATION is the unstable part - on its own ids two identical runs share 30 of ~75, 19 of ~85 and
  202 of ~490 rendered blocks with identical payloads 6 / 1 / 1; matched on the source quote, 44-60% of blocks are the same
  segment and of those 84-91% carry the same role, kinds agree 32% on the spec and 76-91% on the agreements, payload prose
  similarity 0.3-0.5. (2) Whole-document runs are coarser (41 vs 77-80, 61 vs 99-93 blocks). (3) Self-reported confidence never
  discriminates (0.92-0.95 everywhere); the issue codes do. (4) Agreements are operative-heavy (doc-b 387 of 532) and a fifth of
  those are legal obligations outside the processing scope. (5) Pass 2 on the blocks alone is useful even on Haiku: 11 questions
  for a human, 7 conflicts between two alternative models in one agreement, 16 role changes, 50 variables; its merge list was
  misused for non-merges. (6) A truncated structured reply is a failed call. (7) The spreadsheet's sheets become descriptors.
  (8) The blocks are a fifth to a third of the document's tokens; pass 2 fits one request.
- Consequences: a deterministic segmenter (pass 0) owns block identity and agreement is measured per id, field by field;
  payloads need constrained fields, not prose; role gains a relevance axis against the declared scope; batches of blocks bound
  the output per call; confidence stays secondary. Report: the lab folder's `runs/REPORT-2026-10-16.md` (outside the repo).
