The feature (PR #238/#239) is scheduled for field production, so Eric is reviewing
line-by-line before a release. His first two findings, both implemented this session:

1. **Eliminated the optional `missing=<node>` property on `graph.resume`.** Eric's
   reasoning: a typical suspend/resume graph has more than one suspension point, so a
   single no-record fallback node is ambiguous — the engine cannot know which stage's
   absence it is handling. Absent and expired records are indistinguishable by design;
   handling that condition is the developer's and product owner's responsibility at the
   logic level (a `graph.math` IF-THEN-ELSE or a `graph.task` on the resume node's
   forward path). Documented in `docs/guides` rather than solved at the framework
   level. Removed: the `MISSING` constant + `RESERVED_PARAMETERS` entry
   (GraphLambdaFunction), the jump branch in GraphResume, the target-exists compile
   check (CompileGraph.validateResumeNode now only requires `task`), the err6 negative
   fixture, and every doc/help/catalog mention.

2. **Engine-managed `model.run = resume | fresh` flag.** `graph.resume` sets it on
   both outcomes — `resume` when a record was restored (set AFTER the model merge so a
   record written by an older build can never resurrect a stale value), `fresh` when
   none existed — so the graph's own logic can react to the condition: advise the UI,
   gate a shared sub-path, or jump to a recovery node. `graph.suspend` excludes `run`
   from persistence (NON_PERSISTED_MODEL_KEYS), same treatment as the reserved model
   keys. tutorial-14 illustrates the technique: `model.run -> output.body.run` staged
   in every stage reply (order/approval/delivery/ship) and in the rejection body, so
   run 1 answers `"run": "fresh"`, runs 2–4 answer `"run": "resume"`, and a rejected
   later-stage request tells the caller why (`"run": "fresh"` on a decision-shaped
   body = the record expired or never existed).
