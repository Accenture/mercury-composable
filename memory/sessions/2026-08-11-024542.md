## Summary

**KIP-848 arc: field rebalance-CPU report → investigation → `group.protocol=auto` feature
(commit `03898b50` on `feature/kafka-group-protocol-auto`, awaiting Eric's push/PR gate).**

The field reported high CPU during unscheduled consumer rebalances (cloud infrastructure
interruptions), and Eric spotted the kafka-clients 4.3.1 build advisory recommending
KIP-848 (`group.protocol=consumer`). Investigation (read-only, tree kept clean) established:

- **KIP-848 targets exactly this symptom.** Classic protocol = client-driven with a group-wide
  synchronization barrier (one interrupted pod makes every member stop/rejoin/re-sync; a flapping
  member repeats the storm). KIP-848 (GA since Apache Kafka 4.0) = broker-driven, fully
  incremental — only the interrupted member's partitions move.
- **Empirical: our adapter runs it with zero code change.** The full KafkaFlowAdapterTest e2e
  suite (17/17) passed with `group.protocol=consumer` temporarily added to the template against
  the embedded 4.3.1 broker — including the `topic-pattern` binding (java-regex subscription is
  implemented for the new consumer, KAFKA-15538). The adapter overlay (group.id, derived
  max.poll.interval.ms, auto-commit, max.poll.records) is legal under both protocols; F4/F5
  resilience work carries over unchanged.
- **Fail-fast hazard proven:** a template that also sets `session.timeout.ms` (etc.) with
  `group.protocol=consumer` fails consumer construction —
  `ConfigException: session.timeout.ms cannot be set when group.protocol=CONSUMER`.
- **Detection mechanism (Eric's question "can we auto-detect?"):** KIP-848 enablement is the
  cluster-wide finalized feature flag `group.version` (≥1), readable via
  `Admin.describeFeatures()` — which (verified in the 4.3.1 client source) sends a plain
  `ApiVersionsRequest`, the pre-authentication handshake every client performs.
  **Never ACL-gated** (verified in the 4.3.1 broker source: `handleApiVersionsRequest` has no
  authorize call, answers "regardless of current authentication state") — so no grant is needed
  beyond the template's connection credentials, honoring the KafkaHealthCheck convention of
  avoiding Cluster-Describe-gated admin APIs. Live probe of the standalone 4.3.1 broker returned
  `group.version min=1 max=1`. Confluent Platform 8.x = Apache 4.x core, reports the flag;
  Confluent Cloud (Kora) supports KIP-848 but feature-field reporting unverified from here —
  auto conservatively resolves classic wherever the flag is not reported.

**Eric ratified the auto-detection design; implemented same session:**

- `GroupProtocolResolver` (new, package-private): resolves a template `group.protocol=auto` to
  `consumer`/`classic`; probe once per bootstrap.servers per JVM (ConcurrentHashMap cache);
  admin props filtered to `AdminClientConfig.configNames()` so consumer-only keys don't leak;
  10s bounded probe (`probeTimeoutMs` visible for testing); INFO/WARN decision logs in all four
  paths. **Conflict guard:** template setting `session.timeout.ms` / `heartbeat.interval.ms` /
  `partition.assignment.strategy` → classic + WARN naming keys (respect operator tuning, never
  silently strip), no probe. Explicit `consumer`/`classic` → verbatim, no probe.
- Wired at the single choke point `KafkaClientConfig.consumerProperties(ConfigBase, String,
  String)` — covers adapter bindings, KafkaHealthCheck, and twin-kafka's secondary (per-cluster
  templates → independent resolution per cluster, by construction).
- `EmbeddedKafka` extended additively: variant constructor (ports/logDir/featureLevels) using
  `Formatter.setFeatureLevel` — enables a live broker formatted with `group.version=0` (the
  normal upgraded-but-not-enabled cluster state).
- `GroupProtocolResolverTest` (8 tests): auto→consumer on the live KIP-848 broker; **auto→classic

  resolution; end-to-end consume under the resolved consumer protocol.
