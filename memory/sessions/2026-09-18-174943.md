**Agent:** Claude Code

## Summary

Field edge case in MiniGraph: a parent graph invoking a **suspending subgraph** through
`graph.extension` with `for_each` writes **one** store record for all iterations. Investigated,
designed, and ruled with Eric in one pass. Spec at
`draft-design-specs/subgraph-suspend-resume-for-each.md` (branch `docs/subgraph-for-each-suspend-spec`,
`b2cc6d1b`); not implemented.

## The defect

Three deliberate behaviours meet. `GraphSuspend` keys the record on business-cid + graphId;
`RedisStateConnection.storeKey` composes `graph:{graph_id}:{cid}`; and `GraphExtension.inheritBusinessCid`
*deliberately* gives every child the parent's `model.cid` — "keyed by graph + cid, never by a per-call
random id" — because that is what makes a subgraph resumable at all. `for_each` then forks N
invocations of the same graphId under the same cid, concurrently (`concurrency` default 3), so the
surviving suspension is a race. Neither suspend/resume spec mentions `for_each`: unconsidered, not a
regression.

## Why a fix is possible at all

**`graph.resume` is a node in the graph's own traversal, not an external call.** On the resume run
the parent re-forks iteration *i*, so the index is regenerated by the same code path that created it
and nothing outside the engine ever needs to know it. A discriminator an external resumer had to
supply would not have worked here.

## The ruling that changed my mind

I proposed index **and** size in the key (`0-20`), so a size change would produce a miss rather than
a wrong-state restore — self-detecting, failing safe.

Eric killed it with a use case: a warranty list `["phone","laptop"]` that later becomes
`["phone","laptop","headset"]`. With the size in the key, appending restarts the **in-flight
approvals for phone and laptop**. Growing the list is the ordinary thing a user does, so my guard
destroyed the legitimate operation — and it never caught the real hazard anyway, since it could only
detect a size change (the supported operation) and never a reorder (the corrupting one).

**Index alone.** Appending is safe by construction; reorder/insert/remove is a declared constraint.
Worth keeping as a method note: *a guard that fails safe is still wrong if the thing it makes fail is
the common legitimate case.* I was reasoning from "what can the engine detect" instead of "what does
the user actually do."

## The principle behind four rulings

Case 2 deferred, author-nominated discriminator rejected, size guard rejected, CompileGraph detection
declined — all one idea, which Eric stated directly: **every edge case has edge cases; the answer is
clean knowledge design, and avoiding over-engineering is a product-owner responsibility.** Recorded
as [[clean-knowledge-design-over-engine-coverage]] because it is not MiniGraph-specific and would
have shortened all four.

Its corollary for docs: constraints are **declared**, not enforced. A partial gate teaches that
*unflagged means safe* — learned once, applied everywhere.

## A doc defect found on the way

`workflow-suspension.md` tells the field a delegated subgraph "is fully resumable on its own." True
of a single delegation, **false under `for_each`**. That sentence is what the field is designing
against today; corrected inside this sprint (Q5). Found by reading the guide to see where constraints
should land, which is a reason to check the doc surface during design rather than after.

## OTLP log forwarding — CLOSED, not deferred

Eric took the parked design to the field architects and they landed where the spec recommended:
**application log forwarding is an infrastructure task; the engine does not grow that capability.**
Recorded as [[log-forwarding-is-infrastructure]]. It was never tracked as an open thread, so closing
it meant writing the decision down rather than ticking a box.

Worth noting what made the recommendation land: not the engineering comparison but the field's own
**Splunk practice** — stdout shipped by a standard forwarder, application does nothing. That reframed
the question from "how should Mercury export logs" to "why would Mercury export logs when the
platform already does," and the answer to the second is: it shouldn't.

The in-app alternative was the tempting one precisely because it was *easy* —
`OtlpHttpLogRecordExporter` ships in the artifact the span exporter already uses, so it needed zero
new dependencies. Cheap to build, and the cost lands where it is worst: an HTTP exporter reachable
from every `log.info` in the process. **Low implementation cost is not low cost.**

This is [[clean-knowledge-design-over-engine-coverage]] asked one level up — of a capability rather
than a graph composition. Two instances in two days suggests the principle generalises further than
the MiniGraph context it was written in.
