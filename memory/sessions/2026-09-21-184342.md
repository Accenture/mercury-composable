## What happened

**`group.protocol=auto` becomes the bundled default on both engines (Eric's ruling, 2026-09-21).**
Branch `feat/kafka-group-protocol-auto-default` (`ee37b907`, pushed; PR pending — Eric opens): the
consumer template's line `group.protocol=${KAFKA_GROUP_PROTOCOL:auto}` is uncommented, the comment
block states the default and the two overrides (`KAFKA_GROUP_PROTOCOL`, the application's own
template), and the Minimalist Kafka guide's rebalance-protocol section says `auto` is the default and
how the Rust engine's `auto` differs in mechanism only. No engine code changed.

**How it surfaced.** The Rust port's K4 live interop drive (mercury #300) ran BOTH engines on the
classic protocol against the `kafka-standalone` broker (Kafka 4.3.1) even though the broker finalizes
`group.version=1`: this template shipped the line commented out, so the Java demo joined classic (the
Java client's own "set group.protocol=consumer to try it out" hint in its log), and the Rust template
set no key. Eric asked why the Rust port did not switch automatically; the evidence-based answer was
that neither engine did by default, and his two rulings followed: the Rust `auto` becomes optimistic
(`consumer` first, `classic` on the broker's refusal — the fatal `ConsumerGroupHeartbeat` error
librdkafka raises, no probe needed; mercury branch `feat/kafka-group-protocol-auto`), and both
templates ship `auto`.

**Verification:** `mvn test -f system/minimalist-kafka/pom.xml` with the new default — 21 classes, 215
tests, 0 failures; the adapter tests resolve `auto` to `consumer` against the embedded KIP-848 broker
(`GroupProtocolResolverTest` still pins the classic resolution against its `group.version=0` broker).

**Release note to carry:** a behaviour change to READ — an application that never set
`group.protocol` now joins a KIP-848 cluster with the consumer rebalance protocol. Left for the
