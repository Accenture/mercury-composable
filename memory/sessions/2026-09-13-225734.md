## What happened

**The racy closing-post assertions fixed in the Java E1 suite** (branch
`test/closing-post-assertions`, commit `c73e1c50`) — the follow-up to the
finding the Rust port's R1 surfaced (Accenture/mercury#266, recorded in that
repo's port spec §3 item 8).

A terminal post races its own consumption by construction: the segment is
appended store-first, so a drain already in flight (woken by an earlier post)
may pop it, deliver it, and close the rendezvous — deleting the route — before
the producer's own `getRoute` runs. `post` then answers `false` although the
segment WAS delivered. The contract still holds (`false` = stop producing, and
a producer has nothing to send after a terminal segment), so the assertion, not
the engine, was wrong.

Classified all eight terminal-post assertions rather than relaxing them
wholesale — only some can race:

- **Relaxed (5)**, now via a documented `postTerminal` helper: the sequential
  chat close (eight prior data posts), the concurrent-producer close (75 prior
  posts), the any-producer close (two prior posts), the duplicate-wake-up close
  (drains were triggered, so racy in shape even with the 200 ms margin), and the
  stream close in the shared-channel scenario (the preceding data post woke a
  drain).
- **Kept (3)**, each with the reason inline: the healed-drain close — no wake-up
  was ever published for that cid, so no drain can be in flight — and the two
  one-shot closes, where the route is deleted only by `awaitResponse`'s cleanup,
  which runs after the post returns. The one-shot assertions also earn their
  keep: they prove the wake-up path was taken rather than the final-drain
  fallback (which would otherwise make the test pass slowly but silently).

Suite 77/77; the E1 class re-run three times, stable.

Durable lesson (recorded here rather than in continuity — the helper's javadoc
carries it at the call sites): **a cross-engine port is a test review too.** The
Rust twin ran the same scenarios under a different scheduler and exposed a
latent flake that had never fired in Java. Ordering assertions that depend on
"no concurrent consumer has run yet" deserve an explicit reason at the call
site, not a default assertion.
