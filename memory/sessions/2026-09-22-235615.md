## Note 3 — the Rust restart-aware Redis retry (Eric's ruling; Rust only)

Eric: "implement an intelligent retry only when the broken pipe is caused by a Redis restart or reconnection. This
requires some simple life cycle monitoring." Found: the Rust store already had the idempotent-only retry-once
(`116a48b2`, spec §5 item 6) — the polyglot report's "awaits ruling" line was stale — but the foundation (the cache's
path) had none and nothing distinguished a restart from an outage. Design turns: (1) keying the replay on the io kind
(BrokenPipe ⇒ not delivered) was WRONG — `redis-rs` synthesizes BrokenPipe (`closed_connection_error`) both for a
command it never sent and for in-flight ones whose stream ended; (2) the `Disconnection` push that would tell needs
RESP3 (`check_resp3!`) — not available to us; (3) what remained: a heartbeat monitor (its failed PING makes the
manager reconnect eagerly, so the next command — non-idempotent included — succeeds first try) + one retry per lost
connection for idempotent commands, gated on "believed healthy at issue time", never a replay of a non-idempotent
command (D7). Details, API and tests in the Rust log/Increment 135; the Java engine needs no twin (Lettuce requeues
unwritten commands). One test expectation corrected on the way: under a refused outage a command waits on the
manager's reconnect attempts up to the command deadline (408), not a fast 503 — "fail fast" means one
deadline-bounded attempt, never two.
