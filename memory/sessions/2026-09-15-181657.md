## What happened

### 1. platform-core: `packMapOrList` / `unpackMapOrList` — commit `387f0cda`

Eric's observation: `MsgPack` serves two roles at once. As the **event payload codec**, `pack(Object)`
wraps a PoJo/primitive with its type under the reserved keys `_T` (type) / `_D` (data) via
`PayloadMapper`, and `unpack(byte[])` strips them. As a **general purpose serializer** that encoding is
an unintended side effect — a user Map that happens to carry a `_T` key comes back *changed* (this is
the exact sharp edge I flagged when reviewing his MsgPack refactor in PR #395).

Added two methods with a Map-or-List-only contract:
```java
public byte[] packMapOrList(Object obj) throws IOException;   // never adds _T/_D
public Object unpackMapOrList(byte[] bytes) throws IOException; // never interprets _T/_D
```
A PoJo or primitive is rejected with `IllegalArgumentException` (the app encodes it first — e.g.
`SimpleMapper…readValue(pojo, Map.class)`), per Eric's spec.

**Design choice: the new methods are the PRIMITIVES.** `pack` now delegates its Map/List branch to
`packMapOrList`, and `unpack` calls `unpackMapOrList` before doing its `_T`/`_D` unwrap (the old private
`unpackData` was promoted/renamed). So the payload encoding lives in exactly one place and the two roles
are layered rather than tangled — behaviour of `pack`/`unpack` is unchanged.

Five new tests in `MsgPackTest`, incl. `packMapOrListDoesNotApplyTheTypeEncoding` — a map with literal
`_T`/`_D` keys round-trips **verbatim** through the new pair while `unpack()` still unwraps the same
bytes to the `_D` value (the contrast IS the proof). platform-core **493 tests, 0 failures**.

### 4. Build-command finding (my verification error, now documented) — commit `013df0b9`

My first full-reactor check used `mvn test` at the repo root and came back RED: `ai-contract-provider`
15 tests / 1 failure / 9 errors. I flagged it to Eric before he opened the PR rather than reporting
green. Diagnosis: `SkillSnapshot.dependencyVersion` reads
`/META-INF/maven/org.platformlambda/platform-core/pom.properties` — a file Maven writes **only into the
packaged jar**. A reactor-wide `mvn test` never packages upstream modules (they resolve as bare
`target/classes`), so the lookup throws *"the Mercury dependency assembly is incomplete"*, its static
init fails, and every discovery test cascades into `NoClassDefFoundError`. The module passes 19/19
standalone (deps resolve from `~/.m2` as jars), which is what isolated the cause. **Not my change** —
a root `mvn test` fails this module for ANY change. `memory/instructions.md` already documents
`mvn clean install` as the full build (and CI runs `mvn install`); I simply used the wrong command.
Re-ran correctly: **`mvn clean install` → BUILD SUCCESS, zero failures across every module**
(ai-contract-provider 19/19). Eric asked for the reason to be written down, so the Build/Test/Deploy
guide now carries a note explaining the rule, the failure signature, and the single-module exception
(`mvn test -f <module>/pom.xml` is fine). No continuity fact added — instructions.md already names the
command and the guide now holds the *why*.
