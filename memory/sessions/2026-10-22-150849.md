## Findings

- **Parity of substitution before parsing (Eric's question): yes on Rust.**
  - Event Script: Java `TaskExecutor.java:1104` and `:571`, Rust `executor.rs:1473` and `:948`. Both replace `{model.key}`, then
    `[model.i]`, then resolve the source.
  - The graph engine's six mapping-source sites pair up one to one, each substituting first:
    - `handleDataMappingEntry`;
    - `fillFetcherApiParameters`;
    - `getForEachMapping`;
    - `performOutputMapping` (Rust `perform_fetcher_output_mapping`);
    - the dictionary's output mapping;
    - graph.task input.
  - Neither engine substitutes into a dictionary default.
  - **Difference: nested braces.** For `{model.{model.k}}`, Java's `extractSegments` resolves the inner reference and leaves the
    outer braces as text. Rust pairs the first `{` with the first `}` and inserts `null`. Nothing uses the form; it is left for
    WP4.
- **The plugin-argument form is promised** by the Event Script syntax guide in both repositories. No repository flow, graph, test
  or doc uses it. No `{$...}` selector exists anywhere.
- **`serde_json_path` 0.7.2 against the compliance suite:**
  - every one of the 715 answers is the standard's;
  - the 249 invalid queries are refused;
  - every valid query is accepted;
  - it renders a normalized path without RFC 9535 §2.7's escapes (a quote, a backslash, a control character), in 16
    name-selector cases. The engine reads values only. Pinned by name.
- **The parsers' error positions differ:** `serde_json_path` reports a byte offset, converted to a character index. The vectors
  therefore pin acceptance only, never a position.
- **`tutorial-113` differs between the engines** (`graph.math` on Rust, `graph.js` on Java). So the Rust `-err5` is built from
  Rust's own copy, and both engines' gate tests check each message, so a fixture rejected for another reason cannot pass.
