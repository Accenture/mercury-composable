## What We Did

- **Eric brought a second agent's review of #552/#553/#554** - five findings, all accurate: (1) text bands give silently wrong
  answers when the value is shaped differently (`9:30` lands above `16:00` as text; a full timestamp against time-only bands);
  (2) a band written as a list (`gold=[ "10000..25000" ]`, a `key[]=` line) reaches the parser as the text of the list - a
  misleading "is empty" for numbers, a silently matched `["a..h"]` for text; (3) zero-padded codes make a table mixed with no way
  to say "text"; (4) `minRange`/`maxRange` returning a double loses precision beside the `DECIMAL` rule; (5) `a..b..c` accepted,
  `1...2` reported as mixed, bounds re-parsed per lookup. **Eric's proposal:** optional quoting `'text1' .. 'text2'` (single or
  double quotes), quoted text case-sensitive, quoting making a numeric-looking value text (`'0020'..'0030'` is not `20..30`),
  timestamps in ISO-8601 or local year-month-day-hour-minute-second order, and BigDecimal precision for the bounds. **My
  assessment and his four rulings (agreed):** quoted text case-sensitive, unquoted text case-insensitive as today, never mixed in one
  table; decimal bounds from the bound plugins as EXACT TEXT (the DECIMAL convention; a BigDecimal object would turn into text at
  the first event hop and has no Rust twin), whole numbers as longs; timestamps a declared rule, no shape gate (a gate for one text
  shape would teach that the others are safe - an initial-letter band `a..h` must still place `Garcia`); both quote styles, an
  empty quoted bound refused. Plus his doc ask: say that the bound plugins return a string for a decimal number by the
  high-precision design, and that a type-conversion plugin (`f:double`) converts it for an output value.
