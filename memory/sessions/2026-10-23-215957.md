## The configuration-key audit (Eric: "check the parameters so that they can coexist")

A scan of every `.properties` key, every key the code reads and the configuration reference found two keys that are
both a value and a parent:
- `cloud.connector` / `cloud.connector.health`: a false positive, since the second is a function's route name;
- `scheduler.environment` / `scheduler.environment.store`: real, in the mini-scheduler since 4.12.22 (ADR-0030).

A probe with the real `ConfigReader` showed what happens. When the child is set, in either order,
`getProperty("scheduler.environment")` answers `{store=my.store}`, the text of the child map. `ActiveEnvironment`'s
name check then fails at startup with the misleading "scheduler.environment must be one word…". So no installation can
be setting `scheduler.environment.store` today. The Rust port has no such setting.

Eric: "the mini-scheduler and scheduler-example need the same parameter renaming fix". It is released code, so it goes
in its own PR from main, like the `ManifestReader` fix.

## Finding 3: the negative control isolates one route (Eric chose option B)

- **The first attempt changed nothing in the lab.** `InvocationObservers.send` left the unlinked route's reply
  untouched, and the reply carried the caller's tag, which `setCorrelation` and `prepareErrorResponse` already copy. Yet
  `lab.receipt` and the worker stayed in `lab.audit`'s trace.
- **The cause is OneAgent's own context propagation.** `task.executor` and `event.script.manager` are not reached through
  the event bus: `runTaskExecutor` submits them to an executor from the sending thread. OneAgent instruments that
  submission (the `internal …EventEmitter$$Lambda` nodes in the screenshots) and carries the thread's active PurePath
  into the task. An SDK incoming tracer started there nests under that path, ignores its tag, and logs no warning.
- **The fix.** `begin` wraps an unlinked route's scope in an `UnlinkedScope`. Then
  `InvocationObservers.reply(scope, error, delivery)` closes it, so the route's trace ends on its thread, and delivers
  the reply with the tags kept.
  - A deferred `Mono` reply does the same in `resume`.
  - The scope closes at most once, so the worker's later close is a no-op.
  - `WorkerHandler`'s two synchronous reply sends go through `reply`; `getErrorProcessStatus` now receives the scope.
- **Tests:** `InvocationObserverTest` gains two cases, a callback reply and a deferred one. Each checks the caller's tag
  at the receiver and that the route's node ended first. A linked route's reply is still tagged where it leaves.
- **Lab result, 3 of 3 orders:** one Dynatrace trace holds the edge's hops, `lab.receipt` and the worker's; `lab.audit`
  alone is the other. So Mercury's one trace id now maps to one Dynatrace trace, plus the deliberate fragment.
- **Lesson:** with OneAgent, a hop handed to an executor from a thread with an active PurePath is linked by OneAgent
  itself, so the adapter's tag decides only where no path is active. Breaking a link therefore means ending the path
  before the handoff, not only withholding the tag.

Eric: "Scheduler PR 584 merged".

## The OpenTelemetry adapter under OneAgent: spans recorded, never linked across the bus

- **Setup.** OneAgent's `opentelemetry` sensor was already enabled, capturing and an entry point in the lab's JVMs (the
  agent log in Colima's VM; it detected OpenTelemetry Java 1.62.0), so nothing had to be switched on in the tenant.
- **What Dynatrace showed (Eric's screenshots, the 15:33 and 15:39 orders):** every hop is a separate request named
  after its route, under "Requests executed in background threads". `/api/lab/orders` holds only its server span.
- **A diagnostic build, in the lab only and reverted.** It logged each hop's incoming tag, parent, current context
  and span. The spans are OneAgent's (`com.dynatrace.agent.introspection.span.opentelemetry.DynatraceSpan`) and carry
  an empty tracestate. It showed two breaks:
  - at the REST entry, OneAgent's PurePath is not the OpenTelemetry current context, so the first hop has no parent;
  - every hop through the event bus (`lab.validate`, `lab.lookup`, `lab.price`) gets a new trace id although its
    remote parent is valid. The executor hops (`event.script.manager`, `task.executor`) keep it, through OneAgent's own
    thread propagation.
- **Span kinds.** `SERVER` behaves the same; `INTERNAL` produces no span without an active PurePath.
- **Conclusion:** under OneAgent, an API span links only through OneAgent's own context on the thread, never through a
  W3C remote parent the caller sets. RFC-0009 option (b) had anticipated flat spans. For Dynatrace the OneAgent SDK
  adapter is the one that works. The OpenTelemetry adapter has a passing in-memory linkage test but no agent that has
  been shown to honour its linkage. Its future is Eric's call.
