## Context

Two field requests were opened against the Python pack on 2026-11-23. #77 asks that a single `llm.chat` call be
recorded in the transcript audit store, which records an agent loop's turns only (ADR-0035). #78 asks for an
`attachments` field on a single call: images and PDF pages named by reference and read by the helper. Each describes a
reference implementation that is not published. The session started in the Rust repository and read the Python pack,
this repository and the Node pack; it changed this repository only.

## The review, before any change

Read against the Python pack's `main` at `89aff42` (the requests were written 44 commits earlier), ADR-0035, the
schema page, both engines and the provider's published limits.

- **#77 holds as a gap and not as a design.** The single-call path never reaches the audit; the two tables can hold
  the rows with no DDL change; both engines send `x-graph-id` and `x-node` on every `graph.task` request. The
  request's design carries the rows in the event: that departs from ADR-0035's decision 1 (the function reads nothing
  but the record) and decision 3 (two events), leaves a failed write unrepaired, and holds content in the one
  worker's mailbox, an unbounded in-memory queue, during an outage. Further: the schema page's meanings do change (a
  conversation is "one row per reference `llm.chat` returned"; `request` and `response` "carry the provider's format
  unchanged"); `response` must stay an array of blocks; the status rule names four stop reasons and no default; the
  model recorded after a server-side fallback is not stated; `llm.stream` is left out without a word; the
  agent-question reader lists conversations with no filter on their kind.
- **#78 is the right shape with ten open points.** The root becomes readable through the model by every caller that
  can reach the helper; the confinement would be a second one beside the agent tools' workspace, with other rules; the
  limits are not the provider's (an image at most 10 MB base64-encoded on the Claude API and 5 MB on Amazon Bedrock, a
  request limit quoted out of date, 600 PDF pages or 100 on a model under a 1M context window, no encrypted PDF);
  what the byte limit counts when pages are cut is undefined; the read runs outside the call's deadline; cutting a PDF
  is CPU work beside a stream whose batches are pinned as never held back; two statuses differ from the helper's
  convention; the Node twin has no equal PDF library, so a shared vector cannot pin a cut document's bytes; a null
  path drops the attachment without an error; the hash belongs at the read.
- The reviews were posted on the two issues on the maintainer's word. Neither names a person.

## What was done (branch `rfc/0015-0016-llm-chat-audit-and-attachments`)

- **RFC-0015** in `docs/arch-decisions/RFC.md`, Open: a single call is a conversation of one turn, carried by the
  working record. With `llm.transcript.audit.single` on, `llm.chat` saves a closed, one-turn, version 2 record under
  the audit's grace and sends `{conversation, check: true}`; `transcript.audit` is unchanged; `tools IS NULL` tells a
  single call from a loop; the tables stay and the page's meanings are extended. The request's own design is option B.
- **RFC-0016**, Open: `attachments` on a single `llm.chat` call, by reference inside one root under the agent tools'
  workspace rules, the provider's limits checked by the helper, the audit keeping a reference with the source file's
  SHA-256. Several roots, the bytes in the request, the provider's Files API, extracted text and a shared object store
  are its options.
- **Threads** `llm-chat-single-call-audit` and `llm-chat-attachments`, each with its `→ proposal:` pointer.
- No design spec, no code, no CHANGELOG item: a proposal has none.
