### The trigger was a false positive

The review fired on `[continuity-bloat] 36 decay-eligible facts > continuity_max_facts 35`. One of
those 36 is not a fact: `memory-lint`'s `parse_footers` runs `FOOTER_RE` over the whole of
`continuity.md`, including the **schema example in its own header** —
`` `<!-- id: kebab-id | created: YYYY-MM-DD | … -->` `` — and counts `kebab-id` as live. It has
`tier: active` and is not pinned, so it lands squarely in `decay_eligible`.

Verified rather than reasoned: linting an untouched copy of `memory/` reproduced
`58 live facts / 36 decay-eligible / 1 warning`; neutralizing that single line on the copy gave
`57 live / 0 warnings`. The real count is **35 — exactly at the cap, not over it.**

So the review had nothing to lean down, and would have been wrong to invent something. This is the
failure mode `REVIEW.md` step 6 calls the costliest error, arriving from the opposite direction: not
a miscounted `sessions_since_last_used`, but a **phantom fact inflating the trigger that summons the
review in the first place**.

Fixed locally by making the id a placeholder like every other field on that line —
`id: <kebab-id>` — which the `[a-z0-9-]+` capture cannot match. The line still renders as a real
HTML comment showing the exact syntax, and is now internally consistent (`YYYY-MM-DD`, `N`,
`<kebab-id>`). Recorded as [[conv-schema-example-not-a-fact]] so it is not tidied back.

Reported upstream as the durable fix: the parser should skip the header example (every agent-memory
repo ships this header, so every repo over-counts by one). Third report to that team in two days,
and the first that is a correctness bug rather than a decay-signal or cosmetic issue.
