## Fixed a real 500 in the scheduler example's job-list endpoint (field CI flake)

- The field CI pipeline failed on `ScheduleAdminTest.jobListIsReturnedWithoutAJobName`
  (`examples/scheduler-example`), which fast-failed the whole reactor build (every module
  after it SKIPPED). Error: `expected <200> but was <500>`; the server log showed
  `v1.schedule.admin` throwing `Cannot invoke "java.util.Map.containsKey(Object)" because
  "map" is null` while a scheduled job fired ~2 ms earlier.
- Root cause — a genuine reader defect, not a racy assertion:
  - `StateResolver` persists job state with `util.str2file`, which is
    `new FileOutputStream(f, false)` — it TRUNCATES the file to 0 bytes on open, then
    writes. A concurrent reader in that window sees an EMPTY file.
  - `ScheduleAdmin.getJobList()` reads every state file; for each,
    `getJobTime(util.file2str(f))` → `getJob(json)` → Gson `readValue("", Map.class)`
    returns **null** for the empty string → `getJobTime` then called
    `map.containsKey(START)` on that null → NPE → 500.
  - The single-job GET path (`getJob` → `setBody(result)`) already TOLERATES the null
    (200 with null body), and the sibling test `manualJobRunCreatesTheStateRecord` already
    documents the non-atomic-write hazard. The **list path was the one place with an
    unguarded NPE** — that asymmetry was the bug.
  - Why it flakes: `cron.yaml` fires demo-task every 15 s and demo-flow every 25 s (plus a
    0–9 s deferred-start jitter), so a job write overlapping the list read is intermittent.
- Fix (reader-side, matching the single-job path's existing tolerance): guard the null map
  in `ScheduleAdmin.getJobTime` — an unreadable/empty record contributes an entry with no
  timing instead of 500'ing the whole list. Kept the intentionally-simple non-atomic sample
  writer unchanged (an atomic-rewrite alternative was considered and rejected: the sibling
  test and the single-job path both already rely on the tolerant-read contract, and the
  sample's simplicity is a teaching property; real resolvers use a DB/cache).
- Regression test `jobListToleratesAStateFileCaughtMidWrite`: creates a 0-byte state file
  (exactly what the truncate window exposes — note `str2file(f, "")` is a no-op on a
  missing file, so `File.createNewFile()` is used) and asserts the list returns 200 with
  that entry present and no timing. VERIFIED it fails `<200> but was <500>` against the
  unfixed code (stash-out proof) and passes with the fix; full class 6/6 green.
- Latent siblings noted, deliberately unchanged (no evidence they race — same-name job
  writes are sequential at the cron interval): `StateResolver.endTask`/`checkExpiry` would
  also NPE on a null parse of an empty file. The cross-cutting reader that races with ALL
  jobs' writes is the admin endpoint, which is fixed.
- Java-only: the Rust port has no scheduler module (no parity fix).
