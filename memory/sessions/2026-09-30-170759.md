## Corrections (same sitting)

**One: strings at rest.** Eric pointed out that `graph.suspend` saves the state machine to Redis or alike and `graph.resume`
restores it, so a `BigDecimal` in memory comes back as a string, and proposed strings at rest with `graph.math` reading both
forms. Verified and adopted: the suspension envelope carries the `model` namespace, `graph.resume` merges it back with `putAll`
and no conversion, and a platform MsgPack round trip returned `BigDecimal` 10.50 as `String` "10.50", `BigDecimal` 0.00 as
`String` "0.00" (so even the zero rule would not survive a resume), and `Long` 5 as `Integer`. This reverses the item-6
amendment in commit `386f78c8` (BigDecimal in memory, chosen because IF and CONDITION quote text values).

**Two: the rule lives in the evaluator.** Eric then set the comparison rule (a string operand that is a number converts to a
number before `== != < <= > >=`, so `'200' == '200'`, `200 == 200` and `200 == '200'` are the same comparison) and reminded the
agent that every string and number is rendered into the statement text before parsing. That settles the placement: the
evaluator sees literals, not sources, so the rule sits in the comparison operators on parsed values and substitution does not
change; the agent's earlier idea of unquoting canonical decimal strings at substitution is dropped, and the decimal evaluator also converts canonical strings for arithmetic operands. Evidence, the current engine run on the expressions:
`200 == '200'` and `'9.5' > 10.25` are errors; `'9.5' > '10.25'` is true (text order); `'1.0' == '1'` is false;
`'12345678901234567890' == '12345678901234567891'` is false as text, while the same two as number literals compare equal in a
double. So applying the rule to double mode needs a precision guard (a string converts only when it survives the trip through
a double), and flips two results there, which is a READ item. Whether the rule also reaches IF, CONDITION and `COMPUTE:` awaits Eric's confirmation (still open in the RFC).

**Three: `DECIMAL:` replaces the switch.** Eric argued that with proper parsing and type conversion no opt-in mode is needed for
backward compatibility. The agent agreed about conversion (the read and comparison rules need no mode) and named what the switch
still carried: the result type (`COMPUTE:` stores a Double, exact arithmetic a canonical string, so a graph feeding numeric strings
into arithmetic would flip from a number to a string) and the guarantee (legacy graphs must keep accepting Doubles, so without a
declaration a stray JSON number silently drops a money statement to binary floating point). Offered: type-directed arithmetic, a
`DECIMAL:` statement tag, or keeping the switch; Eric chose the tag ("DECIMAL becomes the high-precision COMPUTE"). RFC-0001 was
rewritten around it in the working tree: no root `numeric` property, no `graph.math.numeric` default, no CompileGraph check, no
mixed-mode limit between graphs, rounding always explicit, `DECIMAL:` valid in `graph.math` only (`graph.js` rejects it by name,
since both share the statement recognizer), `COMPUTE:` untouched apart from the comparison rule.
