## 1. opentelemetry-forwarder polish — branch `feature/otel-certification`, commit `2036b5b4`

Reviewed the module ahead of the certification run and found two live instances of bug classes this
repo already has facts about, plus one observability gap.

**`otel.forwarding` — the opt-in switch (default FALSE), Eric's design.** The forwarder lives under
`org.platformlambda`, a base scan package, so the jar alone auto-registered the route and began
exporting. It is now `@OptionalService("otel.forwarding")`, which separates two decisions belonging to
different people: a developer adds the dependency, DevOps decides per environment whether traces leave
the process. With it off the route does not exist — not a registered no-op. `composable-example` now
doubles as the regression app: it carries the dependency with `otel.forwarding=false`, and
`OtelForwardingSwitchTest` pins that the dependency alone registers nothing (mutation-proven by
deleting the annotation). The legacy `otel.trace.forwarder.enabled` stays, documented as superseded.

**The OTLP credential was frozen at `@PreLoad` construction** — the exact shape of
`preload-before-mainapp-lazy-config`, and now its **third** instance after `kafka.health` and
`redis.health`. A vault-published token would have been baked in as absent and every export would 401
for the life of the process, visible only as a per-span warning. Fixed with `setHeaders(Supplier)`
plus a once-only "credential resolved" line so the transition is observable. Mutation-proven.

**A rejected export was undiagnosable.** The SDK's HTTP failure exception has a `toString()` of just
its class name, and the status code lives only in the SDK's separate JUL warning — uncorrelated, and
invisible in a JSON application log. The status, message, truncated body and a targeted hint are now on
the forwarder's own line.

That third fix paid for itself within minutes of the live run, which is the point worth keeping: the
first attempt said `404 | check the endpoint includes the signal path` (the endpoint stopped at
Dynatrace's `/api/v2/otlp` base, missing `/v1/traces`), and after Eric fixed that it said
`403 - User is missing required permission: openpipeline:traces:ingest`. Two distinct
misconfigurations, each named precisely. Neither would have been visible before.

**Header composition, Eric's refinement.** `OTLP_AUTH_HEADER` carries the header name *and* any auth
scheme — the standard-auth-header name plus a scheme word for Dynatrace, a vendor-specific header name
with no scheme for Splunk — so `OTLP_TOKEN` stays purely the secret and rotation touches one variable.
(The literal forms are in the example app's config comments, not here: a memory log should carry
nothing shaped like a credential, and the secret-scan guard deliberately cannot be waived for
`memory/`.) `parseHeaders` therefore accepts `:` as well as `=`,
splitting on whichever comes first — so a value may still contain the other character (a base64 `=`
pad, a URL `:`). Also renamed the service-name variable to `OTLP_SERVICE_NAME`: `OTEL_*` names are
commonly exported machine-wide on instrumented hosts, and inheriting one would silently rename the
app's traces or redirect them — the same reasoning that keeps this module's own tests off `${OTEL_*}`.

**Status:** code complete and green (forwarder 34/34, example 6/6, full reactor SUCCESS). The
certification run is **blocked on Dynatrace support granting the token scope**; the test report for

## 2. `kafka.health` classloader bug — branch `fix/kafka-health-classloader`, commits `96472f9a`, `51a21257`

A field deployment logged, every 5 seconds and 266 times over,
`Class org.apache.kafka.common.serialization.StringDeserializer could not be found`, while the same
JVM's real producers and consumers used the same jar without trouble.

The field's diagnosis was excellent and I verified every claim against the code. Kafka resolves a
class-name config through `Utils.getContextOrKafkaClassLoader()`, which prefers the thread context
classloader and falls back to Kafka's own loader **only when the TCCL is null** — so a non-null but
wrong TCCL fails, where a null one would have worked. `KafkaHealthCheck` is `@KernelThreadRunner` and
builds on a pooled kernel thread; `KafkaFlowAdapter` builds a consumer from the *identical* config, is
not a kernel-thread runner, and was fine. That A/B was the whole diagnosis.

**Where I had to correct them.** Their proposed fix — pass deserializer *instances* — is incomplete,
and the reproducing test proved it: with instances passed, the two deserializer lookups disappear and
the very next class-name config fails instead (`metric.reporters` → `JmxReporter`, same jar). Kafka
resolves several configs this way. In the field their fix would have **moved** the 5-second error, not
removed it. The fix is the classloader: construction runs with the class's own loader as the TCCL,
scoped and restored in a `finally` (a test pins the restoration, because the thread is pooled). They
rejected that as "mutating global thread state" — right instinct, but scoped to one construction on
the probe's own thread it is not global, and it is the only fix covering lookups we have not enumerated.

**Then two rulings from Eric.** Class-valued settings in `KafkaClientConfig` now go in as `Class`
objects rather than names, converging minimalist-kafka with kafka-connector, which always did it that
way — so no client built from those templates depends on the building thread at all. And the
health-check leniency got a boundary: the passing `Waiting for Kafka connection` status exists for one
situation, a value a later credential bootstrap will publish. A class that is not on the classpath will
never arrive by waiting, so that now fails with 503 and says *configuration is unusable* rather than
*cluster is not reachable* — naming the classpath, not the network.

`SecondaryKafkaHealthCheck extends KafkaHealthCheck`, so both probes are covered by the one change.
minimalist-kafka 210/210, full reactor SUCCESS.

## Durable lessons

- **A pooled kernel thread is not just a scheduling choice — it changes what code can *see*.**
  `@KernelThreadRunner` moves work onto a pool whose context classloader need not be the
  application's, so any library resolving class names by string can fail there while succeeding on a
  normal thread. Worth checking whenever that annotation meets a library that takes class names.
- **A lenient health status hides the defect it was designed to tolerate.** The passing-WAITING
  semantics protected against a real failure mode (a restart cannot produce a credential) and, by the
  same token, reported healthy for hours while a deployment was broken. Leniency needs a boundary.
- **"Verify what you benchmarked / ran" applies to jars too.** Two of this session's dead ends were
  stale artifacts: an app running an old forwarder jar, and a `build exit=0` that was really `head`'s
  exit status. Check the pipeline's exit code, and confirm the artifact contains the change.
- Docs updated alongside each fix; continuity facts deliberately deferred until both branches merge,
  so a single merge-hot file is not edited from two in-flight branches.
