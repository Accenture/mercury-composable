## Verification: the same `||` trap, twice

I ran `mvn -q -o test … | tail -40 || mvn test … | tail -40`, got exit 0, and nearly reported the
build green. The 0 was `tail`'s — `||` binds to the **pipeline**, whose status is its last command,
so the fallback never ran and Maven had in fact failed on offline resolution (BC 1.86 was not in the
local repo). Re-run properly: `mvn > log 2>&1; echo "EXIT: $?"` — 500 tests, 0 failures.

This is the second instance of exactly this binding error in this repo (the first was `||` binding
to `sed` rather than `grep` in the undeclared-reference harness). The pattern: **when a verification
command is itself a pipeline, its exit status stops describing the thing being verified.** Capture
the tool's own status before piping. Not promoted to a continuity fact — continuity is already over
its fact cap and a method lesson belongs in the log; if it recurs a third time it earns a slot.

Related: I also declined to trust `BUILD SUCCESS` alone for the BouncyCastle claim, because
`TestBase.generatePrivateKeyAndCert()` returns a **boolean** and its failure path only logs a
warning — a BC breakage would have silently skipped SSL setup and still passed 500 tests. Confirmed
the success message fired once and the warning zero times. The catch-block-returns-false shape is
the same silent-pass hazard as the pipeline exit code, one level up.

## ADR housekeeping — and a process change

Eric accepted the five ADRs still sitting at `Status: Proposed` (0013–0017), all of which had in
fact shipped: Boot-3 retirement, polyglot Event-over-HTTP peers, the AI discovery app, the generic
exception handler, and graph-scoped workflow state. Each now reads
`Accepted (2026-09-18) · Date: <original>`, keeping both dates so the journey stays legible, and
the `<!-- status: -->` footers moved with them. Tally: 24 accepted, 0 proposed.

**ADR-0013 was amended in place rather than superseded** — Eric's call, because it had never left
`Proposed`, so the decision as accepted is the amended one. No ADR-0025. Its rationale now carries
the reason the `for_each` index belongs to *that* decision: ADR-0013 mandated the cid inheritance
that makes the iterations collide, and its original text had explicitly waved the case away as "one
graph × one cid = one record, so a suspendable subgraph is invoked once per cid per run." The defect
was in the ADR's own assumption from 2026-08-10, not just in the code.

**New rule — proposals leave the ledger.** `docs/arch-decisions/proposed.md` now holds work under
consideration as `P-NNNN`; `ADR.md` gets an entry only on acceptance. Eric's reasoning:
*ADRs are an immutable journey of decisions, and a proposal is not a decision.* The failure mode it
prevents is visible in what we just cleaned up — a `Proposed` status accumulated for a month across
five decisions that had all shipped, so the ledger was simultaneously wrong about each of them.
Withdrawn proposals are the sharper case: under the old practice one would sit in the ledger forever
looking like a decision nobody implemented.

Recorded as [[conv-proposals-not-in-adr-ledger]], `tier: core`. It matters as memory rather than
only as a doc header because it **overrides** the agent-memory protocol's own wording ("propose a
newer ADR … and wait for human approval") — and `PROTOCOL.md` is tool-managed, so it cannot be
edited to agree.

**Raised upstream the same day** on Eric's direction, so the tool and the engine stay consistent
rather than this living as a local divergence. The report traces the behaviour to the wording:
followed literally, "propose a newer ADR … and wait for human approval" can only mean *write the
entry into `ADR.md` now, with a status meaning not-yet-decided*, because the guidance names exactly
one file. Nothing was done carelessly here — the five entries were written exactly as instructed,
and nothing ever tells you to come back and flip the status.

The argument that carries it is the case we did **not** hit. Five stale `Proposed` entries are
merely wrong and fixable. A *withdrawn* proposal has **no correct status at all** in a decision
ledger: `Superseded` implies a successor decision, `Deprecated` implies it was once in force, and
both are false — so it sits there permanently, indistinguishable from a decision nobody implemented.
A defect with no valid end state is a stronger case than one with a tedious cleanup.

Guidance-only, no tool code — nothing reads or validates ADR status and the ledger is optional —
so it carries the same low-cost shape as the thread-id note that shipped within the day. Two reports
now pending upstream: this one and the phantom-fact parser bug.
