## The honest gap, and what was done about it

Eric could not confirm the backend side, so the obvious move was to write the report with a
"pending confirmation" note and stop. That would have left the central claim resting on
*absence* of evidence: zero export failures.

**Zero failures is not evidence unless a failure was possible.** A forwarder that silently
skipped export, or never attached the credential, produces exactly the same zero. So the round
was extended into an **A-B-A experiment** — repeat with a deliberately invalid token, then
restore. Leg B produced six failures, one per span, each naming the span, the trace, HTTP 401
and the actionable config key. That converts the clean legs from "nothing went wrong" into
"Dynatrace returned 2xx for every span", because the same code path demonstrably reaches
Dynatrace and demonstrably honors the credential.

What remained genuinely unproven was narrower, and the report said so plainly rather than implying
full certification: *accepted for ingest* is not *visible after pipeline processing*. The dashboard
later closed exactly that gap and nothing more, which is the right shape for a stated limitation —
it was specific enough to be discharged by one observation.

**The durable lesson:** when a verification is blocked on someone else's access, ask what the
evidence you *can* collect would look like if the thing were broken. If broken and working look
identical, the evidence is worthless and a negative control is not optional garnish — it is the
experiment. This cost one extra app restart and turned an inconclusive report into a conclusive
one about everything except UI visibility — which is also why the round could be *reported* rather
than merely parked while waiting on a support ticket.

A useful by-product: leg B returned HTTP 201 like the others, which is direct evidence that a
telemetry backend outage degrades observability and nothing else. That is a property consumers
care about and it had never been demonstrated, only asserted.

## A doc gap Eric caught — the same failure mode twice

Eric asked whether the guides covered the new parameter keys. Three of four surfaces did
(`configuration-reference.md`, `observability.md`, the module README, including the legacy key
marked superseded with its precedence stated). **`docs/guides/build-test-deploy.md` did not** —
its snippet still told the reader to set the endpoint and service name and nothing else, so
following it exactly produced no traces at all, because `otel.forwarding` defaults to false. It
also still advertised the legacy `otel.trace.forwarder.enabled` as the way to disable export.

This is the **`app.env=dev` failure mode again**: a new switch was added, the obvious doc surfaces
were updated, and a *different* guide was left holding configuration that now silently does
nothing. Both times the gap was invisible to every test — the config is inert, not invalid.

The durable fix is not "remember build-test-deploy.md". It is: **when adding a gate that defaults
to off, grep for the keys it gates, not for the places you think document the feature.** That grep
is now part of the check — every doc that configures `otel.exporter.otlp.endpoint` was verified to
also name `otel.forwarding`, and it is a one-line sweep that would have caught both incidents.

### The doc fix broke the build, in a different module, for a non-obvious reason

`doc-canon` is **not** the only documentation gate. `system/ai-contract-provider` packages a curated
subset of `docs/` into the version-matched AI skill snapshot and enforces a **link closure** over it:
every relative link in a packaged doc must resolve to another packaged file. The pointer I added from
`build-test-deploy.md` (packaged) to the new test report (not yet packaged) therefore failed the
build — and it surfaced as `NoClassDefFoundError: Could not initialize class SkillSnapshot` across
eight tests in a module that has nothing to do with OTel, because the closure check runs in a static
initializer. The real cause was one line deep in the log:
`Broken relative link in references/guides/build-test-deploy.md -> ../test-reports/otel-dynatrace-certification.md`.

**Adding a doc to the AI contract takes THREE coordinated edits** — this is the part worth keeping:

1. `system/ai-contract-provider/pom.xml` — the resource `<include>` that copies it into the snapshot;
2. `src/main/resources/skill/files.list` — the checked inventory (alphabetical within its section);
3. `SkillSnapshotTest` — a **hard-coded** list of the non-`guides/**` extras, which `guides/**` files
   never need because the test walks that directory.

Miss (1) and links break; miss (2) or (3) and `inventoryEqualsTheDocumentationClosure` fails. Only
`guides/**` is automatic.

**My process error, plainly:** I pushed the doc commit after running only `doc-canon`, and CI caught
what a full reactor build would have caught locally. A doc change that adds a link *across*
directories touches the contract closure, so it is not a docs-only change and should not be verified
as one.

## Two switches became one, and a hook moved (Eric ruled both)

`otel.trace.forwarder.enabled` was **retired**. It had become redundant: `Telemetry` guards its send
with `platform.hasRoute(...)`, so an unregistered forwarder is already a silent no-op — the
`@OptionalService` gate therefore did the legacy key's job more cheaply (no exporter, no thread pool,
no shutdown hook), and the only way to *use* the legacy key was the contradictory pair
`otel.forwarding=true` + `otel.trace.forwarder.enabled=false`. Retirement is safe in the one
direction that matters: anyone who had it `false` lands on the new gate's default of off.

Retiring the key meant retiring the code that only existed to serve it — `OtelForwarderContext`'s
`enabled` field went too, since nothing in production could construct a disabled context any more and
a reader would hunt for the switch that set it. `isEnabled()` survives with a truthful meaning
(`exporter != null`) instead of a stored flag. **Principle worth reusing: keeping state alive only so
a test can exercise the branch it creates is circular** — the one test asserting the old
registered-but-inert state was testing a state that no longer exists, so it was rewritten to assert
the remaining off state, with a comment naming what was retired so nobody re-adds it.

Separately, the forwarder's hand-rolled `Runtime.getRuntime().addShutdownHook(new Thread(...))` was
migrated to `Platform.getInstance().onShutdown(...)` — the pattern
[[platform-onshutdown-lifecycle]] retired in v4.12.9, which this extension had been missed by.
Registered in the constructor because that is where the exporter is opened, matching the API's own
guidance and all three existing call sites; safe there because `@PreLoad` constructors are invoked
*by* `AppStarter.preload()`, so the platform singleton already exists.
