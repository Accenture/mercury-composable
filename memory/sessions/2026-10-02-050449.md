**Cause.** `useGraphRunWorkflow` computed `canInteract` with `isPrimary`, so a subscribed session got both buttons disabled with the tooltip "Run the graph from
the host session" (Eric's screenshots). The engine never needed that: a subscriber's command goes to the primary, which runs it and replays it in every
subscriber's session (Java `GraphCommandService.runAsPrimary`, Rust `commands.rs`, the same shape). The README even stated the rule ("only the host controls
this lifecycle"), while the guide calls subscribers equal co-authors. The only role checks outside the Session menu were these two.

**Fix.** The gate is gone. `isPrimary` stays an input, but only a change resets the run (subscribing or unsubscribing reroutes commands); the old reset was
level-triggered, which would have reset a subscriber's run on every graph refetch once the gate was gone. `Playground.tsx` passes `sessionCollaboration.isPrimary`
(the `sessionId !== null` guard only kept the gate shut until the session was known). Two tests replace the one that pinned the gate: a subscriber instantiates,
takes its upload invitation, survives a graph refetch and runs; a subscribe and an unsubscribe each reset a Ready run. The README and the technical documentation
drop the host-only rule; CHANGELOG Unreleased item 8.

## Decisions Made

- Remove the gate rather than add a subscriber path: the engine already treats every member's command alike, and Eric's design makes them equal partners.
- Keep a reset on subscribe and unsubscribe, edge-triggered: commands reroute at that moment, so an earlier Ready no longer means what it did.
