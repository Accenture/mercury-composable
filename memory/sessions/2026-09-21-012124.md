**Design (in the `redis-connection` foundation, so both consumers inherit it).** `ResettableRedisBackend` is
the new base of `StandaloneRedisBackend` and `ClusterRedisBackend`: `commands()` / `async()` return stable
`java.lang.reflect.Proxy` facades over `RedisClusterCommands` / `RedisClusterAsyncCommands` that resolve the
live connection per call — every consumer (cache store, return-route store, coordinator, responder) captures
the handle once at construction, and the facade follows a reset. The connection lives in a `Slot` (connection +
consecutive-timeout count) behind an `AtomicReference`; the rule: a timeout on a connection that is NOT open
resets at once, a timeout on an OPEN connection resets on the SECOND consecutive one (a reply clears the
count), one reset per connection instance (CAS on the slot); the next command opens a new connection under a
`ReentrantLock` ([[conv-reentrantlock-not-synchronized]]); a failed connect is a fast 503 via
[[redis-failure-classification]] and is held for 250 ms so a burst of callers is not a connect storm; the
first connect stays eager (construction fails fast as before). The async path cannot see an awaited timeout,
so `RedisBackend.onCommandTimeout()` (default no-op) lets the cache's `MPUT` report it — and MPUT's own
timeout is now the same 408 as a blocking one (it threw an `IllegalStateException` → 500). `RedisFailure`
gained `isTimeout` and its `classify` is a pattern `switch` (Eric's review). Design consulted
[[redis-connection-foundation]] (the one-command-type seam is what makes a single facade type sufficient).

**Tests.** `ResettableRedisBackendTest` against the embedded Redis with a 400 ms command timeout: a blocking
`BLPOP` on an empty list is a real client-side timeout on an open connection — the first is tolerated, the
second resets, the captured facade then works and is the same object; a reply between two timeouts restarts
the count; the server stopped — the first timeout resets at once (connection not open), the next call is a
fast 503 (`RedisFailure.classify`), and after the restart the first call past the 250 ms hold window is live
(the first version of that test hit the hold window because the embedded server restarts in <250 ms — a test
fix, not a code fix); `onCommandTimeout()` follows the same rule. Cache: `aPipelineTimeoutIsA408AndIsReportedToTheBackend`
with a never-completing `RedisFuture` proxy (Lettuce's `awaitAll` calls `get(timeout, unit)` and reads a
`TimeoutException` as "not completed"). Module suites green: redis-connection, distributed-cache,
sync-over-async (the facade is transparent to the return route).
