    Test Report — The agent loop's trace lineage through both language packs¶

    The first drive whose question was the trace itself: does a span lineage stay continuous from the Java engine's REST edge through the agent loop into the language packs - the LLM helper's llm.chat and the MCP binding's route - and back? Conducted 2026-11-14 (UTC+8) with the Playground example's diagram-assistant graph on Claude Haiku 4.5, the Java Playground 4.12.30, the Python pack (mercury-python) and the Node.js pack (mercury-nodejs) from main of the day, and the public Mermaid Chart MCP server behind the binding. Eric set the acceptance criterion before the drive: for OpenTelemetry to be certified, the span lineage ought to be continuous end to end. The drive ran negative control first - the packs as they were - then again after the change this report records.

    Result in brief¶

    • Baseline: every record chained, and the pack legs were missing. Each run logged 11 engine records, each with a parent some record owned, and no record from either pack. llm.chat (two turns) and diagram.render.mcp (the MCP tool) appeared only as time inside the engine's llm.run and diagram.render. A tree with no orphans is not the same as a tree with every hop.
    • Cause: two rules met, with nothing between them. The calling engine records nothing for an RPC over Event-over-HTTP, because its HTTP client leg async.http.request is in skip.rpc.tracing by default; a Java or Rust callee fills that gap with its own three records - the http.request edge for POST /api/event, event.api.service and the function's round-trip record from its local inbox. The packs suppressed the worker-side record of every RPC-served execution, as the engines do, but left none of the callee's records in its place, and their replies carried no span for an engine inbox to chain onto. The forwarder drops a record without a valid span id, so no backend could have shown the hop either.
    • Fix: the packs now leave what a Java callee leaves (mercury-python #53, mercury-nodejs #120, Eric's choice among three shapes): a traced call at /api/event leaves http.request (the edge's round trip, parented onto the caller's span - the envelope's span, else the traceparent header's; the backend's SERVER span), event.api.service (the ingress, parented onto the edge) and, for an RPC, the function's round-trip record with the responder's span, parented onto the service; a reply carries the responder's span (WorkerHandler parity) and the packs' PostOffice records a local RPC round trip as InboxBase does.
    • After: 20 records per run, every parent owned by a record, in both packs. The helper's edge sits under the engine's llm.run and the binding's under diagram.render; each function sits under its event.api.service; the timings nest. The tree is now the same shape whether the callee is a Java engine or a pack.
    • A declared function's name never enters a trace. The MCP binding's mcp.tool, the one function behind every bound route since mercury-python #52 and mercury-nodejs #119, appears nowhere: every trace field comes from the service entry the event was addressed to, and the route name diagram.render.mcp is the hop's identity.

    Reading the tables: the engine's llm.run calls the helper twice (two model turns), and each call appears as the helper's http.request edge under llm.run's span, event.api.service under the edge, and llm.chat under the service with its round_trip; the engine's diagram.render calls the binding once, and the binding's http.request edge sits under diagram.render's span with event.api.service and diagram.render.mcp beneath it. The engine's own records are the baseline's eleven, unchanged. The packs' from fields name the engine function that called (llm.run, diagram.render) because the engine's PostOffice stamps the calling route on the wire envelope.

    Findings¶

    1. An RPC over Event-over-HTTP is the callee's to record. The caller's async.http.request leg is in skip.rpc.tracing by default so that an HTTP call folds into the calling function's span; the Java callee's event.api.service and REST edge are traced for exactly this reason (its javadoc: so the /api/event edge is visible in the span tree). A runtime that suppresses the responder's record for an RPC, as the engines do, has to leave the callee's records instead - the packs' "engine parity" had copied the suppression without the records that justify it. The rule, stated for all four runtimes: every traced execution leaves exactly one record; who emits it depends on the side, never on the runtime.
    2. The responder's span has to ride the reply. A Java inbox names the round-trip record's span from the reply (InboxBase.spanIdFromResponder), and WorkerHandler puts it there. The packs' replies carried none, so even a Java caller recording the hop would have produced a record the forwarder drops (no valid span id). Both packs now set it.
    3. The alias shape is invisible, by construction. mcp.tool never appears in any record; the trace knows the bound route only. This settles the question the drive began with.
    4. Timings nest as they should. In every call the edge's exec_time covers the function's round_trip, which covers its exec_time; the engine's round trip to the pack exceeds the pack's edge by the wire's few milliseconds (for example diagram.render 3,588.9 ms and 3,590.4 ms round trip against the Python binding's edge 3,567.4 ms and diagram.render.mcp 3,566.2 ms with a 3,567.0 ms round trip).
    5. The guards. mercury-python tests/test_event_stream.py and mercury-nodejs test/event-stream.test.ts pin the three callee records and their parents for a streamed call and for a plain RPC, the span on the reply, the refusal's edge record (404) and the silence of an untraced call; the local round-trip record replaces the former "RPC legs emit no dataset" pin in both packs.

    What this drive did not do¶

    • No backend confirmation. The records were read from the logs, which are the forwarder's input, mapped one to one to spans (the 2026-09-22 OpenTelemetry forwarder certification). Eric's review in a Dynatrace tree remains the certification step, as it was then; that report's Scenario 2 carries an addendum pointing here.
    • The Rust engine was not the caller. It speaks the same wire contract and stamps the same spans; a Rust Playground drive would show the same tree.
    • One model, one graph. The trace shape does not depend on the model or the graph; the drive used the cheapest model that completes the diagram task.
