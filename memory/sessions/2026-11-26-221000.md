**User:** the maintainer - a field report passed on with its graph and node ids to be ignored, and his reading of it:
"for parallel calls using for_each, the HTTP exception of one invocation (e.g. HTTP-500) can be overridden by another
successful invocation, thus the exception is not caught in the exception handler ... Please investigate"

## What was done

- **Read the path.** `GraphExtension`, `GraphTask` and `GraphApiFetcher` each run a `for_each` in batches of
  `concurrency` through `po.request(batch, timeout, false)` and loop over the responses; `GraphExecutor` (and
  `GraphTraveler`, the dry run) decides a node failed when `{node}.status` is an integer and `{node}.error` is set,
  then answers with that status or jumps to the handler and stages it as `error.code`.
- **Root cause.** Each response writes `{node}.status`; only a failure writes `{node}.error`, and nothing clears it. So
  the status is the last response's and the error is any failure's. `FutureMultiInbox` returns
  `new ArrayList<>(replies.values())` from a `ConcurrentHashMap` keyed by the reply's random id, so "last" is neither
  the last requested nor the last to arrive. The same pattern runs across a fetcher's dictionary items without
  `for_each`, where the calls are sequential and the last item's status wins.
- **Reproduced** on a branch with a harness that asserts nothing and tallies what the caller receives:
  `ForEachFailureProbe`, the function `v1.iteration.outcome` (fails for a chosen element, with a delay per kind of
  element), a subgraph and twelve parent graphs `unit-test-foreach-*`. No engine source was changed.

## Findings (30 runs a scenario unless stated)

| Scenario | Without `exception=` | With `exception=` |
| --- | --- | --- |
| One batch of three, the middle element fails | HTTP 200 with the error map as body in 15 to 19 of 30 (extension 19, task 15, fetcher 18) | handler entered with `error.code` 200 in 17 to 20 of 30 |
| Four elements, the first fails, the second batch succeeds | HTTP 200 in 30 of 30, all three skills | `error.code` 200 in 30 of 30 |
| Four elements, the last fails alone in its batch | the right status in 30 of 30 | the right code in 30 of 30 |
| The failing element is the slowest, or the fastest | the same split as the first row (17 to 22 of 30) | the same split (17 to 23 of 30) |
| A fetcher with two dictionary items, the first fails (5 runs) | HTTP 200 in 5 of 5, `target` names the item that succeeded | `error.code` 200 in 5 of 5, the mapping continued |
| The same, the failing item last (5 runs, control) | HTTP 400 with the right `target` in 5 of 5 | - |

Beside the masking:

1. **Order.** The aggregated `result` keeps the batches in order and shuffles each batch: five elements came back in
   list order in 6 of 30 runs, nine elements in 0 of 60 (the extension and the task). The fetcher's help page says
   the order is guaranteed.
2. **A missing answer.** With a node `ttl` of 2 seconds and one element that takes 4, the run answered HTTP 200 with
   the other elements' results in 24 of 24 runs (16 without a handler, 8 with one that was never entered): the batch
   request returns the partial list when the wait ends, and no status or error is written for the missing element.
3. **Output mappings on failure.** They run, though the pages say they are skipped; the handler's caller saw the
   partial `results`, and without a handler the mapping wrote into the error body, which the node's error shares.
4. **A stale response in the fetcher.** A failed element maps the previous element's `response` again: the result
   list held a second copy of another element's value in 22 of 30 runs of the first row.
5. **The fetcher's after-features** receive `batch.get(i)` with `responses.get(i)`, which the arbitrary order breaks
   (read, not run: the fixtures carry no feature).

The report's reading, corrected in two details: which element ends first plays no part; and with a handler the handler
is entered, with a code of 200, while without one the run stops at the node and answers 200.

The Rust engine, by reading only (`crates/knowledge-graph/src/extension.rs`, `skills.rs`, `fetcher.rs`): the same
last-status loop, with a batch that keeps request order and turns a timeout into a response, so there a failure is
masked when a success follows it in list order.

## Decisions

None taken. Proposed to the maintainer, recorded in the thread: one failing element fails the node with the first
failing element's status, error, stack and target in list order; no answer within the deadline is a 408; results in list
order; output mappings skipped on failure; no further batch once a batch has a failure; best effort left to the design
of the element's own subgraph.
