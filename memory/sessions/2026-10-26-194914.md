## Findings

- **ClassGraph 6.0.0 is not safe yet.** It needs JDK 25 and has a new API, and Mercury's baseline is Java 21
  (`stack-language-java21`). ClassGraph 5 has the same new API and covers JDK 17 to 24 only, leaving out Java 25, our
  recommended runtime. 4.8.199 is the last 4.x release, with an unchanged API, and 4.x is end of life apart from serious fixes.
- **ClassGraph A-B on packaged jars.** The unit tests run from `target/classes` and never exercise the Spring Boot executable
  jar that 4.8.191 changed (`nested:` URLs).
  - A git worktree carried this branch's diff with ClassGraph 4.8.184, so the two builds differed in that one dependency.
  - `composable-example` and `rest-spring-4-example` ran from copies of their jars, on each version.
  - `/info` and `/info/routes` were identical (29 and 18 private routes). `/info/lib` was identical apart from the ClassGraph
    entry (70 and 76 libraries).
  - The startup logs were identical line for line after removing timestamps, thread ids, PIDs and memory figures.
- **Kafka 4.4's storage `Formatter` writes the bootstrap snapshot only into the metadata log directory it is given.**
  `GroupProtocolResolverTest` failed 3 of 8 (`auto` resolved to `classic`).
  - 4.3.1 wrote a `BootstrapDirectory` file into every directory. 4.4.0 writes a snapshot only when the directory is the
    metadata directory, and Kafka's `StorageTool` now passes `config.metadataLogDir`.
  - Our four brokers named none, so each started with no feature finalized. The fix is `setMetadataLogDirectory`, which
    exists in 4.3.1 too.
  - Negative control: `EmbeddedKafkaTest`'s new assertion fails on the unfixed helper ("the metadata log should be formatted")
    and passes with the fix.
  - The resolver's `group.version=0` case had passed only because no broker finalized anything: an "off" case cannot tell
    whether it is testing anything while the "on" case is broken.
- **The `zstd-jni` pin stays.** kafka-clients 4.4.0 ships the fixed 1.5.7-17, which meets the comment's removal condition. But
  Boot 4.1.2 manages kafka-clients 4.2.2, so an application under the Boot parent without `kafka.version` relies on the pin.
  The old 1.5.7-16 pin would now downgrade it.
- `api-playground` and `pg-example` sit outside the reactor and resolve `platform-core` 4.12.26 from `~/.m2`, so they still
  show Vert.x 5.2.1 and ClassGraph 4.8.184 until the next release installs a new `platform-core`.
