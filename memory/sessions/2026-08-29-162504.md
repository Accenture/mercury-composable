## Summary

**SSE consumption + Event-over-HTTP streaming — design round ratified, Phase 1
implemented (Java).** The follow-up arc to [[thread-http-response-streaming]]: with the
engine→HTTP-edge leg done, Eric opened the engine→wrapper gap (Event-over-HTTP is
drop-n-forget or request-response — no progressive rendering) and framed two candidate
approaches (on-demand WebSocket; AsyncHttpClient consuming SSE) plus a call for
alternatives.

**Option analysis (assessment ratified by Eric):** CHOSEN — SSE response on the same
call + progressive consumption in AsyncHttpClient (one ordered stream per call, in-band
terminals via the existing protocol, no new inbound surface, gateway-survivable, and
the same client capability is needed anyway for direct LLM-provider token streams —
grounded in code: the Event-over-HTTP relay already flows through AsyncHttpClient).
REJECTED: WebSocket (wrapper scope fence, 4 codebases, gateway-hostile, drifts toward
the opt-in mesh), per-segment POSTs to the reply lane (serialized RTT per token; opens
reply lanes to remote posts), gRPC/HTTP-2 push, long-polling, the x-stream-id relay.

**Spec:** draft-design-specs/async-http-client-sse-streaming.md. **D1–D9 approved as
recommended**, with **D5 REVISED to Eric's hybrid framing** for envelope mode: control
plane vs data plane — all control signals ride as key-value headers in envelope frames
(reserved SSE event name `envelope`, base64 MsgPack: the first frame = head control;
the terminals ARE control signals; plus any segment that cannot round-trip as raw text
— Map/bytes bodies, `\r`, reserved-name collision), while token segments ride raw SSE
frames. Quantified: pure envelope-per-frame costs ~200+ wire bytes for a 5-byte token
(the envelope structure repeats, not just base64) — the hybrid cuts the hot path ~90%.
Phasing (D9): Phase 1 = raw-mode consumption (START, per Eric); Phase 2 = envelope mode
engine⇄engine; Phase 3 = wrapper twins.
