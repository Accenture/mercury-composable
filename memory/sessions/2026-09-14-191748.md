## Design ruling: distributed cache is a separate module; sync-over-async stays small

The field asked whether sync-over-async is "generic enough" to also cover distributed-cache
use cases (PUT/GET/MGET/DELETE/PUT_IF_NOT_PRESENT), consumed either as an Event Script /
graph task with output mapping or directly via a layer-1 PostOffice call.

- Assessment given: do NOT extend sync-over-async's rendezvous protocol into a cache (different
  concern; would bloat a lean transport). The reusable generic asset is its **Redis client
  layer** (RedisBackend + RedisConfig + factory + cluster/auth/health). The cache belongs in the
  **already-planned generic Redis distributed-cache module** (the `redis.health` route name is
  reserved for it) as a composable action function — which natively serves the field's two
  patterns because both are just "a composable function." The `soa.redis.*` vs `redis.*`
  namespacing (with fallback) done earlier this session makes the two modules coexist cleanly.
- **Eric ruled: "agree with your design direction. Keep sync-over-async small."** Recorded as
  [[cache-separate-from-soa]].
- No code this increment beyond the memory decision — the cache module is future, gated work.
  The clustered-Redis / config branch (`feature/sync-over-async-clustered-redis`) remains ready
  for Eric's PR.
