## Clustered Redis for sync-over-async (field request)

- The field asked sync-over-async to support **clustered Redis** (AWS ElastiCache
  cluster-mode-enabled) as well as single-node. Lettuce supports both. Eric ruled the
  selection should be configurable OR auto-detected; auto-detect confirmed feasible and
  chosen as the default (his ruling), with standalone fallback.
- Investigation findings that shaped a small, clean change:
  - **One common command type.** In Lettuce 7.5.2 the standalone `RedisCommands` *extends*
    `RedisClusterCommands`, and cluster's `RedisAdvancedClusterCommands` extends it too, so
    `RedisClusterCommands<String,String>` is the super-type both topologies satisfy. Every
    op the module uses (single-key setex/get/eval/lpop/llen/del + `publish` from
    `BaseRedisCommands`) resolves on it — the store retypes to it with no behavioural change.
  - **One cross-slot hazard.** Every operation is single-key EXCEPT `cleanup`'s
    `DEL request:{cid} queue:{cid}` — two keys in different hash slots → CROSSSLOT on a
    cluster. Fixed by splitting into two single-key DELs. This keeps the **Redis key format
    and the whole wire contract identical**, so no forced Rust change (see parity note).
  - **EVAL append+TTL** is single-key (cluster-safe as-is); classic **Pub/Sub** `PUBLISH`
    crosses the cluster bus to the pod's subscriber (wake-ups unaffected).
  - **Auto-detect** = connect to the seed, `INFO cluster` → `cluster_enabled:1`; fall back
    to standalone if the probe is inconclusive (e.g. `INFO` restricted).
- Design (the seam): new `RedisBackend` interface (`commands()`/`openPubSub()`/`cluster()`/
  `close()`) with `StandaloneRedisBackend` + `ClusterRedisBackend`, built by
  `RedisBackendFactory.create(config)` (mode switch + auto-detect). `RedisClusterMode`
  enum {AUTO,STANDALONE,CLUSTER}. Threaded through the coordinator, `StreamResponder`,
  `SyncRuntime`, the autostart, and `soa.redis.health` — all cluster-aware through the one
  seam. Ownership: `SyncRuntime` owns the backend (closes it after the coordinator); a
  `RedisClient` convenience ctor wraps a shared client non-owning, so existing tests compile
  unchanged (near-zero churn — only additive tests).
- **Credentials** (Eric's ruling): configurable in `application.properties`, no IAM SDK /
  provider in core. New optional `redis.username` (ACL/RBAC user) beside `redis.password`;
  values resolve `${ENV_VAR}` from env vars a **lower-`sequence` `@MainApplication`
  credential bootstrap** publishes first (the documented vault pattern,
  [[preload-before-mainapp-lazy-config]]). Auth is identical standalone vs cluster (AWS
  applies one credential set to the whole replication group). Lettuce's
  `withAuthentication(RedisCredentialsProvider)` remains the clean future seam if rotating
  IAM tokens are ever needed — noted, not built.
- Config keys added: `redis.username`, `redis.cluster.mode` (auto|standalone|cluster,
  default auto), `redis.cluster.nodes` (host:port,… seeds; blank = single host:port /
  configuration endpoint). `RedisConfig` gained a 9-arg canonical record + a
  backward-compatible 6-arg standalone ctor (used by tests) + `seedUris()` + `withTimeout()`.
- Verified: sync-over-async module 83/83 green (incl. new `RedisBackendFactoryTest` proving
  auto-detect resolves the embedded single-node server to standalone and round-trips through
  the seam, and extended `RedisConfigTest` for mode parsing + seed URIs); the
  sync-over-async-demo consumer builds+tests clean against the changed API. Cluster-mode
  topology/CROSSSLOT behaviour is validated against a real cluster in the field (no embedded
  cluster fixture exists).
- **Cross-engine parity note:** the wire contract (key names, segment JSON, channel naming)
  is UNCHANGED, so existing standalone polyglot interop is unaffected. For a polyglot
  deployment ON a cluster, the Rust port needs the same two items — a cluster-client option
  and the cleanup DEL split — a Rust-side follow-up (like K3), NOT a wire break. Flagged to
  Eric; parked until he calls it.
