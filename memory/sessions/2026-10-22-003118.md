## Context

A field report: the OpenTelemetry forwarder's traces reach Dynatrace, but OneAgent's code-level view does not show the hops
between composable functions, and its log fields do not tie to the trace it shows. Eric asked whether OneAgent handles virtual
threads, Vert.x and Netty. Research answered yes, each on its own, but not Mercury's handoff: the event loop enqueues to a per-route
mailbox drained by a virtual thread started at boot, so no agent context survives a hop. A field design brief followed and was
reviewed. It got four changes: the send hook goes in `EventEmitter`, not `PostOffice`; the entry point is the real unknown;
an OpenTelemetry-API adapter is tested alongside the SDK; a scoped default. It also gained a cheaper first diagnostic for its
log question: an `app-log-context.yaml` mapping `dt.*` keys to Mercury's ids. Eric then asked for the recommendation
implemented on a feature branch the field takes as a snapshot ("v4.12.25-snapshot"). **His rule: no PR until the feature has
been tested in the field as a snapshot release.**

## What was done (branch `feature/dynatrace-oneagent-compatibility`, off `main` `250970d9`)

- **The seam, `org.platformlambda.core.spi`** (platform-core, no vendor dependency). It has `InvocationObserver` (`begin` on
  the thread that runs a function; `send` on the sending thread), `InvocationScope` (error, then end, on its own thread),
  `InvocationContinuation` (a Mono's result resumes it exactly once on the completion thread, or `abandon` closes it on cancel),
  `InvocationCarrier` (the envelope's string tags), `InvocationInfo`, and the registry `InvocationObservers`. The registry guards
  every observer call, closes several observers' scopes LIFO, and applies a route filter: `invocation.observer.include` /
  `exclude` (the default excludes the telemetry routes and `temporary.inbox`) and `invocation.observer.unlinked`, the
  experiment's negative control (a route that never sees the incoming tag). It observes only traced events.
- **The hooks.**
  - `WorkerHandler.executeFunction`: open after the log context is registered, pass the scope down by reference (into
    `handleMonoResponse`, which detaches it), close before `stopTracing`.
  - `EventEmitter.runTaskExecutor`: Event Script's two routers bypass the worker, so without this hook every flow step
    breaks the chain.
  - The five `EventEmitter` send entry points, each on the engine's own copy: `send`, both `asyncRequest`, both `eRequest`.
    The Event-over-HTTP overloads hook themselves; the local paths hook after the HTTP branch, so each path is tagged once.
  - The worker passes `ps.getException()`, not `!ps.isSuccess()`: `ProcessStatus.setExecutionTime` resets the success flag after
    an exception (since 2024, `756a1333`), so a failed RPC function's trace metrics read `success: true`. That is flagged as a
    separate task, not fixed here.
- **`extensions/dynatrace-oneagent`** (`dynatrace.oneagent=true`, `@OptionalService` + `@BeforeApplication`). It uses
  `oneagent-sdk` 1.9.0, Apache-2.0 with no dependencies; the API was checked with javap. Each hop is an incoming-message-process
  tracer that consumes the `dt_tag` before it starts, and each send an outgoing-message tracer whose tag goes into the envelope.
  An empty tag (no PurePath on the sending thread) removes any stale tag.
  - All hops share one messaging system (`Mercury`); the destination is the application by default, and
    `dynatrace.oneagent.destination=route` names every hop after its route. The route and Mercury's trace id are custom request
    attributes.
  - A Mono uses an in-process link: created on the hop's thread while its tracer is open, traced on the completion thread.
  - Tier B logging, opt-in (`dynatrace.oneagent.log.context=true`), writes OneAgent's ids into the log context as
    `dt.trace_id` / `dt.span_id`.
  - Startup logs the SDK state, registers nothing when the SDK is PERMANENTLY_INACTIVE, routes the SDK's logging callback to the
    application log, and warns when `otel.tracing` or `otel.forwarding` is on too.
- **`extensions/opentelemetry-tracer`** (`otel.tracing=true`, API-only dependency). Each hop is a `CONSUMER` span named after its
  route; its parent is the W3C context from `otel_traceparent` / `otel_tracestate`, else the thread's current context, else a new
  trace. The span is made current on the worker thread. A span is not bound to a thread, so a Mono's span ends at delivery: its
  real duration. Startup logs the API implementation class.
- **Found by the OneAgent linkage test, fixed:** Event Script's kick-off event to `task.executor` (`EventScriptManager.processRequest`)
  carried no trace id, because the executor reads it from the flow instance. That hop was therefore unobserved, and the first task's
  tag came from a thread with no context; with a real OneAgent, the first task would have started a new PurePath. The event now
  carries the flow's trace. `TaskExecutor` never reads it, so Event Script's behaviour is unchanged.
- **Docs:** `docs/guides/observability.md#live-tracing` (the design, a settings table, deferred results, the agent requirements,
  the four-point field experiment), seven keys in `configuration-reference.md`, both extension READMEs, CHANGELOG Unreleased
  Added 7 (EXPERIMENTAL), and RFC-0009 (Open) in the register.
- **Sonar hygiene for the field's gate:** `Utility.sleep`, not `Thread.sleep`, in the new tests (S2925; the repo has had none since
  #192), and a `FALSE` constant in `OneAgentSetup` (S1192).

  - `OneAgentSetupTest` (4).
  - `OneAgentLinkageTest` (5) runs through real dispatch: REST edge → `demo.hello` → RPC → `demo.echo` (the echo's tag was
    produced on `demo.hello`'s thread), a two-task flow (each task's tag produced by an observed Event Script router), a Mono
    via an in-process link, and the negative control (a tag produced, none consumed).

    `toString()` changes.

  150 ms on the completion thread, exactly once. `OtelLinkageTest` (4) covers one tree over HTTP, the flow's task spans under
  `task.executor`, a Mono span of at least 200 ms, and the negative control.
