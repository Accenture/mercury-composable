## What happened

Field finding on twin-kafka: a Kafka **bridge** (listen to one cluster, publish to another) failed to
deploy because the unused client's credentials do not exist — a managed Confluent cluster issues an API
key per client, and the app built both regardless. Eric asked for an opt-out on producer and consumer
for both minimalist-kafka and twin-kafka, default true.

### Review finding: the asymmetry was sharper than reported

The **consumer was already conditional** (the flow adapter starts only when `yaml.*.flow.adapter` is
set); the **producer was unconditional** — `new KafkaProducer<>` ran on every startup in both
`KafkaFlowAutoStart:64` and `SecondaryKafkaAutoStart:74`. That single line is the deployment failure.

Two secondary hazards on the same missing-credential axis, both in the `@PreLoad` health-check
constructor (which runs at startup whether or not `kafka.health` is a listed dependency):
`KafkaClientConfig.loadFirst` throws when a CI/CD-rendered `file:` consumer template was never rendered
for a produce-only leg, and a template with `group.protocol=auto` opens an AdminClient right there
(`GroupProtocolResolver:106`). Neither crashes startup — `AppStarter:395` catches and logs "Unable to
preload" — so the route silently goes unregistered and `/health` then fails on a missing route.

### Shipped (Eric ratified D1–D4)

Four keys, default true, veto-not-trigger semantics (repo idiom: `LogContextConfig:114`):
`kafka.producer.enabled` / `kafka.consumer.enabled` and the `secondary.*` twins. Each cluster reads
only its own keys and names its own key in any error, via the existing `registryUrlKey()` seam
precedent (new sibling `producerEnabledKey()`).

- **D1** — `simple.kafka.notification` stays REGISTERED with the producer off and fails naming the
  setting; an unregistered route would yield "route not found" and send a developer into flow YAML.
- **D2** — a binding declaring `dlq-topic` with the producer off **fails startup**
  (`KafkaFlowAdapter.rejectDeadLetterWithoutProducer`). Without it, `writeToDeadLetter` hits its
  null-publisher branch (`KafkaFlowConsumer:579`) and drops poison messages with a DATA LOSS log while
  committing the offset. A consume-only leg is exactly the shape that wants a DLQ.
- **D3** — `kafka.health` builds its Metadata probe from the PRODUCER template when the consumer is
  off, filtered through `ConsumerConfig.configNames()` so producer-only keys are dropped rather than
  logged as unknown config. Same self-maintaining filter idiom as `GroupProtocolResolver.probe:117`.
  Keeps `mandatory.health.dependencies=kafka.health, secondary.kafka.health` working on a one-way bridge.
- **D4** — both disabled is allowed (a "Kafka off in this profile" switch) with a startup WARN.

Docs: a `{#opt-out}` section in minimalist-kafka.md, a `{#one-way}` worked bridge config in

## Durable lessons

1. **An environment condition must be checked AFTER every caller-input check.** My first cut resolved
   the publisher up-front "to fail before any payload work" and broke
   `SimpleKafkaNotificationTest.schemaPathKeepsItsByteArrayDocumentContract`: a caller passing a
   non-`byte[]` schema document got `IllegalStateException` (producer disabled) instead of the
   `IllegalArgumentException` its contract promises. The existing suite caught it. The producer check
   now sits at the publish site, and `KafkaOptOutTest.callerMistakesAreReportedAheadOfTheProducerCheck`
   pins the precedence from the other side.
2. **A module test run resolves its dependencies from `~/.m2`, not from the working tree.** The twin
   suite failed to compile against the stale installed `minimalist-kafka` jar until
   `mvn install -DskipTests -pl system/minimalist-kafka` ran first. Cross-module changes need the
   install step (or `-am`) before the downstream suite means anything — a green downstream run against
   a stale jar would have been worse than the compile error.
3. Redundant `@SuppressWarnings` is its own smell — dropped a `java:S107` on a 7-parameter method
   (the rule flags >7). Add a suppression on evidence from a scan, not in anticipation of one.
