## The honest gap, and what was done about it

Eric could not confirm the backend side, so the obvious move was to write the report with a
"pending confirmation" note and stop. That would have left the central claim resting on
*absence* of evidence: zero export failures.

**Zero failures is not evidence unless a failure was possible.** A forwarder that silently
skipped export, or never attached the credential, produces exactly the same zero. So the round
was extended into an **A-B-A experiment** — repeat with a deliberately invalid token, then
restore. Leg B produced six failures, one per span, each naming the span, the trace, HTTP 401
and the actionable config key. That converts the clean legs from "nothing went wrong" into
"Dynatrace returned 2xx for every span", because the same code path demonstrably reaches
Dynatrace and demonstrably honors the credential.

What remains genuinely unproven is narrower and is stated as such in the report: *accepted for
ingest* is not *visible after pipeline processing*. That is the only thing the dashboard would
add, and the report says so rather than implying full certification.

**The durable lesson:** when a verification is blocked on someone else's access, ask what the
evidence you *can* collect would look like if the thing were broken. If broken and working look
identical, the evidence is worthless and a negative control is not optional garnish — it is the
experiment. This cost one extra app restart and turned an inconclusive report into a conclusive
one about everything except UI visibility.

A useful by-product: leg B returned HTTP 201 like the others, which is direct evidence that a
telemetry backend outage degrades observability and nothing else. That is a property consumers
care about and it had never been demonstrated, only asserted.

## A doc gap Eric caught — the same failure mode twice

Eric asked whether the guides covered the new parameter keys. Three of four surfaces did
(`configuration-reference.md`, `observability.md`, the module README, including the legacy key
marked superseded with its precedence stated). **`docs/guides/build-test-deploy.md` did not** —
its snippet still told the reader to set the endpoint and service name and nothing else, so
following it exactly produced no traces at all, because `otel.forwarding` defaults to false. It
also still advertised the legacy `otel.trace.forwarder.enabled` as the way to disable export.

This is the **`app.env=dev` failure mode again**: a new switch was added, the obvious doc surfaces
were updated, and a *different* guide was left holding configuration that now silently does
nothing. Both times the gap was invisible to every test — the config is inert, not invalid.

The durable fix is not "remember build-test-deploy.md". It is: **when adding a gate that defaults
to off, grep for the keys it gates, not for the places you think document the feature.** That grep
is now part of the check — every doc that configures `otel.exporter.otlp.endpoint` was verified to
also name `otel.forwarding`, and it is a one-line sweep that would have caught both incidents.

Raised for Eric rather than decided: `otel.trace.forwarder.enabled` is now redundant. `Telemetry`
guards its send with `platform.hasRoute(...)`, so an unregistered forwarder is already a silent
no-op — which means the new `@OptionalService` gate does the legacy key's job more cheaply (no
exporter, no thread pool, no shutdown hook), and the only way to *use* the legacy key is the
contradictory pair `otel.forwarding=true` + `otel.trace.forwarder.enabled=false`. Retirement is
safe in the one direction that matters: anyone who has it set to `false` today ends up off after
upgrading too, since the new gate defaults off.
