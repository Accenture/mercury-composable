## Method — the guide-sufficiency probe

A fresh agent (Explore subagent, no session context) may read ONLY `docs/llms.txt`, `docs/index.md`
and `docs/guides/**` (md + json); no source, no examples, no web; it starts from `llms.txt` (the
guide-first rule) and lists every file it opened. Per question it gives pages used, a concrete answer
(exact keys, annotations, YAML fields, API calls, status codes as the guide states them), a verdict —
SUFFICIENT / PARTIAL (names the missing detail) / INSUFFICIENT — and what it would have needed source
for. The verdict scale is the metric: **guide sufficiency rate = SUFFICIENT / total**.

**The Rust engine DOES enforce the graph.task output-mapping source rule.** `set_fetcher_output_entry`
in `crates/knowledge-graph/src/common.rs` admits a constant, a `f:` plugin call, `result`/`result.`/
`result[`/`$.result`, `model.`/`$.model.` and the node's own namespace, and rejects anything else —
with the pre-#394 wording *"Invalid output data mapping in API fetcher {node} - LHS must start with
'model.', 'result.' namespace or '{node}.'"*. My grep for Java's REWORDED message (`valid only on the
input side`) found nothing and I wrote "the Rust engine has no such gate" into `caf93c64`'s commit
message, the thread and this log. Wrong: **grep for the mechanism, not for the other engine's message
text** — the twin often carries older wording. Consequences: (1) the graph.task doc fix applies to the
Rust twins (skills-reference §graph.task, `help graph-task.md`, the commands JSON note) — same
sentence, byte-parity on the help page; (2) the stale error text (and the `input.*` clue) is a Rust
lockstep engine item alongside the guarded-completion parity check (backlog P2); (3) both engines
skip the namespace check for a `f:` plugin source, so the Java sentence now lists plugin calls too
