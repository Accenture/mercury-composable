## Decisions taken as defaults, for Eric's review in the PR

1. The deadline is a `timeout` input (`llm.run.timeout=25s`): `graph.task` passes no time to live to a function. Step 3
   could have `graph.task` pass it instead.
2. The input-schema vocabulary is the module's own closed JSON Schema subset (the model is given JSON Schema; the graph
   contract's validator is OpenAPI 3.0). Keys are walked in name order, so Java and Rust name the same first problem
   whatever order a map keeps (serde_json sorts keys by default).
3. An unknown `llm.run` input and an unknown catalog-row field are refused: a misspelt `approval` must never let a write
   run.
4. `max_turns` bounds the conversation's turn count, so a resume spends from the same budget.
5. `params` passes the other `llm.chat` parameters; the loop owns `params.timeout_ms`, and `params.model` is refused in
   favour of the `model` input.

## Lessons

- **A function cannot see its caller's timeout.** `graph.task` holds the RPC timeout; the callee does not receive it
  (the worker uses it only to expire a `Mono`). Any engine function that must answer before its caller gives up needs
  its own deadline input, or the caller must pass one.
- **Order-sensitive error messages need a defined walk order** when two engines share them: the first problem a map
  holds is the first in its iteration order, and Java and Rust maps iterate differently.
