## The Sonar findings Eric's IDE surfaced mid-prep

SonarQube flagged `java:S2095` + `java:S2093` on `KafkaHealthCheck.buildClient` — the two
deserializer **instances** created inside the `try` and never closed. The proposed remedy
(try-with-resources) would have been a bug: the returned `KafkaConsumer` owns those deserializers
and closes them itself.

The better answer was to delete the resources rather than suppress the rule. Once `KafkaClientConfig`
puts `Class` objects in the properties, Kafka constructs the deserializers itself with no loader
lookup, so the instances were pure redundancy — a leftover from the first iteration of the fix, when
they were believed to be part of it. `buildClient` is back to `new KafkaConsumer<>(config)`, plus the
classloader override that is the actual fix, and the two imports went with them (grepping for the
import, not just the usage — the habit learned when Eric's IDE caught leftover imports in #399).

**That was not enough, and the reason is worth keeping.** Eric re-scanned: S2095 cleared but S2093
persisted, because the *consumer itself* is created inside a `try` that has a `finally` — the exact
shape the rule matches. The rule cannot be satisfied here: `buildClient` is a factory, and closing
the consumer before returning it is precisely the bug. The fix was structural, not a suppression —
the classloader scoping moved into a `withModuleClassLoader(Supplier<T>)` helper, so the
`try`/`finally` creates nothing and the method that creates the consumer has no `finally` at all.
Each half is then honest about what it does: one scopes a thread-local and closes nothing, the other
creates a resource and transfers ownership. Eric confirmed the re-scan clean.

The generalizable bit: when an analyzer flags a pattern that is genuinely wrong to "fix", the move is
usually to *separate the concerns the pattern conflates*, not to suppress. The suppression would have
been defensible and would have taught nothing; the split made the code read better and the reason is
now in the javadoc where the next reader finds it.

Two follow-on touch-ups from the same scan: the explicit `<String, byte[]>` witness I had used in the
lambda went back to the diamond (inference reaches through the `Supplier` target), and `behaviour` →
`behavior`, matching the American-English convention #402 applied in platform-core. The
`Constructor 'KafkaHealthCheck()' is never used` hint is inherent — `@PreLoad` instantiates it
reflectively and no IDE can see that.

**Mutation-proven before trusting it — twice, once after dropping the instances and again after the
restructure moved the override.** That blind-loader test is now the only thing between this code and
the field bug, so both times the override was disabled and the tests re-run — all
six in `KafkaHealthCheckClassLoaderTest` fail, and the first failure after the deserializers is
`sasl.oauthbearer.jwt.retriever.class`, a *third* class-name config beyond the two already
enumerated. More evidence for the ruling that the loader is the thing to fix, not the settings.

Also from the second screenshot: a method name missing its camel hump

## Decisions

- **This release is not a "no action required" release, and says so.** v4.12.10 was; this one
  changes an observable behaviour: an application whose Kafka template genuinely cannot build a
  client has been reporting `/health` green and will now report 503. That is the correction the
  release exists for, but a running deployment can notice it, so both the CHANGELOG and the release
  notes state it under its own heading. Stating it plainly costs one paragraph; discovering it in
  production costs a page.
- **`latest_release` in continuity waits for the tag.** Following the v4.12.10 rhythm: the release
  PR carries the sweep, the CHANGELOG, this log and metadata refreshes; the `latest_release` line —
  which quotes the squash hash and tag — is written after Eric tags, because those values do not
  exist yet. Recorded here so the next session does not read the omission as an oversight.
- **The deferred Kafka continuity fact lands here.** It was held back to avoid editing merge-hot
  `continuity.md` from two in-flight branches; `feature/otel-certification` touches that file not
  at all, and the Kafka branch has now merged, so this is the only branch editing it.
- **A code change rides in the release branch, deliberately.** A release branch normally carries only
  the sweep and the CHANGELOG. The Sonar finding is on code shipping *in this very release*, and the
  field's gate holds Overall Code to zero blocker/critical/major — so leaving it would hand the field
  a finding on the release meant to unblock them, and fixing it later would need another release.
  Flagged in the PR text rather than slipped in quietly; Eric gates the PR either way.
