# Subgraph suspend/resume under `for_each` — design spec

**Status:** RULED, ready to implement — field edge case reported 2026-09-18; shape and all five
open questions ruled by Eric the same day (§3, §7). **IMPLEMENTED on both engines 2026-09-19** — Java
#418 (`fb171c18`, with the doc sweep #420 and the rule-statement fix #425), shipped in v4.12.13; Rust
mercury #284 (Increment 118); ADR-0013 accepted in place with the index in the key. Status header
corrected 2026-09-23.

**The defect.** A parent graph invokes a subgraph through `graph.extension` with `for_each`, and the
subgraph contains suspend/resume nodes. All iterations write **one** store record, so only the last
suspension survives — and because the iterations run concurrently, which one that is, is a race.

**Repo scope:** Java (`mercury-composable`) and the Rust port in lockstep — the store key is a
cross-engine contract (§7, Q2).

**Related:** [graph-suspend-resume-implementation-plan.md](graph-suspend-resume-implementation-plan.md),
[suspend-resume-rationalization.md](suspend-resume-rationalization.md) — **neither mentions
`for_each`**, so this is an unconsidered case rather than a regression.

---

## 1. Why the collision happens

Three deliberate behaviours meet:

| Component | Behaviour |
| --- | --- |
| `GraphSuspend.getPersistenceEnvelope` | writes `{cid, graph, node, ttl, model, seen, run}`; **cid + graph form the retrieval key** |
| `RedisStateConnection.storeKey` | composes `graph:{graph_id}:{cid}` |
| `GraphExtension.inheritBusinessCid` | propagates the parent's `model.cid` to **every** child — "keyed by graph + cid, never by a per-call random id" |

`for_each` then forks N invocations of the **same** `graph_id` under the **same** cid, concurrently
(`concurrency`, default 3, clamped 1–30). One key, N writers.

None of the three is wrong on its own. `inheritBusinessCid` is what makes subgraph resume work at
all: the child must land on the same business transaction id or it could never be resumed.

## 2. Why the fix is viable at all

**`graph.resume` is not an external call.** It is a node in the graph's own traversal; a record is
found by re-invoking the graph with the same cid. So on the resume run the parent re-executes the
same `for_each` node and re-forks iteration *i* — **the index is regenerated by the same code path
that created it**, and nothing outside the engine ever has to know it.

That is the whole basis of this design. A discriminator that an external resumer had to supply would
not be viable here, because there is no external resumer.

## 3. Ruled shape (Eric, 2026-09-18)

1. **The key segment is the array index alone** — `0`, `1`, `2`. Not the size (see below; an earlier
   draft carried `<index>-<size>` and that was wrong).
2. It is placed in the **subgraph's state machine** as a reserved model key, and becomes a segment of
   the composite suspend/resume key.
3. **Constraint: the `for_each` array has positional consistency** — an item that is already in
   flight keeps the same index across the suspend run and the resume run. **Appending is
   explicitly supported.**
4. **Rejected — hashing the iteration's values:** flaky.
5. **Rejected — an author-nominated discriminator:** it needs an extra configuration parameter on the
   calling node and invites human data-entry error. (It would also have to be re-entered identically
   at every call site of the same subgraph, so the error surface grows with reuse.)
6. **Edge case 2 is deferred** (§6).

### Why the index alone, and not index + size

An earlier draft put the array size in the key (`0-20`), so that a changed size produced a **miss**
rather than a wrong-state restore — self-detecting, and failing safe to a fresh run.

**The domain says otherwise**, and it is the human-intervention scenario that shows it. A user's
warranty list is `["phone", "laptop"]`; later they add one
more and it becomes `["phone", "laptop", "headset"]`. With the size in the key, `0-2` and `1-2`
become `0-3` and `1-3`: both miss, and **phone and laptop restart from fresh** — discarding
suspensions that may already hold a human approval. Growing the list is the ordinary thing a user
does, so the guard destroyed the legitimate operation.

It was also guarding the wrong thing. The size segment could only ever detect a **size** change —
the operation that turns out to be supported — while a **reordering**, the change that actually
resumes another item's state, produced an identical key and passed straight through. So it blocked
the common good case and never caught the hazard.

With the index alone:

| Change between suspend and resume | Result |
| --- | --- |
| **Append** `headset` | `0`, `1` still resolve — phone and laptop resume correctly; `2` is a fresh run. **The use case works.** |
| **Reorder** | an iteration resumes another item's state — undetectable by the engine, and the reason §3.3 is a declared constraint |
| **Remove** an item | later items shift down and hit the wrong records; the tail record is never looked up and expires on its TTL |

So there is no engine-side detection left, and the spec should not pretend otherwise: positional
consistency is a **declared constraint** (§5), carried by documentation rather than by a check.

## 4. Mechanism

Every piece has an existing precedent.

**Transport — a header, not the body.** `callExtensionWithForkJoin` already holds `i`. The segment
rides as a header on the forward envelope, exactly as the business cid does through
`inheritBusinessCid`. It must **not** go in the body: that is `parameters`, the author's own `input`
mapping contract, and engine metadata does not belong there.

**Landing — a reserved model key.** The graph executor lifts the header into the child's state
machine. The key joins `GraphLambdaFunction.RESERVED_MODEL_METADATA`
(`cid, instance, flow, ttl, trace, parent, root, none, run`), which `GraphStateSkill` already uses as
`NON_PERSISTED_MODEL_KEYS` — so it is automatically excluded from the persisted model on suspend and
from the restored model on resume. Correct by construction: the **current** run supplies it, exactly
as it supplies `model.cid`.

**Store contract.** `graph.suspend` puts the segment in its dataset; `graph.resume` sends it in the
`type=get` body alongside `{cid, graph}`; `RedisStateConnection.storeKey` extends to
`graph:{graph_id}:{cid}:{index}`.

**Backward compatibility.** A subgraph invoked *without* `for_each` has no segment, and its key stays
`graph:{graph_id}:{cid}` unchanged. Records suspended before the upgrade remain reachable, and the
parent graph's own records are untouched (a parent has no index).

## 5. What a graph author sees, and what must be DECLARED

Nothing new to configure — no node property, no mapping. But the field designs graphs with a lot of
imagination, so the limits have to be **stated**, not inferred. A constraint a developer has to
discover by experiment is a defect in the documentation.

`workflow-suspension.md` already has the right surface and the right voice: its **Design rules**
section declares each limit as a rule. These belong there, written to be lifted verbatim.

### 5.1 One existing rule is wrong today and is corrected by this sprint

The guide currently says:

> **Suspension is self-contained per graph.** Records are scoped by graph + cid … A delegated
> subgraph inherits the parent's business correlation ID and **is fully resumable on its own**.

That is true of a single delegation and **false under `for_each`**, where every iteration shares
graph + cid and the record collides. It is what the field is designing against today. Corrected as
part of this sprint (Q5) — once the fix lands the sentence becomes true again, qualified by the
positional-consistency rule in §5.2.

### 5.2 Rules to add

- **`for_each` over a suspending subgraph requires a positionally consistent array.** Each iteration
  gets its own record keyed by its **position** in the array. An item already in flight must keep the
  same position when the transaction resumes.
  - **Appending is safe and supported.** Adding `"headset"` to `["phone", "laptop"]` leaves both
    in-flight workflows on positions `0` and `1`; the new item simply starts fresh.
  - **Inserting, removing or reordering shifts positions**, and a shifted iteration resumes
    **another item's** state. The engine cannot detect this. If your list can change in any way
    other than appending, key the workflow on something stable instead — give each item its own
    business correlation ID and delegate per item, rather than relying on array position.
  - **Where the array comes from decides whether this rule is easy or hard to keep.** Suspension
    serves two scenarios (see *When a workflow must wait*), and they differ here. For **human
    intervention** the array is usually a curated list — a user's warranty products — that grows by
    appending, which is exactly the supported change. For an **event-driven** wait on an async
    downstream, the array is more often derived from a query or a batch manifest, and re-deriving it
    on the resume run guarantees nothing about order. In that case **freeze the list into the
    parent's `model` before fanning out**, so the resumed run iterates the array it suspended on
    rather than whatever the source returns later.
- **Do not reach a suspending graph through a flow launched by `for_each`.** Parent → `for_each` →
  flow → graph with suspend/resume is **not supported**: the iteration identity does not survive the
  flow hop, so those runs collide exactly as before. Put the flow *inside* the subgraph instead —
  a subgraph may call a flow — and the composition works with the iteration identity intact.
- **Nested `for_each` over suspending sub-subgraphs is not supported.** Suspension at multiple
  nesting levels carries too many side effects to reason about. Nested `for_each` is discouraged on
  its own terms in any case — it is a formula for slow performance — so the recommendation is the
  same with or without suspension: flatten the model.

### 5.3 Why these are declared rather than enforced

Not because enforcement is hard — for one of these shapes it would be easy — but because the engine
is the wrong place to answer it.

**Every edge case has edge cases.** Chasing them into the engine has no natural stopping point, and
each guard added is a shape the engine must then keep working forever. The answer is **clean
knowledge design**: a graph model kept simple enough that the question does not arise. Avoiding
over-engineering is a **product-owner responsibility**, exercised in the design phase and at the
certification gate — not a runtime problem for the engine to absorb (Eric, 2026-09-18).

That is also why there is no CompileGraph detection for these shapes (Q3). A partial gate would be
worse than none: it teaches that *unflagged means safe*, which is learned once and applied
everywhere. Declared rules cover the whole surface, including the shapes no gate could see.

## 6. Edge case 2 — deferred, and why it is different in kind

Parent → `graph.extension` with `for_each` → **flow** → graph with suspend/resume.

The business cid survives that chain because it is an **Event Script** mechanism: `FlowInstance`
preserves `businessCorrelationId` and exposes it as `model.cid`, and `CompileFlows` lists `model.cid`
among the reserved keys a mapping may never overwrite. MiniGraph does not carry it across the hop —
the other engine does.

An iteration index has no such carrier. To survive a flow hop it would have to become an Event Script
reserved key too: a second engine's contract, its own Rust lockstep, and a MiniGraph concept pushed
into a layer that has no notion of graph iteration. Eric's ruling is to defer — it would create other
side effects.

**Documented workaround, which is why deferring costs little:** a subgraph can itself call a flow. So
`parent → subgraph(for_each) → flow` expresses the same composition with the index staying inside
MiniGraph, where it is carried correctly.

## 7. Rulings (Eric, 2026-09-18)

- **Q1 — the reserved key's name: `model.iteration_index` stands.** It was questioned only while the
  composite draft made it under-describe a value holding index *and* size; with the index alone it is
  exact. Recorded rather than deleted — it is a reserved key, and the next reader should know the
  name was considered.
- **Q2 — Rust lockstep, not optional.** `GraphStateSkill` already notes that both engines trim the
  cid identically "so the mixed-fleet key stays one key": the store key is an explicit cross-engine
  contract, and a Java-only change would split the key space for an installation running both engines
  against one Redis. *Read as:* Java leads with the key format pinned, Rust twin immediately after,
  per house precedent and [[conv-ports-adopt-java-release-number]] — say so if a simultaneous pair
  was meant instead.
- **Q3 — no CompileGraph detection.** For simplicity: this is a **design-phase** concern and a
  product-owner responsibility, not something the engine should detect (§5.3).
- **Q4 — nested `for_each` with suspension is a declared non-goal.** Suspend/resume at multiple
  nesting levels has too many side effects, and nested `for_each` is discouraged regardless as a
  formula for slow performance. Declared in §5.2.
- **Q5 — the §5.1 correction ships inside this feature sprint**, not as a separate earlier PR.

## 8. What this is not

Not a change to how suspension works, not a new node property, and not a change to the parent graph's
own suspend records. The engine-side surface is one header, one reserved model key, and one extra
segment in the store key.
