## What We Did

- **The design review.** Viable, and half of it already decided: the loop spec's 7.3 ask row (a routeless row whose
  call waits in the approval block and resumes with an answer) is built in both engines (`AgentLoop`, `agent_loop.rs`)
  and documented only in the spec; the graph suspends durably with a mandatory expiry and an at-most-once resume. The
  loose end is delivery and collection. The one change recommended to the concept: the function delivers and collects,
  the engine keeps waiting (a tool call is bounded by the tool timeout and the Event API's time to live; a wait in the
  pack dies with a restart and duplicates `graph.suspend`).
- **Round 1 of `draft-design-specs/ask-a-person-channel.md`** (an uncommitted review branch, revised in place):
  the message, the signed stateless ticket, the return link (a GET shows, a submit resumes - link unfurlers click), the
  reply endpoint with the engine-entry allowlist, the inbox as a mailbox for a device that is not always on, the
  resume gate so a reply never starts a fresh run, channels through vendor MCP for the outbound half only.
- **Round 2, Eric's generalization (R1-R6):** the agent-question UI as one store-and-forward channel beside a chat, a
  mail server and a topic, a standalone application on the pack framework; the tool sends one message event and knows
  no channel; the main flow and delivery-and-collection as separate parts; the main flow keeps no store, so the reply
  page reads the wait by the reference graph's re-advice and the re-suspend keeps the original expiry. **R7:** no
  authentication in development; SSO or an OAuth 2.0 access token in production.
- **Round 3:** Q2-Q9 agreed as proposed; **R8** adds `kind: advice` - a notification with no decision, for status
  updates of a long AI SDLC run and acknowledgements after a response - with no ticket and no link, appended in the

  Playground's `order-assistant`. Section 15 lists the defaults set without a ruling.
