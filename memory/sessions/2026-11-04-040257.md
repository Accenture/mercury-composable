## Built (branch `feat/graph-extension-async`, commit `8693df4f`, PR #609)

- **`GraphExtension`:** `async=true` starts the target (a deployed graph, or a flow through `flow://`) and returns
  `next` at once.
  - The target inherits the business correlation ID. It runs under its own TTL (a flow's own `ttl`, or the
    `graph-executor` flow's TTL for a graph), or under the node's `ttl` when the node declares one.
  - With `for_each` the node starts one run per element. A sliding window keeps at most `concurrency` runs active,
    and each run carries its `x-iteration-index` position, as a synchronous fan-out's does.
  - The runs are waited on in the background, for their TTL plus 5 s, so the next element can start and each
    run's end is logged with its status.
  - The run events carry the node's span explicitly, because the thread that starts a later run has no trace
    context.
  - The sync and async paths now share one event builder (`forwardEvent`), and the sync behaviour is unchanged
    (249 module tests).
- **Failure to start:** an unknown graph id or `flow://` id gives 404, and an input the target graph's root
  `schema` refuses gives 400. Both are staged like a failing call and routed to `exception=`. The input is
  validated by the schema validator before any run starts; for a fan-out, every element is checked first.
- **`GraphModelValidator`:** `async` is refused on another skill, a value other than `true`/`false` is refused,
  and `output[]` is refused on an asynchronous node. All three apply at CompileGraph and at the Playground's
  pre-run check.

## Decisions taken as defaults, for Eric's review in the PR

1. An unknown `flow://` target is `exception=`-routable on an asynchronous node (a synchronous node throws, which
   aborts). In async mode a failure to start is the only failure the node can report.
2. A refused input is validated before the run starts, so the spec's "a refused input" reaches the parent. The run
   reports to nobody, and a 202 for a refused input would mislead.
3. The node's `ttl` is the target's TTL (the child-call deadline on a sync node).

## Findings for 3b

- The entry kind can be read from the flow instance's reply route:
  - a plain REST request replies on `async.http.response@<origin>`;
  - a `stream: true` request replies on its lane, `async.http.response.stream.{n}@<origin>`;
  - anything else is an event entry, whose return path would be `input.header.x-return-path`.
- No WebSocket entry runs a deployed graph today (the WebSocket services are the Playground's `graph` and `json`),
  so the spec's WebSocket row is new entry work.
- `AsyncHttpResponse` keys the context by request id. Once the engine sends `eof` the context closes, and the
  flow's later single-shot reply is dropped. A streamed graph can therefore send its result as the terminal event.
- Possible latent bug (not verified by a test): `TaskExecutor.abortFlow` sends the error to `flowInstance.replyTo`
  before `endFlow`, and `EventEmitter.send` throws for a null destination. So a flow launched with no callback
  (`FlowExecutor.launch` without one) that aborts may never close its instance. The asynchronous extension always
  waits on a reply, so it does not hit this path.

## Lessons

- **A negative control can pass by coincidence of values:** the parent's TTL and the target flow's TTL were both
  30 s, so passing the wrong one looked right. When a test asserts "not X but Y", make X and Y differ.
- **An async node's failure-to-start set is the node's whole error contract**, because nothing else comes back.
  What the target would refuse at its root has to be checked before the start.
