## What was built

- **`diagram-assistant`**, the Playground example's third AI graph: an `llm.run` node whose one catalog row, `render_diagram`,
  maps to the route `diagram.render`; the model drafts a Mermaid diagram from the description, validates it through the tool,
  fixes it if the server says it is invalid, and answers with the validated code. 11 nodes: the island with the catalog and the
  handler, `check-input`, `assist` (`max_turns` 6, `timeout` 50s, `ttl` 55s, `progress`, `result_limit` 8 KiB), `route`,
  `respond`, `stopped`, `failed`. The catalog row's input schema uses the loop's closed subset - the server's `$schema`
  keyword stays out of the row; the binding's digest covers the server's own schema.
- **Wiring:** `event-over-http.yaml` maps `diagram.render` to the MCP binding (`mcp.peer.host`, `mcp.peer.port`, default
  8088, the Python binding; 8089 the Node one); `mcp/mermaid-servers.yml` in the example's resources is the binding's server
  file for the demo (the Mermaid URL, a 20 s timeout, the tool's digest as reviewed today).
- **Tests:** `MockDiagramRender` serves the route in the test scope; `MockLlmChat` learned the diagram conversation (a draft,
  one validation call, the answer); `DiagramAssistantTest` (3 cases: the description required, the answer with the validated
  code and the call log `render_diagram` → `diagram.render` ok, the watched run's `tool.start` on the bound route). The
