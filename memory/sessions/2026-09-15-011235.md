### The platform shutdown-lifecycle feature (the substantive outcome)

Reviewing the "`CacheRuntime.shutdown()` is never used" finding, I first proposed deleting it. Eric
corrected: that hides a real **feature gap — Mercury has no platform shutdown lifecycle**; components
hand-roll their own `Runtime.getRuntime().addShutdownHook(new Thread(...))` (three in-tree:
`PersistentWsClient`, `BdbElasticStore`, `FileElasticStore`). We examined the lifecycle events first
(startup is covered by `@BeforeApplication`/`@PreLoad`/`@MainApplication(sequence)`; shutdown is the gap;
ready-to-serve is a soft gap) and he approved a minimalist imperative API.

Implemented **`Platform.getInstance().onShutdown(Runnable)`** ([[platform-onshutdown-lifecycle]]): one
platform-owned JVM hook (installed lazily on first registration), callbacks run in reverse registration
order, each isolated. `runShutdownHooks(List)` is package-private + parameterized so the logic is
unit-tested without a real JVM shutdown; PlatformShutdownTest added (3 tests). Migrated the three
hand-rolled hooks onto it (each already holds a live `Platform` — no premature-init risk), and wired
`CacheRuntime` to register its Redis-connection close from `build()` — so `shutdown()` is now a *used*
method (finding resolved via a real feature, not deletion).
