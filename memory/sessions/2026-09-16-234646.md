## CompileGraph — `task` and its skill must agree, both ways

A node with a `task` route but no `skill` compiled and passed silently as a structural node. The
graph traversed it, nothing executed, nothing was reported — the model looked right and did nothing.
Now an `IllegalArgumentException` from `GraphModelValidator`, and bidirectional: a `task` must be
claimed by a task-consuming skill, and each of those skills requires a `task`. The set is
`graph.task`, `graph.suspend`, `graph.resume`.

**Two wrong versions preceded the right one, and both were caught by running the suite:**

1. Keying on `task`/`input`/`output` rejected three valid tutorial graphs. `Provider` nodes use
   `input` for their HTTP request shape, `Dictionary` nodes use `output` for their projection — 40
   such nodes, none with a skill by design. `input`/`output` are descriptor fields, not work markers.
2. `graph.task` *only* — as literally instructed — would have rejected 20 valid nodes. The source
   says why: `graph.suspend` and `graph.resume` are documented **supersets of graph.task** whose
   `task` names the pluggable state-store function.

**The durable lesson:** a validator is a claim about every model that already exists. Checking the
claim against the corpus took one command each time and twice returned "no". Neither error was
visible by reading the rule; both were obvious the moment the suite ran.

The corpus check also gave the rule its confidence: `task` without `skill` occurs **zero** times, and
all **67** nodes carrying one of the three skills carry a task. The invariant was already true — it
simply was not enforced.

Tests assert the **message**, not just the throw: a malformed fixture would satisfy `assertThrows`
for an unrelated reason and give false confidence. A guard test pins that descriptor nodes stay
valid, so the check cannot be re-broadened the way the first draft was.

## Event Script — case-insensitive header lookup

`TaskExecutor` lowercases an `input.header.*` reference, which agrees with the HTTP adapter because
that adapter ingests headers lowercased. The Kafka flow adapter delivers wire casing, so a
producer-sent `Content-Type` was addressable by **no** mapping at all.

Fixed as a case-insensitive lookup retried only when the direct lookup misses — HTTP is untouched
and pays nothing. The rejected alternative (lowercase at the Kafka adapter) would have changed what
the `*` whole-body passthrough hands a function and broken flows matching exact casing.
**Generalizable: normalize at the point of use, not at ingestion, when the ingested form is part of
someone else's contract.**

The scan is a package-private `headerIgnoringCase` specifically so it could be tested directly
rather than shipped unproven.
