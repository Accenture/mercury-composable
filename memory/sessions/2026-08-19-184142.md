**The fix (Eric ratified the 4-part plan; Java-only — no Rust OTel forwarder):**
1. `forward()` WARN now logs the failure cause (`rc.getFailureThrowable()`, available at SDK
   1.63.0) — any future drop is self-diagnosing.
2. `buildExporter(...)` sets an explicit `RetryPolicy` with a WIDENED exception predicate
   (`setRetryExceptionPredicate(e -> true)`): every IOException retries under the default
   bounded backoff (5 attempts, 1s→5s); HTTP status semantics unchanged (429/502/503/504 only).
   Rationale: OTLP delivery is at-least-once — duplicates tolerated, drops are data loss; this
   also fixes silent production span loss in the field, not just CI.
3. New `OtlpExportRetryTest`: a raw-socket FlakyOtlpServer fully reads each request, KILLS the
   first connection without responding (client sees EOF where the status line should be — the
   exact non-retryable class), serves an empty OTLP 200 on later connections. Asserts export
   success + ≥2 connections. **Mutation-proven:** with `setRetryPolicy` removed, the pin fails
   on the first-attempt drop.

**Durable lesson:** the OTel SDK's "retry by default" is narrower than it sounds — transport
failures outside a small IOException whitelist are single-attempt. For fire-and-forget
telemetry exporters, always (a) log the failure cause and (b) decide the retry predicate
deliberately.

Also: **the PR's own first CI run FAILED with the same test — and the new cause log paid for
itself immediately**, naming a SECOND failure class the retry cannot reach:
