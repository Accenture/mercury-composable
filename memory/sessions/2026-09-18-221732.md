**The generalisable part is the hazard, not the recovery.** Two agents sharing one working tree is
not two agents sharing a repo — `git add`/`commit` acts on whatever branch is checked out *now*,
so a branch created by one is a commit target for the other. Creating a branch is normally a private
act; in a shared tree it is a global one.

## Verification: the same `||` trap, twice

I ran `mvn -q -o test … | tail -40 || mvn test … | tail -40`, got exit 0, and nearly reported the
build green. The 0 was `tail`'s — `||` binds to the **pipeline**, whose status is its last command,
so the fallback never ran and Maven had in fact failed on offline resolution (BC 1.86 was not in the
local repo). Re-run properly: `mvn > log 2>&1; echo "EXIT: $?"` — 500 tests, 0 failures.

This is the second instance of exactly this binding error in this repo (the first was `||` binding
to `sed` rather than `grep` in the undeclared-reference harness). The pattern: **when a verification
command is itself a pipeline, its exit status stops describing the thing being verified.** Capture
the tool's own status before piping. Not promoted to a continuity fact — continuity is already over
its fact cap and a method lesson belongs in the log; if it recurs a third time it earns a slot.

Related: I also declined to trust `BUILD SUCCESS` alone for the BouncyCastle claim, because
`TestBase.generatePrivateKeyAndCert()` returns a **boolean** and its failure path only logs a
warning — a BC breakage would have silently skipped SSL setup and still passed 500 tests. Confirmed
the success message fired once and the warning zero times. The catch-block-returns-false shape is
the same silent-pass hazard as the pipeline exit code, one level up.
