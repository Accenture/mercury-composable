## The actual mechanism

Kafka consults the thread context classloader **before any client exists** — in the static
initializer of its own config classes.

- `ConfigDef.define` resolves a `Type.CLASS` setting's **default** at define time
  (`ConfigKey.<init>`: `defaultValue = parseType(...)`, ConfigDef.java:1338).
- `SaslConfigs.addClientSaslSupport` (SaslConfigs.java:388) defines
  `sasl.oauthbearer.jwt.retriever.class` with a class **NAME** as its default.
- So initializing `ConsumerConfig` loads that class through `Utils.getContextOrKafkaClassLoader()` —
  no broker, no SASL, no credentials, no connection involved.

`healthProbeProperties` reaches that initializer while **resolving the template**, through
`ConsumerConfig.configNames()` (KafkaClientConfig.java:207) — before `buildClient` is called at all,
and therefore outside v4.12.11's override.

**Why only produce-only, and it is almost absurd:** the consumer path's references to the same class
are `ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG`-style **compile-time String constants**, which
javac inlines — no class initialization — so its first touch is `new KafkaConsumer<>(config)`, already
inside the override. The produce-only branch calls a real static **method**. Verified in bytecode:
`consumerProperties` holds zero references to `ConsumerConfig`; `healthProbeProperties` holds an
`invokestatic ConsumerConfig.configNames()`. Same jar, same thread, same config — the difference was
one inlined constant.

## Two consequences that explain the rest of the field evidence

1. **It is an `Error`, not an `Exception`.** `ExceptionInInitializerError` is not caught by
   `catch (Exception e)`, so it escaped `handleEvent` and `/health` answered a **raw 500**, not a 503.
   The field observed exactly this and reasoned correctly from it — the report used "surfaces as a 500,
   not the 503 probe() produces" as evidence the failure was outside construction handling. Right
   inference, and it pointed one call earlier rather than one call later.
2. **It never heals.** A class whose initializer threw is erroneous for the life of the JVM
   (JLS 12.4.2): every later access throws `NoClassDefFoundError: Could not initialize class` on
   *every* thread, however correct its loader. One probe on one pooled kernel thread poisons the class
   permanently. So the leniency model does not apply at all here — there is nothing to wait for.

Also consistent: no `buildClient` WARN/ERROR was logged, because `buildClient` was never reached.

## Reproduction, before touching the code

A 30-line program in a fresh JVM, no broker and no Kafka client: touch `ConsumerConfig.configNames()`
on a thread with a blind TCCL. It prints the field's message **verbatim**, then shows an ordinary
thread with the correct loader failing afterwards with `Could not initialize class`. Getting the
diagnosis from a reproduction rather than from Kafka-internals reasoning is what kept me off the
report's path — my own first instinct was also "it must be the deferred SASL login".

## The fix

- `probe()` and `href()` now run **entirely** under the module classloader (template resolution,
  construction, round-trip, close). `buildClient` keeps its own nested override, since it is a seam
  tests and subclasses call directly.
- A `catch (LinkageError)` renders a poisoned class as a 503 naming the *configuration* — never the
  network, and never the passing waiting status. Both unusable-config paths share one `unusable(...)`
  shape.
- `GroupProtocolResolver` reaches `AdminClientConfig` and `Admin.create` the same way on the consumer
  path; it is safe only because the probe now pins the loader around template resolution. Noted in
  its javadoc so a future edit does not move it out from under the pin.
- Guide and test-class javadoc corrected: both still said the override was scoped to *construction*.

## The durable lesson

v4.12.11's own durable lesson was "a pooled kernel thread changes what code can SEE, not just when it
runs." It was right, and still too narrow: **what a wrong loader can damage is not limited to the
operation you wrapped.** Class initialization is a one-shot, JVM-wide, irreversible event that can be
triggered by something as innocuous as a static method call in a config builder — so "wrap the Kafka
call" is the wrong granularity. Wrap every path that can touch the library, and remember that the
compiler decides which of your constant references are even capable of triggering it.

Second, smaller: a field report with a correct mechanism and a plausible wrong location is more
dangerous than a vague one, because the proposed patch looks like a one-liner. The report was honest
about exactly this ("the one piece I could not prove..."), and that caveat is what earned it a
reproduction instead of a merge.
