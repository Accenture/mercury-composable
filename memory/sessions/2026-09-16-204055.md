**Eric's call to ask for a GET was the better experiment**, and worth recording as a pattern. A
second POST would have re-run one path; the read path produces a *structurally different* trace —
`v1.get.profile` → `v1.decrypt.fields`, five spans against the write path's six — which shows the
forwarder maps what each flow actually did rather than emitting a fixed shape. It also exercised the
data path end to end: the POST response masked `address`/`telephone` as `***` and the GET returned
them in clear, so encrypt-on-save and decrypt-on-read each ran and each appears as its own span.
**Generalizable: when asked to repeat a verification, prefer a variation that changes the output
shape — a repeat mostly re-tests the harness.**

The default-off leg gave more than expected. It is not silent: `Skip optional class
…OpenTelemetryForwarder during PreLoad phase`. DevOps can see the feature was considered and
declined, instead of inferring it from absence — so that property is now confirmed three ways (unit
test, no route at runtime, explicit log line).
