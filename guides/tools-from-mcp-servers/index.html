    Tools from MCP Servers¶

    Recipes: when an agent loop needs a capability an existing MCP server already provides, how to put that server's tool on a graph through the language packs' MCP binding, with nothing added to the engine and one digest pinned per tool.

    At a glance

    • What — seven recipes, one per server: Git, Time, Fetch and Filesystem (the maintained reference servers), Neo4j's Cypher server (the vendor's alternative to the built-in graph tools), GitHub's hosted server and Playwright's browser (vendor servers). Each is an entry of the packs' extensions/mcp-binding/resources/mcp-recipes.yml, the digests describe printed, the bind lines and a catalog row rewritten for the graph.
    • The rule — build when the sandbox must be the pack's or the capability is a few lines; bind when the server is a product's own front door. The built-in tools cover files, the web, the knowledge graph and the clock; these recipes cover what they do not, and name the alternative where the two overlap.
    • Governance is unchanged — the model reads the graph's row, never the server's description; a tool that changes anything is write: true on its row and waits for a person under the node's default mode; the binding refuses to boot when a server changes a tool's schema under the graph.
    • Kept honest — a gated test in each pack starts the servers from the recipes file and checks the digests (MCP_RECIPES_LIVE=1; GitHub's with GITHUB_MCP_TOKEN). The 95 digests here were read on 2026-11-18 from the versions the entries pin, through both packs; a changed digest is the recipe rotting, caught at the test or at the boot.

    Build or bind¶

    The sixth principle of the built-in tools, applied: a capability is built into the packs' agent-tools extension when its sandbox must be the pack's (a workspace root with a write mark, a host allowlist, row caps and a delete gate), when the pack's process must not depend on a second runtime, when the contract must be portable across backends, or when it is a few lines; it is bound from an existing MCP server when that server is a product's own front door, maintained by its vendor, with the surface that would be written anyway. Its reads run unasked and its writes are approved under the node's mode like any other tool's.

    The need Built in Bound, by a recipe below
    Files inside one workspace file.read, file.write, file.list, file.search, file.extract the Filesystem server, as an alternative (read-only recipe)
    A page, or a section of a site web.fetch, web.crawl the Fetch server, as an alternative to web.fetch alone
    The agent's knowledge graph graph.schema, graph.query, graph.write, graph.ingest Neo4j's Cypher server, as an alternative without an ingest
    The clock time.now the Time server, for zone conversion and relative times
    A repository's history and state — the Git server
    A code forge — GitHub's hosted server
    A browser — Playwright's server

    How a binding works¶

    Four lines, from the packs' MCP binding (ADR-0033; the function-per-tool shape of 2026-11-16):

    1. A server-file entry in the pack's resources/mcp-servers.yml: the transport (stdio, a subprocess of the pack's process, or http, a streamable HTTP endpoint), the command or the URL, and every credential as a ${NAME} reference resolved from the pack's environment at boot and never logged. ${NAME:default} carries a default.
    2. describe connects to a server, lists its tools and prints, for each, the SHA-256 of its input schema in canonical JSON, the bind line to paste and a catalog row to review: python extensions/mcp-binding/mcp_binding.py describe git in mercury-python, node extensions/mcp-binding/mcp-binding.mjs describe git in mercury-nodejs.
    3. A function that binds the tool. bind(server, tool, digest) returns the tool as an async callable; an ordinary preload function on a route of your choosing calls it, shaping the arguments on the way. The route names the capability (repo.log), never the transport, so the same route may later be served another way.
    4. A catalog row on the graph with the description rewritten for the use case and write: true where the tool changes anything, plus an Event-over-HTTP entry on the engine for the route (one route per entry).

    At boot the binding verifies every declaration and refuses to start, by name, when a bound server is not configured, a tool is no longer offered or its digest changed. The engine's loop then treats the route like any other: the pre-flight check finds it served, the node's mode governs its writes, and every result returns to the model as text.

    # mercury-python, extensions/mcp-binding/mcp_binding.py (or an application that imports it)
git_log = bind("git", "git_log", schema_sha256="c4e5907dca6fbbbb7ba130e7ab57445f91d7c1df0d67f01a610940176b3c708e")

@preload(route="repo.log", instances=10)
async def repo_log(_headers: dict[str, str], body: Body):
    arguments = dict(body) if isinstance(body, dict) else {}
    return await git_log({"repo_path": REPOSITORY, **arguments})   # the path is configuration, never the model's

    // mercury-nodejs, extensions/mcp-binding/mcp-binding.mjs
const gitLog = bind('git', 'git_log', { schemaSha256: 'c4e5907dca6fbbbb7ba130e7ab57445f91d7c1df0d67f01a610940176b3c708e' });
preload('repo.log', { instances: 10 }, async (_headers, body) => gitLog({ repo_path: REPOSITORY, ...body }));

    Reading a recipe¶

    Each recipe gives the entry as mcp-recipes.yml holds it (nothing in that file is loaded by default; an entry is copied into mcp-servers.yml), the tools with the digests describe printed, which of them belong on a graph and how each is marked, the sandbox the server itself enforces, and one catalog row as an example. The digests were read on 2026-11-18 from the pinned versions; the Python and the Node.js binding printed identical digests, as the shared canonical form intends, and the live digests test of each pack re-reads them.

    The row is yours; the digest is the server's. A row's input_schema is what the graph exposes to the model, written in the loop's closed vocabulary (type, properties, required, additionalProperties, items, enum, const, the numeric and length bounds, pattern; title, description, default, examples and format documentary); the digest pins the server's schema, which several servers write with keywords the loop refuses ($schema, anyOf). So a row is never a copy of describe's output: describe prints the server's schema to review, and the row is written from it, usually narrower - the function in between adds what the graph must not expose (a repository path, a database name) and leaves out what the model must not choose.

    Git¶

    The reference Git server (Python, uvx): the history and state of one repository, which --repository confines every tool to. Bind it when a use case works on a repository - release notes from the log, a review of a diff, a commit after approval. The function adds repo_path from configuration, so no graph names a path.

    Time¶

    The reference Time server (Python, uvx): the current time in a zone, a conversion between zones and a time some interval ago. The built-in time.now answers "now" in a few lines without a process; bind this server when a use case converts between zones or reasons about relative times. --local-timezone fixes the server's default zone.

    Fetch¶

    The reference Fetch server (Python, uvx): one tool that fetches a URL and returns its content as Markdown, with robots.txt honoured, private addresses refused by default and --allowed-hosts as the allowlist (repeat the option for more hosts; *.example.com matches the subdomains). The built-in web.fetch and web.crawl cover the same ground with the allowlist in the pack's configuration and no child process; bind this server when its Markdown output or its readability extraction is wanted, for a single page at a time - the crawl has no counterpart here.

    fetch:
  transport: stdio
  command: uvx
  args: ['mcp-server-fetch==2026.11.11', '--allowed-hosts', '${MCP_FETCH_ALLOWED_HOST:docs.example.com}']
    Tool Digest (schema_sha256) On a graph
    fetch 16fdd8e4c71db0b8693474bca52a6a1d81f6d862bb842ccead7287a220e1ef98 read

    The server's own description of fetch addresses a chat assistant ("this tool now grants you internet access"), which is exactly why the row carries the graph's description and the model never reads the server's. The server returns max_length characters (default 5 000) and the model pages with start_index; the row below fixes the length.

    { "name": "page_fetch", "route": "page.fetch",
  "description": "Fetch one page of the product documentation as Markdown. Pass start_index to continue a page that was cut.",
  "input_schema": { "type": "object", "additionalProperties": false, "required": ["url"],
    "properties": { "url": { "type": "string", "pattern": "^https://docs\\.example\\.com/" },
                    "start_index": { "type": "integer", "minimum": 0 } } } }

    Filesystem¶

    The reference Filesystem server (Node.js, npx), started in read-only mode: the ten tools that read and list, each confined to the directories named on the command line. The built-in file.* tools are the default for files - they ship their rows and need no second runtime - and this server is the alternative when a Node.js runtime beside the pack is acceptable and its surface is wanted: a directory tree as JSON, media files as content blocks, several files in one call. Without --read-only the server also offers write_file, edit_file, create_directory, move_file and copy_file, each write: true on a graph; --read-only-dir <path> protects one directory while the others stay writable.

    Neo4j's Cypher server¶

    The vendor's server (Python, uvx): the schema, a read query and a write query against one Neo4j database, the connection taken from the environment. It is the alternative to the built-in graph.schema, graph.query and graph.write when the graph is Neo4j and the vendor's own surface is preferred; the built-in tools stay the default because their rows are portable across the openCypher databases, graph.schema needs no plugin, and graph.ingest has no counterpart here - a model using this server writes its MERGE statements itself. get_neo4j_schema needs the APOC plugin in the database; --read-only leaves write_neo4j_cypher out of the listing.

    neo4j:
  transport: stdio
  command: uvx
  args: ['mcp-neo4j-cypher==0.6.0']
  env:
    NEO4J_URI: '${NEO4J_URI:bolt://127.0.0.1:7687}'
    NEO4J_USERNAME: '${NEO4J_USERNAME:neo4j}'
    NEO4J_PASSWORD: '${NEO4J_PASSWORD}'
    NEO4J_DATABASE: '${NEO4J_DATABASE:neo4j}'
    Tool Digest (schema_sha256) On a graph
    get_neo4j_schema 51d2e5525a9bb54a5a06451a19eea2832e868b6c9c44637f29294e52c35b70ce read (APOC)
    read_neo4j_cypher 9631746823a32739ed4fa1dd5bd2bd04c93780ade4ba3b48aa9f3915b4069562 read

    "properties": { "query": { "type": "string", "maxLength": 4000 }, "params": { "type": "object" } } } }

    GitHub's server¶

    Keeping a recipe honest¶

    A recipe rots when the server it names changes a tool's schema, renames a tool or drops it. The binding catches that at boot, by refusing to start with the server and the tool named; the recipes are checked before that, by a gated test in each pack that starts every credential-free server from mcp-recipes.yml with uvx or npx, lists its tools through the binding's own client and compares the digests with the pinned ones; GitHub's hosted server is listed the same way when a token is in the environment, once under the read-only header (exactly the pinned reads) and once without it (every pinned tool):

    # mercury-python
MCP_RECIPES_LIVE=1 pytest tests/test_mcp_recipes.py
# mercury-nodejs
MCP_RECIPES_LIVE=1 node --test test/mcp-recipes.test.mjs
# both: the Neo4j server also wants NEO4J_PASSWORD and a database at NEO4J_URI; GitHub's wants GITHUB_MCP_TOKEN

    The pinned digests live in tests/vectors/mcp-recipes.json (test/vectors/mcp-recipes.json in the Node.js pack), one file shared byte for byte, and the test fails by name: the git recipe rotted - missing [...], changed [...]. The fix is a review, never a blind re-pin: run describe on the server, read the new schema, decide whether the row on the graph still says what the tool does, then update the digest next to the function, in the vector file and on this page in one change. Without the live flag the tests still load the recipes file and check that every pinned server has an entry, so a broken entry fails the ordinary suite.
