## What We Did

- **The answer: viable, and built, on `feature/minimalist-msgpack` (a local worktree; not pushed, no PR - Eric gates both).**
  `system/minimalist-msgpack` (`org.platformlambda.mini.msgpack`, groupId `org.platformlambda`, 4.12.20, Boot parent for
  the build only, no compile or runtime dependency): a streaming `MsgPackWriter` and `MsgPackReader` written from the
  published specification (spec.md, 2017-08-09, fetched and read) for nil, bool, int, float, str, bin, array and map;
  `MsgPackFormat` (the 35 formats, a 256-entry first-byte table, `0xc1` null), `MsgPackType`, and one checked
  `MsgPackException extends IOException`. No extension types: the reader knows their framing so `skipValue()` steps over
  one, and platform-core keeps reading one as null. platform-core's `MsgPack`, `CanonicalPackager` and `AsyncHttpClient`
  now use it; the value layer (`_T`/`_D`, null transport, `MAX_DEPTH` 64) is unchanged; `msgpack-core` is gone from the
  reactor. Module home `system/`, not `extensions/`: platform-core must depend on it and extensions depend on platform-core
  (Eric agreed).
- **How the four criteria are met.** Big-endian fields through `VarHandle` byte-array views (the sanctioned intrinsic), no
  `sun.misc.Unsafe`, no reflection, no deprecated API, `java.base` only; no `synchronized`, `ThreadLocal` or lock, a
  reader or writer per call (virtual threads never pin); the writer's integer rule is msgpack-core's and `rmp`'s (fixint for
  -32..127, unsigned widths for larger non-negatives, signed for negatives), float32/float64 bit for bit, shortest str/bin/
  array/map headers, short ASCII text written straight into the buffer.
- **Robustness rules of the reader** (all tested): every read bounded by the array window; str/bin/ext lengths and array/map
  counts 32-bit unsigned and checked against the remaining bytes before anything is allocated or consumed (N elements need N
  bytes, N entries 2N - `df 80 00 00 00`, the CVE-2026-90473 shape, is refused at the header); `0xc1` refused; `skipValue()`
  iterative (100,000 levels skip with no stack); a failed read leaves the position unchanged (so `readBigInteger()` can
  follow a refused uint64); lenient UTF-8 and str/bin cross-acceptance on read kept (msgpack-core's defaults).
- **Tests.** Module: 134 (the spec's format table pinned byte by byte against a literal copy of the table; hand-derived vectors
  at every boundary; non-minimal encodings; every hostile header; every ext format skipped; a seeded 3,000-document corpus
  round-trips and 300 documents' every proper prefix - over 50,000 cuts - is refused), JaCoCo gate 90% line and branch,
  passing. platform-core: the serializer tests pass unchanged - `CanonicalPackagerVectorsTest` (the independent-oracle
  vectors, byte-identical with the Rust engine), `CanonicalPackagerTest`, `MsgPackTest`, `EventEnvelopeTest` - plus three
  regression tests for the behaviour changes. **Full reactor `mvn clean install` on the branch: BUILD SUCCESS, 37 modules,
  237 suites, 1,767 tests, 0 failures, 0 errors, 3 skipped, 6:58 min.** `readLong` and `readDouble` were then given a
  single return each (a Sonar S1142 pre-emption); the module was re-installed and re-verified: 134 tests, platform-core's 89
  serializer tests, and the differential's four legs again - the last leg against the main checkout's compiled platform-core,
  because the reactor install had replaced the released `platform-core-4.12.20.jar` in `~/.m2` with the branch's build (the
  branch carries the same version number; a `mvn install` on main puts main's back).
- **Differential against msgpack-core** (`benchmark/msgpack-codec-harness/Harness.java`, run in separate JVMs per backend,
  outside the reactor on purpose): 20,000 seeded random documents (16.9 MB) pack to BYTE-IDENTICAL files on both backends,
  and each backend decodes the other's file with 0 mismatches. The first verify pass reported 9,124 mismatches in both
  directions - the harness's own expectation model (map keys not normalized for unpaired surrogates while values were);
  recorded in the report as the proof that the comparison can fail.
- **Benchmark** (best of 3 runs each, interleaved, idle machine, OpenJDK 27 on the Mac): the 395-byte envelope packs in 0.54 and
  unpacks in 0.55 of msgpack-core's time (446 vs 825 ns, 540 vs 983 ns); the 8 KB payload 0.39 / 0.72; the 7 KB list of 50
  records at par (0.96 / 1.03, within the ~4% run-to-run spread). The small-payload gain is msgpack-core's per-call overhead
  (an 8 KB MessageBuffer per packer, a synchronized ByteArrayOutputStream, two copies).
- **Three behaviour changes, each pinned by a test:** `org.msgpack.*` no longer transitive; every decoding failure of
  `MsgPack.unpack` is an IOException (EventEnvelope -> IllegalArgumentException, as documented; msgpack-core also threw
  unchecked `MessagePackException`s, which AsyncHttpClient caught by name); a uint64 above Long.MAX_VALUE reads as a
  BigInteger (was an unchecked overflow), as CanonicalPackager and the Rust engine already do.
- **Documentation:** `docs/test-reports/minimalist-msgpack-benchmark.md` (Eric's ask; method, environment, the table,
  what was not measured, how to reproduce; in the mkdocs nav, not in the AI contract snapshot, referenced by path and never
  by link from snapshot pages), RFC-0006 (Open) in `RFC.md`, CHANGELOG Unreleased item 10 under Changed (items 10-27
  renumbered to 11-28, one unbolded item by hand), the `api-overview.md` note under Binary serialization, the module README,
  the harness README. The Rust engine needs no change (`rmp`/`rmpv`, pure Rust, not flagged).
- **Lessons.** (1) A hostile-header check that refuses `dc 00 01` with no element behind it is right and my first test was
  wrong - write the test from the rule, not from the encoding. (2) Random text generators must pick code points, never char
  indices: a char index on a surrogate pair's low half makes an unpaired surrogate (two of my own bugs, in the module test
  and the harness). (3) `a += f()` evaluates `a` before `f()` - a trap when `f()` moves the cursor `a` tracks.
