## Review findings (Java)

1. **Fixed — null-safety:** the `parseJson` pattern switch had no `case null`; an absent
   model variable (`f:json(model.missing)`) or a nested plugin (nulled by the engine's
   loop guard) threw raw `NullPointerException` instead of the intended
   `IllegalArgumentException`. `case null, default ->` now raises the clean message.
2. **Fixed — 400 vs 500:** malformed JSON leaked Gson's `JsonSyntaxException`, which the
   top-level flow handler maps to HTTP 500 (only `IllegalArgumentException` → 400). Now
   normalized: `"Unable to parse JSON: <first line of parser cause>"` — a user error,
   and a message shape the Rust twin can match.
3. **Verified sound, documented rather than changed:** blank input → empty map
   (deliberate leniency); scalars rejected (`Input is not JSON: ...`); Gson lenient mode
   accepts unquoted keys and a trailing comma silently appends `null` (`[1, 2,]` →
   `[1, 2, null]`) — pinned in tests as a known footgun.
4. **Tokenizer verified end-to-end:** `splitTopLevelArguments` is paren-depth-aware, so
   commas/braces inside `text({...})` ride safely; `replaceWithRuntimeVar` and
   `scanDynamicIndex` pass non-`model.` segments through verbatim (Eric confirmed the
   design intent mid-session). Consequence: `{model.key}`/`[model.index]` inside the
   JSON text are substituted BEFORE parsing — documented as a dynamic-JSON feature.
5. **Two stale doc claims corrected (both engines):** the plugin intro said commas are
   unsafe inside constants (tokenizer is depth-aware — only an *unbalanced* `)` can
   mis-split) and flow-schema-reference said nested plugin calls are supported (the
   engine deliberately nulls them).
6. Sonar smells cleared in the new test (S5778 single-invocation lambda, S1612 method
   ref) — field gate holds Overall Code to zero majors.
