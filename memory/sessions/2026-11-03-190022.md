# Session (2026-11-03T19:00:22.000Z)

**Agent:** Claude Code
**Title:** the mini-scheduler retries a slow state resolver or environment store, and the firing id rides the resolver's parameters

## Context

The field's engineers reported that the state resolver occasionally timed out in their dev environment: the scheduler's
`expires` request gave up after 5 seconds with an unhandled exception, and the resolver logged its claim ("good to go")
187 ms later, so the work succeeded and only the reply was late. (The report named a job; that name identifies the field's
business and stays out of the repository and memory.) Eric first raised both scheduler timeouts to 10 seconds on `main`,
asked for a review, then proposed a short timeout with 3 retries instead, so a cold start is recorded in the log.

## Review findings (before the redesign)

- The resolver timeout matched the symptom; the environment store's did not - its read already degrades to the last value.
- `run.scheduled.job` has ONE instance (`@PreLoad`'s default), and every scheduled point blocks it twice in a row (the
  store read in `isActiveNow`, then the resolver), so a longer wait delays every other job and every completion callback.
- A resolver that claims the job while it answers `expires` strands its claim when the answer is late, and a retry would
  then find its own claim and answer "not expired" - the firing lost, silently. Hence the firing id.
- **A latent bug on the same path:** an error answer completes a PostOffice request normally, so `ActiveEnvironment.refresh()`
  took a failing store's error text as the active environment's name and put every instance on standby.

## What was done (branch `fix/mini-scheduler-store-retry`)

- Eric's rulings: retry, 3 seconds per attempt, the firing id - but as `_firing` inside the parameters, not a new header,
  because the scheduler is live in the field and a contract change means a database schema change there; a key with a `_`
  prefix is the system's by convention ([[scheduler-resolver-contract-in-parameters]]).
- `RetryRequest` (new): `po.request(event, timeout, false)` so a timeout is a 408 answer, a new request per attempt, up to 3
  retries of a timeout only; WARN per timed-out attempt, INFO for an answer after a retry, ERROR when none is answered.
  `ActiveEnvironment.refresh()` and `persist()` use it; a read counts only on status 200 (the bug above). `JobExecutor` mints
  one firing id per trigger, puts it under `_firing` in the parameters of `expires` (which had no body) and `start`, uses it
  in the correlation id, and logs a skip for no answer, an error answer, or "not expired" after a timed-out attempt.
  `JobLoader` drops a job's own `_`-prefixed parameter with a warning; the job's service and flow never see `_firing`.
- The example's `GET /api/schedule/{name}` filters `_` keys out of the stored record; both sample `StateResolver` contracts
  document `_firing` and the retry (their duplicated "2." numbered as 3). READMEs (module: *Slow answers: retries and the
  firing id*; example: a pointer). CHANGELOG Unreleased: Added 1, Changed 2, Fixed 1.
- Tests: `RetryRequestTest` (short timeouts: answered at attempt 3, all four timed out, an error not retried),
  `ActiveEnvironmentTest` (a late read retried; a store error keeps `prod`), `ResolverRetryTest` (a resolver late once is
  asked again with the same `_firing`, `start` carries it, the service body lacks it; a reserved parameter dropped at load).
- **A test race the slower suite exposed:** `SchedulerTest` registered `hello.world` in its own `@BeforeAll`, but the
  scheduler starts with whichever test class runs first; a `demo-task` run that fired earlier was spent (the sample
  resolver's 10-second window then refused the next one) and the 20-second wait ran out. `hello.world` and `hello.flow` are
  now `@PreLoad` test functions; `SchedulerTest` 20 s → 6.9 s.
- Eric's Sonar edits: `Thread.sleep` → `Utility.getInstance().sleep` in the two test functions; the same in
  `RetryRequestTest`. The ignored `offer()` results became `add()` where a test knows its event count (`ResolverRetryTest`,
  `ActiveEnvironmentTest`, `TimeZoneTest`) and a checked `offer()` with a debug line in `HelloWorld`/`HelloFlow`. Touched
  files' older findings fixed too: five lines over 120 columns and a duplicated message in `ActiveEnvironment`, a javadoc
  line ending in a semicolon in `JobExecutor`.
