## Context

After #576 closed the ASM, Vert.x and Netty advisories, Eric's IDE scan still flagged `json-smart` 2.6.0 itself
(CVE-2026-113602, 5.3, "Insufficient Information" in Mend). The session investigated, and three options were laid out:
- record the advisory as unfixed;
- close the substitution injection;
- replace json-path.

Eric chose to explore the third, "then we have more control in the future for JSON path parsing". He then asked for RFC-0010 on
a branch, stating that **RFC 9535 is preferred**: it standardizes the syntax for cross-language predictability, and moving Java
to it is a transition, because Jayway was built on the 2007 Gössner proposal long before the IETF standard.

## What was found

- **No fix to move to.** json-smart 2.6.0 (August 2025) is the latest release, for `accessors-smart` too. CVE-2026-113602 is not
  in the public databases searched.
- **json-path cannot drop json-smart.** json-path 3.0.0 (February 2026) is the latest release, and its filter engine calls
  json-smart's `JSONParser` directly (`ValueNode.isJson`, `ValueNodes$JsonNode.parse`, found by disassembly), whatever JSON
  provider is configured.
- **Reachability.** The parser reads the JSON literals of a filter. Normally that is authored text, but the knowledge graph's
  `{namespace.key}` substitution into a `$` source (`GraphLambdaFunction.substituteVarIfAny`) inserts two kinds of value
  unquoted:
  - a list or a map, as compact JSON. Its depth is bounded: the request was already parsed by the engine, and the event codec
    allows 64 levels.
  - a text value next to a dot, as written. That is a JSONPath injection: a request value can add segments or a filter. Found by
    reading the code, not yet proven by a test.
- **The Java surface is one call:** `JsonPath.read` in `MultiLevelMap`, plus `PathNotFoundException`, and the Playground's
  `InvalidPathException` in `GraphCommandService` (`HttpRouter`'s is `java.nio`'s).
- **The documented syntax is a subset of RFC 9535:** dotted paths, `[*]` and `.*`, an index, a slice, `..`, unions and `==`
  filters. Jayway's `?(…)` is a parenthesized RFC 9535 filter expression. The shared fixture `unit-test-jsonpath-1` and the claim
  `json-path-result-shape` pin ten behaviours on both engines.
- **The Rust engine is already on RFC 9535:** `serde_json_path` 0.7, with Jayway's result shape emulated in `mlm.rs`. It drops a
  parse error (`.ok()?`), so a Jayway-only path answers null on Rust while Java evaluates it. That is a silent divergence today.
- **The JSONPath Compliance Test Suite** (BSD-2) has 715 cases, 249 of them invalid selectors.

## What was done (branch `docs/rfc-0010-minimalist-jsonpath`, off `main` `1e8e05af`)

- **RFC-0010 in `docs/arch-decisions/RFC.md`** (Open). It covers:
  - the module `system/minimalist-jsonpath` (RFC 9535 in full over Mercury's `Map`/`List` trees, `java.base` only, a bounded
    query cache);
  - the two Mercury rules kept on both engines (Jayway's result shape; a hyphen in a dotted name);
  - refusal by name, at the call and at deployment (CompileGraph and the flow compiler), with Rust moving off its silent null;
  - limits on nesting;
  - substitution as data (quoted literals and bracketed names; a list or map refused);
  - six behaviour changes, an evidence plan (the suite shared with Rust, the fixture, a Jayway differential outside the reactor,
    a benchmark, a JaCoCo gate), the size against `minimalist-msgpack` (1,136 lines of code and 1,058 of tests),
    WP1–WP5, options (a)–(d) and five open questions.
  - The entry has no relative links, because the register is packaged into the AI contract snapshot.
- **RFC-0009** (the OneAgent proposal) exists only on `feature/dynatrace-oneagent-compatibility`, so `main`'s register goes
  0010 → 0008 until that branch merges. Its merge places 0009 between them.
