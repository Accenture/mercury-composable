**Viability (grounded by a 4-reader code study of the v4.11.0 adapter):** flow
selection is already per-message — the adapter sends `flow_id` as a per-request header
to `event.script.manager` on every record — so the feature is purely adapter-local,
ZERO engine changes. All the load-bearing seams exist: fail-fast binding validation
before any Kafka connection (`topic` XOR `topic-pattern` precedent for `flow` XOR
`flows`), `@MainApplication` start order makes `task://` route existence checkable at
startup, and the commit-after-success + retry→DLQ envelope wraps any target unchanged.

**Ratified design (Eric's incremental rulings during review):**
- Optional `flows:` rule list replaces `flow:` (mutually exclusive). Rule grammar
  `<selector>(<matcher>) -> <target>` + mandatory `default`.
- Selectors: `input.header.<name>` (case-INSENSITIVE name lookup — Kafka preserves
  wire casing) and `input.body.<key>` (composite paths, Map bodies only).
- Three matcher modes, explicit over sniffing: exact `key(value)`; wildcard `key(val*)`
  (presence of `*`); regex only via the explicit `key(regex: <expr>)` prefix — "regex
  is more an exception rather than norm" (Eric).
- **Order matters — first match wins in declaration order.** A non-match (missing key,
  non-Map body, non-string value) never errors; "when none matches" → `default`.
- Targets: `flow://<flow-id>` (existing dispatch, 5-site repo convention) and
  `task://<route>` — direct function invocation with the fixed contract: copy all
  record headers + whole payload, stamp trace/cid like the flow path, per-binding
  `ttl` (default 30s) since a bare function has no flow ttl. The explicit `task://`
  prefix deliberately diverges from the bare-route convention of internal dual-target
  sites (field-facing routing table → self-documenting).
- **`serializer: 'json'` ratified into v1** (Eric, two mid-review refinements: first
  promoted optional deserialization from future-work — "not every installation uses a
  schema registry"; then named the parameter `serializer` with the default SimpleMapper
  as the mechanism, deliberately open-ended for later extension). Semantics as spec'd:
  object→Map (body rules + Map delivery to flow/task), array/scalar delivered parsed
  but body-rule non-match, exclusive with `schema.enabled`, works for plain `flow:`
  bindings too, SimpleMapper's Gson numeric gotcha noted. **One open decision point
  flagged to Eric: parse-failure handling** — spec'd as best-effort ("try"): byte[]
  kept, falls through to `default`; the poison→DLQ alternative documented in place.
  **Also (same session): Eric CONFIRMED the parse-failure semantics** — on best-effort
  failure the raw byte[] passes into the selected flow/task input as-is; a target
  expecting something else throws, so the exception rides the existing retry→DLQ path
  naturally. Zero special handling in the adapter's processing loop. The design is now
  fully ratified with no open points; only the implementation go remains.

**Pre-existing sharp edge surfaced (separate from the feature):** Event Script
lowercases `input.header.*` references (TaskExecutor, matching HTTP-adapter
ingestion) but the Kafka adapter preserves wire casing — a mixed-case Kafka header is
unreachable in flow data mapping today. Raised as its own Open Thread; the routing
grammar's case-insensitive header-name lookup dodges the trap for routing itself.
