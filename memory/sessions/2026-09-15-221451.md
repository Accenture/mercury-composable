### 1. The template shipped dead routes — `app.env=dev` was missing

Eric's `rest.yaml` added the full playground-enabled route set to `templates/starter-graph`, but the
template's `application.properties` had no `app.env=dev`. Every one of those services is
`@OptionalService("app.env=dev")`, and `RoutingEntry.resolveServices` **skips** an entry whose service
is unregistered (`log.warn("Skip {} {} - {}")`, `validateMultipleServices` → *"Service ... not
available"*). So the template would have started clean, passed its tests, and served none of the new
endpoints. Added the switch with a production-removal note.

### 2. The `/public/index.html` classpath trap (the real find)

With dev mode on I ran the template and hit `GET /index.html` — and got **platform-core's placeholder
welcome page**, not the Playground. Both jars ship `classpath:/public/index.html`
(`system/platform-core/src/main/resources/public/` and
`system/minigraph-playground-engine/src/main/resources/public/`), and the first jar on the classpath
wins — for the static-content route (`HttpRouter` defaults to `classpath:/public`) *and* for
`GetIndexHtml`'s own `getResourceAsStream`.

Why the examples are fine and the template was not: `examples/minigraph-playground` and
`examples/distributed-cache-example` declare **only** `minigraph-playground-engine` (platform-core
arrives transitively, hence later), while the template declared `platform-core` **first**. Fixed by
ordering the engine ahead of platform-core in `pom.xml` and `build.gradle`, with a comment in both
explaining why the order is load-bearing.

This failure mode is nasty precisely because it is narrow: `mvn test`, `curl`, and even the companion
endpoint all stay green — only the browser notices. Documented in two guides.

### 3. Layer 3 — one endpoint, one flow

The example's `/api/l3/profile` + bespoke `l3-profile.yml` are replaced by the standard
`/api/graph/{graph_id}` + the `graph-executor.yml` flow copied verbatim from the template. Deleted the
now-dead `l3-profile.yml` and its `flows.yaml` entry; refreshed the stale `MainApp` javadoc (which also
still claimed the cache value was an `EventEnvelope` — stale since PR #395).

### 4. The graph rejects an unknown action (Eric's request)

`profile-cache`'s decision node ended `IF ... '=save' THEN encode ELSE cache-delete`, so *any*
unrecognised or absent action **deleted the profile**. Now every action is matched explicitly and the
fall-through goes to a new `reject` node —
`int(400) -> output.status` + a message, the idiom `starter-quote` already used and that
`GraphExecutor.executionComplete` supports (*"a graph may stage its own HTTP status declaratively"*).
No Java needed. Added `layer3RejectsAnUnknownAction`, which also asserts the record **survives** a
rejected request — the regression the old graph would have failed.
