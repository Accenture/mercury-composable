## Context

A graph deploys at startup only: bundled and listed in the manifest (ADR-0011), or as a graph set the manifest names
(ADR-0027); the 4.12.19 lane adds an external manifest and still restarts; nothing undeploys. Before the draft arrived
the current state was read from the code and the guides: `CompileGraph` runs once at `@BeforeApplication`,
`compileManifest` has no runtime caller outside tests, `CompiledGraphs` is four static concurrent structures whose
`removeGraph` serves the later-wins replacement only, the executor deep-copies the model at run start, every
Playground service is already gated on `app.env=dev` (so the draft's "prototyping workspace in dev mode" is the current
code), `UnpackGraphSet` already takes a `.pack` as a raw body, and an unregistered route answers 503.

## The review (round 1)

The draft - bundled graphs and the workspace unchanged, a third folder under two switches, a set uploaded to a
deployment endpoint and registered without a restart, undeploy by set, user-defined functions in language-pack sidecars,
the dashboard owned by the field - is right in every item, and every primitive exists. The spec refined four things the
draft left open: who owns a graph id at run time (manifests own theirs, one hot set owns an id, a re-upload replaces its
set; collisions 409, never later-wins, since shadowing a bundled graph would be undeploying it by another name), how a
set replaces its previous version (the registry as one immutable snapshot swapped once, so a run never sees half a set),
how a deployment survives a restart (an engine-written record in the folder, the allowlist at reconcile; a hand-copied
package ignored), and what the switches do when off (the folder is never read; today's engine exactly). Round 1
recommended a periodic check of the record for several instances.

## Decisions (round 2, Eric, 2026-11-24)

- Every recommendation accepted as the default (D1 to D12; Q2 to Q9 as recommended): the set as the unit, both switches
  off, `location.graph.deploy` (default `file:/tmp/deploy`), the ownership rules, the optional `X-Graph-Set-SHA256`
  header with the verifier route as a seam only, one swap per deployment, the record as the allowlist, a refused upload
  leaves no files, the route advisory that never refuses, the list endpoint, suspended runs declared not drained, the
  Rust twin in the sprint, POST for undeploy, the gateway alone for authentication, no Playground action this sprint.
- **Several instances: on-demand registration, no poll** (Eric's direction, in place of round 1's periodic check). His
  first form was per graph: a miss looks for `<graph-id>.json`, a hit checks `file.exists()`. Refined here to one
  revision marker read per registry lookup of a hot-deployed or unknown id, with a whole-record reconcile under the lock
  when it moved, because the per-graph form misses a replaced set (the file exists before and after), would refresh a
  set one graph at a time and lose all or none, and would make the folder the allowlist. Eric chose the marker, confirmed
  that it keeps all or none per set on every instance, and that a developer cannot drop a graph into the folder - the
  endpoint is the only door at run time, as the manifest is at startup.
- **Ids (Eric's question):** uniqueness across the engine is enforced, not recommended - one flat namespace, 409 for a
  second set carrying an id; inside a set the package format enforces it. A self-contained set (its subgraphs under ids
  of its own) is the declared design rule, and the deploy advisory also lists `graph.extension` targets outside the set.
  His follow-ups: whether the one-owner rule is a necessary safeguard - yes, reuse across sets is by reference to a set
  of its own, never by containment, because a graph with two owners leaves undeploy, replace and the certified-artifact
  question without one answer (a private copy is renamed before packing; a dangling reference shows in the advisory);
  and that a composable function, unlike a graph, is safely reused by every graph that names its route - the function
  boundary is where the shared utilities of graphs live (ADR-0001), the point of the sidecar recommendation.
- **Round 3 (Eric, the same sitting):** a set has exactly one main graph and zero or more subgraphs; only the main
  graph is used at `/api/graph/{graphId}`; the reference for on-demand registration is the main graph id, which must be
  unique; and the set is named after its main graph. Taken as D14 and D15: the set name is the main graph's id (the
  set-name rule already uses the graph-id character set; `graph_id` when present must equal it), one string is the
  handle at every surface, the undeploy path is the main graph id, and a hot-deployed set's subgraphs are private at
  REST, at OpenAPI and to another set's `graph.extension` - enforceable at both edges because the executor already
  tells an HTTP entry from an extension's dataset. D13 revised: the set's own record `<id>.deployed.yaml` is the
  marker, which removes round 2's global file and the last-writer race between administrators deploying different
  sets. Checked before the rewrite: no bundled set declares `graph_id`, so a startup-lane set keeps its free name and
  public graphs with nothing to migrate (Q10 leaves a later alignment of the lanes open).
- **Round 4 (Eric, after PR #671 merged):** "add a feature update in the graph.task node to support a new property that
  holds the provider URL" - because the engine's Event-over-HTTP map is loaded once at startup, a hot-deployed graph
  that calls a custom composable function in a sidecar cannot resolve the provider's address without a restart.
  Reviewed against the code: `PostOffice.eRequest` (and `asyncRequest`, `request`) already takes security headers and
  a fully qualified endpoint, the static map's `target` is the full URL and is consulted before local discovery, the
  skill's reachability check refuses a route that is neither local nor mapped, `for_each` uses the batch request
  which has no endpoint form, an unresolved `${X}` leaves `/api/event` with no host, and the Rust Event API client's
  endpoint split already supplies `/api/event`. Five recommendations accepted as D16: transport headers as a list
  property (the one gap in the draft; a configured server alias not taken), the reachability check skipped with the
  provider's 404 as the node's error, `server.url` winning over local and the map, the gate requiring an absolute URL
  after resolution wherever `task` is consumed, `for_each` per element. Eric's adjustment: node properties are a
  multi-level map, so `server` cannot be a leaf and a parent - the endpoint is `server.url`, the headers
  `server.header[]`. Folded into the spec as 3.10 (out of scope moved to 3.11), D16, Q11 and the work packages, into
  the register entry's proposal, options (I) and resolution, and into the thread.
- **Round 5 (Eric):** "for easy prototyping, please update the react UI to support hot deploy into the
  minigraph-playground and hot undeploy from a dialog panel. when dev mode is disabled, please provide a template
  command line script (e.g. node mjs) to upload a graph set into a target engine and another one to undeploy". Taken
  as D17, reversing Q8: a **Deploy** dialog on the Playground's packaging panel (`GraphSetPanel`, `useGraphSetPanel`,
  which already packs on the engine and inspects a dropped package) - pack and deploy, the digest in the browser with
  an expected digest sent as the header, the deployed-sets table with undeploy, the switches-off hint - and two Node
  scripts in `templates/starter-graph/scripts` beside the AI companion broker, under the folder's rules (zero
  dependencies, Node 22 or newer, the only copy). Both are clients of the same endpoints; the engine changes nothing.
  Folded into the spec as 3.11 (out of scope moved to 3.12), D17, Q8's reversal and WP2c/WP2d, into the register
  entry and the thread. Not built: the endpoints do not exist yet, so the UI and the scripts follow WP1 and WP2.
- Impact on the ledger, to be written at promotion: ADR-0011 amended (deployment stays explicit and gated, no longer
  restart-scoped; a set may register at first use on an instance that did not receive it, still through the record and
  the gate; hot-dropping still does nothing; compiled-or-404 stands), ADR-0027 extended (the set as the run-time unit;
  the loader's pieces shared).

## WP1 built (the same sitting, on the maintainer's word "Start WP1"; branch `feat/hot-deploy-wp1`)

- **The registry** (`CompiledGraphs`): one immutable `Snapshot` (graphs by id with model, location and set; the
  deployed locations) behind an `AtomicReference`, writers serialized on a `ReentrantLock`, readers lock-free; the
  public API unchanged; `replaceGraphs(removeIds, models, location, set)` for one swap; `getGraphsOfSet`; a `Refresh`
  hook consulted on `getGraph` and `graphExists` with the id and the compiled copy's location (null when unknown), the
  plain accessors (`getGraphLocation`, `getGraphSet`) left without it so the hook's own work never re-enters it.
- **The loader** (`GraphSetLoader`): `gate`, `sha256`, `normalizedPath` and `folderOf` package-private for the
  hot-deployment class; `meetsUnpackFolder`; `checkUnpack` refuses an unpack folder that is the hot folder, inside it
  or above it.
- **`HotDeployment`** (new, `start` package): `configure()` from the properties (`graph.hot.deploy`,
  `graph.hot.undeploy`, `location.graph.deploy`, `graph.hot.deploy.throttle`) or explicitly for a test; a folder that
  is not `file:/`, is the temp folder or inside or above it, or cannot be written turns hot deployment OFF for the run
  with an ERROR; `reconcileAll()` after the manifests refuses a hot folder that meets an unpack folder, adds the
  location to the deployed locations (after the manifests, so the bundled folder stays primary), removes leftover
  staging folders, reconciles every record and warns of a package no record names; the hook `check`; `reconcile`
  per set as the spec's 3.7 says, with the record parsed from its file; `deploy`, `undeploy`, `list`,
  `isPrivateSubgraph`. Staging: a set's package and graph files are written to `.staging-<random>` inside the folder,
  gated there through the shared `gate` (the readback resolving `${...}` for this environment), then moved into place
  by atomic rename - so a refused upload leaves nothing and a refused replacement leaves the previous version intact.
- **Decisions made while building, open to the maintainer's review:** the record is parsed from its file (not from a
  temporary copy), and the hook's "unchanged" test compares the record's bytes as read at registration; a reconcile
  whose new version fails the gate keeps the previously registered copy and marks the set refused (the list shows
  it); the deploy of bytes already deployed answers `changed: false` and rewrites nothing; `undeploy` of an invalid
  name is 400 and of a bundled graph 404 (the folder never holds a record for one); the `Refused` exception carries
  the HTTP status (400, 404, 409, 500, 503) and every reason for WP2's entries; `canDeploy`/`canUndeploy` for the
  entries' `@OptionalService` twins; `getDeployedLocation()` stays the first manifest's folder.
- **Tests:** `HotDeploymentTest` (12) with the full test application, the gate-refused set built through the canonical
  packager directly (the packager refuses it, as the loader test does); the three classes green together, and the
  whole engine module with its upstream modules built (`mvn -o test -pl system/minigraph-playground-engine -am`):
  296 tests, 0 failures, 0 errors. No `synchronized` outside a comment; no line over 120 columns in the new and
  changed sources. The CHANGELOG entry waits for WP2, when the feature is reachable over REST.

## WP2 built (the same sitting, on the maintainer's word "Start WP2"; branch `feat/hot-deploy-wp2`)

- **The REST surface:** `DeployGraphSet`, `UndeployGraphSet`, `ListDeployedGraphSets` in `rest`, each
  `@OptionalService` on its switch (`OptionalService` takes a comma-separated OR, so the list registers under either),
  mapping `Refused` to `AppException(status, message)`; the deploy answer carries the deployment and an advisory
  computed from the registered models: a task route known here (local or in the Event-over-HTTP map), unknown, or

  subgraph. The three entries in the engine's, the example's, the starter-graph template's and the test application's
  `rest.yaml`; `UnpackGraphSet.packageBytes` shared for the body.
- **D15, private subgraphs:** `GraphExtension.forwardEvent` adds `parent_graph` (the caller's id) to the target's
  dataset - a top-level key the HTTP flow adapter never writes, so a REST caller cannot claim to be a parent;
  `GraphExecutor.createInstance` answers 404 for a private subgraph unless the parent is a graph of the same set at
  the same location; `GetGraphOpenApi` answers 404 for one.
- **D16, `server.url`:** `TaskServer` in `common`. Found while building: the config reader that reads a graph back
  at the gate normalizes a dotted property key into a nested map, so a compiled node holds `server: {url: ...,
  header: [...]}` while a draft in the Playground holds the flat `server.url` the author typed - exactly the
  multi-level shape the maintainer named when he chose `server.url` over `server`; the helper reads both forms. A
  URL without a path gets `/api/event`; `GraphTask.invokeTask` and the `for_each` fan-out (one `request` per element,
