**Root cause (proven live before any fix):** the graph-scoped store contract (v4.11.6, ADR-0013)
keys records by `graph:{graph_id}:{cid}`, but the playground DRY-RUN lane
(`GraphCommandService.handleInstantiateGraph`) constructed each `GraphInstance` with an ephemeral
`PLAYGROUND + "-" + uuid` handle — Eric's Redis held two orphaned
`graph:playground-<uuid>:order-1001` records, one per submit, unreadable by any later
instantiation (each resume probed under a THIRD uuid). Pre-v4.11.6 the key was `graph:state:{cid}`
so the ephemeral handle was harmless — the identical hidden-blocker shape as the graph.extension
random-UUID cid (R2). The production executor lane always passed the stable manifest id — which is
why every existing suspend/resume e2e (executor-lane) stayed green. The Rust twin had the
identical bug (`commands.rs` `playground-{uuid}`).

**The fix (+ Eric's ruling):** the dry-run instance now carries the model's stable identity — the
root node's `name` property, which the export path keeps in sync with the graph's file/deployment
id (`Expect root node name=<filename>`), so dry-run and executor scopes match.
**Eric's ruling: a suspend/resume model whose root has NO name is REJECTED at instantiation** with
a teaching message ("...needs a stable identity. Add a 'name' property to the root node...") — my
first draft's silent ephemeral fallback would have broken resume invisibly for exactly the case
that matters. A nameless draft WITHOUT suspension keeps a unique playground handle (scratch drafts
unaffected). Guard-first ordering = rejection has no side effects (prior instance kept, no temp
write); Eric's S3776 catch (complexity 18) fixed by extracting `instantiateGraph` from
`handleInstantiateGraph` (the established helper-extraction shape). Java =
`stableGraphIdentity`/`rootName`/`usesSuspension` + the guard; Rust = `stable_graph_identity`/
`root_name`/`uses_suspension` + the guard in `handle_instantiate` (first attempt landed at the
