## What happened

### 1. Redis client separation — commit `3c7cabea`

Eric's ruling: the two modules *should* instantiate separate `RedisClient`s, and the `redis.*`
fallback exists for backward compatibility where sync-over-async runs alone. I had scoped this
against the live code in the previous session ([[ot-redis-client-separation]]), so the work was
purely editorial — nothing in the code changes, because `RedisBackendFactory` already builds a
client per call and every endpoint-defining key resolves per namespace.

The old text in both guides presented shared-vs-separate **neutrally** ("a deployment can point both
at one server, or decouple them"). New *Separate Redis clients, by design* section in
`distributed-cache.md`, a matching reframe in `sync-over-async.md`, and pointers from both
`configuration-reference.md` sections. The three points a reader cannot derive from a config table:
separation of concerns; the **decisive** operational reason — a cache with an eviction policy under
memory pressure can evict a `request:{cid}` rendezvous key **mid-request**, leaving the caller
waiting for a reply that can never arrive; and the partial-override trap (the fallback is per key,
so `soa.redis.host` without `soa.redis.password` inherits the other module's credentials).

Durable lesson, recorded on the thread: **a backward-compatibility affordance reads as a
recommendation unless the docs say otherwise.** State what a fallback is *for*.

### 2. P4 — Berkeley DB retired

The threads from 2026-07-05 specified this precisely, which made it a scoping exercise rather than a
design one. Removed: `BdbElasticStore`, the `elastic.queue.store` switch, `deferred.commit.log`, the
`elastic.queue.cleanup` reserved route, and platform-core's `com.sleepycat:je` dependency.

Two decisions I put to Eric rather than assume, because each changed what I'd build:

- **`benchmark-reporter`** — its whole purpose was the file-vs-bdb A/B. Eric: keep it, as a
  single-store benchmark of the in-memory event system for validating milestone releases, **and keep
  the original BDB-vs-File reports**. So `analysis/` is preserved intact and reframed as the
  historical record (with an explicit note that the comparison is no longer reproducible), while the
  runnable tool, its HTML footer, and the mixed-workload narrative lose the A/B framing.
- **`ServiceQueue` dual dispatch** — Eric chose to collapse it. This is the architectural half of the
  change: the store *determined* the dispatch model (a carrier-pinning store had to run inline on the
  loop), so retiring it leaves one mode — every route on its own virtual thread via a bounded
  mailbox. It is also the riskiest part of the diff, being the hot path for every route.

Test handling worth noting: `ElasticStoreParityTest` existed to prove the file store matched BDB.
With no second implementation its name became a lie, but its assertions are exactly the contract BDB
had proven — so it became `ElasticStoreContractTest` (file-only, loop unwrapped) rather than being
deleted. platform-core stayed at **493 tests**, which is the check that the retirement lost no
coverage.
