# Session (2026-10-30T22:04:05.000Z)

**Agent:** Claude Code
**Title:** the mini-scheduler gains a job's optional time zone, so a cron statement follows daylight saving

## Context

Eric asked whether a field installation whose business hours are local, while its scheduler's JVM runs on UTC, must edit its
cron hours at a daylight-saving changeover. It must: `JobLoader` built each trigger with
`CronScheduleBuilder.cronSchedule(...)` and no zone, so Quartz read the statement in the JVM's default zone, and UTC has no
daylight saving. Setting `TZ` or `user.timezone` would fix the scheduler but also move the log timestamps, the Event Script
date plugins' default zone and `Utility`'s local-date helpers, so it was not advised before a changeover. Eric asked for the
enhancement on a feature branch and a PR (no RFC).

## What was done (branch `feat/mini-scheduler-timezone`)

- **`jobs[].timezone`** in the cron file: `JobLoader.getZone` parses it with `ZoneId.of` (a region such as
  `America/New_York`, or an offset such as `UTC`); the trigger gets `.inTimeZone(TimeZone.getTimeZone(zone))`. A job without
  the key keeps `ZoneId.systemDefault()`, the old behaviour. An unknown id rejects the job with an error at startup, through
  the loader's existing invalid-entry path: `java.util.TimeZone.getTimeZone("America/NewYork")` answers GMT, so the obvious
  one-liner would have run a misspelt job at the wrong hour. The startup line names each job's time zone.
- `ScheduledJob` gains `public final ZoneId zone` and a five-argument constructor; the four-argument one was removed at Eric's
  request (IntelliJ: never used; `JobLoader` is the only caller).
- `TimeZoneTest` (three tests) with two 2099-only jobs in the test `cron.yaml` (`eastern-probe`, `misspelt-zone`): the
  trigger's zone, its UTC fire times on both sides of a changeover (13:00Z in June, 14:00Z in December for 09:00 New York),
  the default zone for a job without the key, and the rejected job with no trigger.
- Docs: the configuration reference's Scheduler section (a `jobs[].timezone` entry; `deferred.start` and `leader.election`
  marked as cron-file keys), the mini-scheduler README (*Time zone*), the example README and a commented line in the
  example's `cron.yaml`. CHANGELOG Unreleased: a new `### Added` heading (Added 1) and Documentation 3.
- **Quartz's changeover behaviour, measured on Quartz 2.5.2** rather than taken from its javadoc (which says "a skip or a
  repeat"): with `America/New_York`, `0 30 2 * * ?` does not fire on 2027-03-14, and `0 30 1 * * ?` fires once on
  2026-11-01, at 01:30 EST (06:30Z), the second pass. The docs state that.
