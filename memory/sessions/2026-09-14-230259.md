### 1. Extracted the `redis-connection` foundation (commit `5b73f311`, refactor)

Pulled the Redis client layer out of sync-over-async's `support/` into a new lean module
`extensions/redis-connection` (package `org.platformlambda.redis`, deps: platform-core + lettuce +
embedded-redis) that more than one extension can reuse — realizing the "extract a foundation" half of
[[cache-separate-from-soa]]. Key design moves:

- **Generified `RedisBackend<V>` by value codec.** Keys stay `String`; `V` is the codec's value type.
  sync-over-async programs against `RedisBackend<String>` (unchanged behaviour); the cache uses
  `RedisBackend<byte[]>`. The standalone/cluster seam survives generification because
  `RedisCommands<K,V>` and `RedisAdvancedClusterCommands<K,V>` both extend `RedisClusterCommands<K,V>`
  for ANY V. Added `async()` (the common `RedisClusterAsyncCommands<String,V>`) for pipelining.
- **Prefix-parameterised `RedisConfig.from(config, prefix)`** — `soa.redis.*` or `redis.*`, both falling
  back to the base `redis.*` (the fallback logic generalised to `get(prefix+suffix, get("redis."+suffix,
  default))`). `from(config)` still defaults to `soa.redis.` so existing sync-over-async callers are
  untouched.
- **`RedisHealthCheck` → `RedisHealthProbe`** — the probe logic de-annotated (removed `@PreLoad`),
  because a foundation `@PreLoad` function would auto-register in EVERY consumer under
  `web.component.scan=org.platformlambda`. Each module now binds it with a thin `@PreLoad` subclass:
  `SoaRedisHealthCheck` (`soa.redis.health`) in sync-over-async, `CacheRedisHealthCheck`
  (`redis.health`) in the cache. `resolveDurationMs` became `protected static` for the subclasses.

sync-over-async became a consumer: added the `redis-connection` dependency, updated imports +
`RedisBackend<String>` type decls in `SyncRuntime`/`ReturnRouteCoordinator`/`StreamResponder`/
`SyncOverAsyncAutoStart`, `new StandaloneRedisBackend<>(client, StringCodec.UTF8, false)`, migrated the
Redis tests to the foundation (git tracked them as renames), and added a small `SoaRedisHealthCheckTest`
for the subclass wiring. The one external consumer touched was the demo's `StreamProducer` import

intermediate. redis-connection **30 tests** green; sync-over-async **62 tests** green, coverage gate met.

### 2. Built `extensions/distributed-cache` (commit `bb88e65c`, feature)

The generic Redis-backed L2 cache as one composable action function `v1.cache.redis`
(`@OptionalService("redis.cache.enabled")`), per draft-design-specs/distributed-cache.md (Q1–Q8):

- `RedisCacheStore` over `RedisBackend<byte[]>` (`RedisCodec.of(StringCodec.UTF8, ByteArrayCodec)`):
  PUT (`SETEX`), GET, MGET (cross-slot scatter-gather), **MPUT = pipelined per-entry SETEX** via
  `async()` + `LettuceFutures.awaitAll` (TTL-preserving, not raw MSET), DELETE, PUT_IF_NOT_PRESENT
  (atomic `SET NX EX`), LIST_PUSH (atomic `RPUSH`+`EXPIRE` Lua — the return-route idiom), LIST_POP,
  LIST_LEN. Optional `redis.cache.key.prefix` namespaces every key (stripped again on MGET output).
- **One shared multiplexed connection, no pool** ([[cache-separate-from-soa]] §4.4): `CacheRuntime` holds
  the single `RedisBackend<byte[]>`; `redis.cache.instances` (`@PreLoad envInstances`, default 20) is
  worker concurrency, all sharing that connection. **Lazy** build (app starts even if Redis is briefly
  down; a late credential is picked up on retry — the [[preload-before-mainapp-lazy-config]] pattern;
  cache calls then fail fast and `redis.health` reports waiting), so no eager `@MainApplication`
  autoloader (unlike sync-over-async, which must keep a live subscriber).
- `RedisCache` dispatches on the `action` header via a `Supplier<RedisCacheStore>` test seam.

distributed-cache **32 tests** green (embedded Redis, port 16383). Full reactor `mvn install` **green**
(34 modules). Foundation/consumer fixtures given distinct embedded-Redis ports (16381/16382 vs
16379/16380 vs 16383) so a parallel `-T` build can't collide.
