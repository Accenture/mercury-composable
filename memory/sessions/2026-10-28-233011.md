## Decisions (Eric, round 2, 2026-10-28)

- The outcome envelope carries an optional approval.
- The transcript lives in an access-controlled store, so the state machine stays small.
- The split is agreed: an opaque transcript, normalized calls, and the pack builds the tool-result message.
- A graph with an agent loop is asynchronous: an HTTP 202 advice through a flow's `execution: response` plus a notification,
  or a watched WebSocket or streaming session that gets progress and the final result. With suspend and resume, a run spans
  days.
- No nesting: each agent loop is a graph node, and the graph sequences them.
- The node calling the loop carries a mode, `auto` by default, which the graph can override. A high-risk write asks a person.
- MCP clients live in the language packs. No engine runs a child process.
- The loop lives in the engines: Java first, then the Rust port catches up.
- The route is `llm.run` (Eric's proposal; I agreed). The component is "the agent loop".
- Approval is declared per use case: a business `decision` (a boolean, or a 1-based integer) routed by the graph, with the
  tools anticipated at design time.
- The draft is formalized as an RFC, to be refined before implementation.
- Development uses the packs' Claude API backend.

## Decisions (Eric, round 3, 2026-10-28 — the spec's Q1-Q7)

- The modes `auto`, `manual` and `unattended` are agreed. No mode runs a marked row without a person.
- `max_turns` is the run's budget: a node setting with a global default, and a proxy for cumulative input tokens. There is no
  token limit.
- Audit retention has a global default in the application's configuration.
- `llm.run` lives in a new opt-in module, `extensions/agent-loop`.
- The deferred final response exists in Event Script only. MiniGraph gets it as a node that runs a subgraph or a flow
  asynchronously.
- The progress contract is agreed in principle, and I proposed its schema.
- The language packs get store access, so the transcript lives in the pack's store.
- Each agent loop has a narrow scope, so its turns stay few, and a graph may hold several loop nodes.

What changed in the spec as a result:

- The transcript moved from an engine-named store route to the pack's own store, so the engine holds no store client.
- Approval now defers the whole turn, so no second store holds results kept back.
- A settings table: node inputs, each with a global default `llm.run.*` key. The keys were checked against the existing
  engine `llm.*` keys and the value-and-parent rule.
- `graph.extension async=true`: no `output[]` and no `for_each`, refused by CompileGraph.
- The progress event schema: `progress`, plus the terminal `result` and `error`, with `seq` stamped by one engine route.
- Four smaller open questions: Q8-Q11.

## Decisions (Eric, round 4, 2026-10-28 — the spec's Q8-Q11)

- The defaults stand: 10 turns, a 64 KiB result limit, a 7-day transcript TTL and retention 0.
- Transcripts may share the suspend store's Redis, under their own prefix and namespace (`transcript:` beside
  `graph:{graph_id}:{cid}`; a Redis ACL can confine the pack's user to its prefix).
- The progress route is the caller's, not an engine route:
  - for REST, `async.http.response` (final result only) or the progressive-rendering reply lane;
  - for an event such as a Kafka message, the route in its `x-return-path` header.

  The engine relay that stamped one `seq` per session was dropped; `seq` now counts per sender. A node opts in with
  `progress=<text>`, and only then does its function receive `x-return-path`. A function that forwards its headers
  downstream therefore cannot leak a caller's return path.
- `async=true` supports `for_each` for parallel fan-out:
  - `concurrency` bounds the active runs;
  - the `for_each` suspension rules apply unchanged;
  - a use case that needs one notification for the whole set starts one asynchronous subgraph that fans out
    synchronously inside.
- No open question remains. One default was set without a ruling: v1 does not forward the model's own progress notes.

## Decision (Eric, round 5, after the PR opened)

- **`x-return-path` is generic:** a function route name. It may be served locally, over Event-over-HTTP, or by a
  wrapper that publishes to a Kafka topic, keyed by `cid` so that one run stays in order on one partition. A new
  transport is a new wrapper function, not an engine change.
- **I proposed three rules to bound it**, pending Eric's confirmation on the PR:
  - the engine sends and never waits, and a failing return route does not fail the run;
  - a receiver orders a sender's events by `seq`, since separate Event-over-HTTP calls can arrive out of order;
  - only routes the application declares in `return.path.routes` are honoured, and a REST entry ignores an inbound
    `x-return-path` header. Otherwise a caller could direct events at any route it can name, a store or a write
    included.

  No existing configuration key starts with `return.`. Pushed to PR #595 as `ba60d62a`.

## Findings

- **The pack never speaks Bedrock Converse.** Both Bedrock surfaces go through the Anthropic SDK's clients
  (`AsyncAnthropicBedrockMantle` and `AsyncAnthropicBedrock`), which use the Messages format. The real risk runs the other
  way: normalizing the transcript would lose the thinking blocks that the 5.5 models need back unchanged. Hence the opaque,
  append-only transcript. It travels as JSON text, so no engine codec re-encodes a provider block
  (`conv-serialization-gotchas`).
- **`llm.chat` accepts only string message content today** (`_turns`), so the loop contract is a real pack change:
  tool-use, tool-result and thinking blocks have to round-trip.
- **`graph.task` bounds a call by the graph's `model.ttl`** (30000 ms unless the graph sets it), and a `GraphInstance`
  keeps one `reply_to` and replies once at the end. Progress sent from a node mid-run is engine work, the concept's Q8
  follow-up.
- **The MCP client is the official MCP SDK** (`mcp` on PyPI, `@modelcontextprotocol/sdk` on npm). The Anthropic SDK's
  `anthropic[mcp]` extra only converts an MCP session's tools for its own tool runner (beta), which a route binding does not
  use. This answers Eric's question.
- **API facts the spec states**, checked against the claude-api skill:
  - all parallel results go back in one message, with `is_error` on a failure;
  - forced `tool_choice` is a 400 on the 5.5 models;
  - thinking blocks go back unchanged, and an edited history is rejected;
  - `refusal` and `model_context_window_exceeded` are stop reasons;
  - the cache usage fields are `cache_creation_input_tokens` and `cache_read_input_tokens`;
  - sampling parameters are refused.

  The tool-name pattern `^[a-zA-Z0-9_-]{1,128}$` and the shared grammar budget come from the prototype, not the skill.
- **`graph.extension` always waits for its target today.** The node's result is the target's output body. So an
  asynchronous start is a new property, not a new skill. A graph can already answer 202, because tutorial 14 maps
  `int(404) -> output.status`, so the generic `/api/graph/{graph_id}` endpoint needs no variant flow.
- **No partial gate for nesting.** A pre-flight check could refuse a row that names `llm.run` but not one that reaches it
  through a flow, so the rule is declared and not enforced (`clean-knowledge-design-over-engine-coverage`).
