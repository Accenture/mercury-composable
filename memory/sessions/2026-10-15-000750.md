## What We Did

- **Eric relayed a field installation's question:** multiple insert/update statements are slow in PostgreSQL - can they run "in parallel
  with a single connection"? Investigated `extensions/reactive-postgres`: `PgRequest.update` is one autocommitted statement per call on a
  pooled connection; `batch`/`transaction` chain the statements sequentially on one connection in one transaction; the pool is
  `postgres.connection.pool` (default 20) with 200 `PgService` instances. The R2DBC driver (r2dbc-postgresql 1.1.2) serialises every
  statement on a connection through one conversation queue (`ReactorNettyClient.exchange`), and PostgreSQL itself runs one statement at a
  time per backend - so the answer is **no**: parallel statements on one connection only queue. The levers are round trips and commits.
- **Measured** with a throwaway test on the module's embedded PostgreSQL (500 single-row inserts, two runs): sequential autocommit
  800/650 ms; one transaction of 500 statements 323/249 ms; 500 statements in flight over the pool via `po.request(List)` 267/191 ms;
  ONE multi-row INSERT 94/98 ms. The embedded round trip is ~0.1 ms, so the field's gap over a network is far wider. Recommendations
  relayed: a multi-row statement (or `unnest`/`UPDATE ... FROM (VALUES ...)`), `transaction()` for atomic groups (one commit, not N
  flushes), fan-out across the pool for independent statements, then the database side (indexes, triggers).
- **Eric: "please add the multi-row insert helper to PgRequest."** Built on `feat/pg-multi-row-insert` (commit `1d5143b1`, pushed; PR is
  Eric's to open): `insertRows(po, table, columns, rows[, onConflict])` builds `INSERT INTO t (c) VALUES ($1, ...), ($n, ...)` through the
  public `multiRowInsert(...)` builder, appends an optional `ON CONFLICT` clause (upsert / DO NOTHING), validates table (optionally
  schema-qualified) and column names as plain identifiers because they are written into the SQL, refuses a list or map value (the
  statement classes rewrite a list parameter into the SQL text for IN clauses), and splits a large set into statements of at most 1000
  parameters executed in one `transaction()` - all or none. Tests: the builder in `StatementTest`, the round trip, upsert, DO NOTHING
  and five refusals in `ReactiveDbTest.insertRowsTest`, and 2500 rows across 13 statements in `insertRowsBeyondParameterLimitTest`
  (429 ms). Module suite green (ReactiveDbTest 8, StatementTest 7, SqlStatementTypesTest 7). README section and CHANGELOG `Unreleased`.
- **Finding worth keeping - the 1000-parameter cap.** The first cut used PostgreSQL's 65535-parameter limit and 13108 rows took 22 s
  (first seen as a 5 s request timeout). Spring's `DatabaseClient.GenericExecuteSpec` is immutable: `PgService.bindParamsToStatement`
  calls `bind()` once per parameter and each call copies the binding set, so a statement's cost is quadratic in its parameter count.
  Capped at 4000: 5.0 s; at 1000: 4.1 s - the constant and the comment carry the numbers. The remaining time is the event-system
  serialisation of a 65k-parameter PoJo, acceptable for the field's sizes and not engineered around ([[clean-knowledge-design-over-engine-coverage]]).
