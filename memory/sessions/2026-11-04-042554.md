**Title:** an aborted Event Script flow whose caller cannot be told was never closed - failing tests, fix, PR #610

## Context

A side session started from the RFC-0011 step 3a session (#609). Reading `TaskExecutor` there raised a suspicion:
`abortFlow` sends its error to `flowInstance.replyTo` before `endFlow`. A flow launched with no callback has a null
`replyTo`, and `EventEmitter.send` throws "Missing routing path" on a null destination. The brief: prove it with a
test first, and fix it only if the test fails.

## Verified - real on two of three abort paths

`FlowAbortWithoutCallbackTest` launches `abort-without-callback-test` with no callback. A probe task records the
flow instance id (`model.instance`), then fails, stalls past a 500 ms dataset ttl, or passes on to a task whose route
is not deployed. Each case asserts that `Flows.getFlowInstance(id)` is null within 2.5 s. Against the unfixed code:

- **Timeout: fails.** The timeout abort runs outside `handleEvent`'s `try`, so the exception escapes. The instance
  stays in `Flows` and runs on when its slow task answers, after its deadline; it stays for good if the task never
  answers.
- **Missing route: fails.** The first abort is the `catch`'s own, so the exception escapes there too. The instance
  stays until its ttl watcher fires (10 s).
- **Task failure, no handler: passes.** The abort runs inside the `try`, so the `catch` calls `abortFlow` again. That
  call skips the send, because the flow is already marked responded, and closes the flow. The only trace is a
  misleading "Unable to execute flow ... - Missing routing path".
- **Control:** the same timeout with a callback passes (408 delivered, flow closed).

## Fixed (PR #610, branch `fix/event-script-abort-without-callback`, commit `3a9b4c06`)

- `abortFlow` sends only when `replyTo` is not null, as `sendResponse` already did. With none, it logs
  `Flow <id>:<instance> aborted with status <status> - <reason>` at error level, so an operator's alerting still
  sees the abort that "Missing routing path" used to signal. It then reaches `endFlow`.
- `abortFlow` and `sendResponse` are the only two senders to `flowInstance.replyTo` in the repository.
- CHANGELOG: `## Unreleased` gained `### Fixed` 1. The heading sits above the `---` before `## Version 4.12.28`, and
  the released sections diff empty against `v4.12.28`.
- The test waits with `Utility.getInstance().sleep`, the repo's convention: no test in the repository calls
  `Thread.sleep` (Sonar S2925).

## A callback route that is gone - added on Eric's word (second commit on #610)

A scratch test then showed the same shape with a non-null address: a callback route that no function serves, as on
the mesh when the caller's instance has left. On the timeout path the send threw "Route ... not found" and the
instance leaked. The brief prescribed the null guard only, so the question went to Eric, who answered "Add it to
#610".

- Three committed cases with `GONE_CALLBACK` (`abort.probe.callback.gone`, never registered). On the first commit's
  code the timeout and the missing route failed (2 of 7), and the task failure passed through the second abort.
- `abortFlow` moves the send into `sendAbort`, which catches the `IllegalArgumentException` `EventEmitter.send`
  documents for a missing route or address. It logs `Flow <id>:<instance> aborted with status <status> - <reason>.
  Unable to tell <route> - <cause>`, and `endFlow` always runs. It catches rather than using `finally`: an exception
  that still escaped would reach `handleEvent`'s `catch`, whose second `abortFlow` would run `endFlow` again and emit
  the flow's trace twice.
- With the guard: 7 of 7. Each abort leaves one record, and no "Unable to execute event script" line remains.
- Reactor: BUILD SUCCESS, 270 suites, 2953 tests, 0 failures, 3 skipped, in two legs. `minigraph-playground-engine`'s
  fork first failed with "Address already in use", because another session's test run in the main checkout held
  port 8090. It was resumed with `-rf :minigraph-playground-engine` once that run ended. Concurrent sessions share
  the fixed test ports, so before a reactor run, check `lsof -iTCP:8090 -sTCP:LISTEN` as well as the `pgrep`.
- Not changed (read from the code, not tested): `sendResponse` to a gone callback still throws. The flow does not

  skipped. Nobody is there to receive the response, so it was left as it is.
