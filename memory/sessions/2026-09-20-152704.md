His reason: an AI agent had **hard-coded the static decision table inside a composable function and

**Finding — no engine gap, on either engine.** `GraphLambdaFunction.initializeWithNodeProperties` (Rust
`initialize_with_node_properties`) copies every node's properties into the state machine at
instantiation: a skill node's non-reserved properties at `{node}.{key}`, a **skill-less node's whole
property map at `{node}`**. `DataMappingHelper.getLhsElement` resolves ANY selector against the state
machine (no namespace whitelist), so a `graph.task` input entry `state-rules -> table` hands the whole
table to the function in one line — exactly the ask. The property grammar already gives the human-readable
table: `keys[]=rule-a` / `rule-a[]=CA` appends into list properties (`MultiLevelMap` empty-index append),
the Playground renders a list property one row per element under its key (`MinigraphNodeBody.tsx`) and
the editor round-trips same-key rows as `[]` lines; a nested table is one `'''…'''` JSON text property
parsed by `f:json(state-rules.table)` at mapping time (plugin arguments accept any mapping source). No
compile gate or pre-run check inspects mapping SOURCES (`GraphModelValidator` and `CompileGraph` check
RHS metadata writes and the `->` shape only), and node type names are free text (`with type
DecisionTable`). The ONLY statement of this anywhere was one row of the namespaces table
(`{node-name}` — "a node's own properties") plus a half-sentence in the `graph.data.mapper` reference;
the `graph.task` reference, its in-Playground help and the AI agent guide never showed a data node feeding
a function — which is why an agent had no pattern to follow.
